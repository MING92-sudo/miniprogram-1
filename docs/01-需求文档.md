# 2. 系统总体需求

## 2.1 系统定位

系统定位为"作业工具+管理平台+合规通道"三位一体：

- **作业工具**：维保人员通过微信小程序完成现场签到、逐项作业记录、电子签名、故障上报
- **管理平台**：维保部通过管理端进行计划调度、实时监控、异常闭环、数据统计、绩效考核
- **合规通道**：系统自动将维保记录、故障隐患、使用单位确认等数据按监管接口规范上报智慧平台

## 2.2 用户角色

| 角色 | 使用端 | 核心职责 |
|---|---|---|
| 维保人员 | 微信小程序 | 接收工单、现场签到、填写记录、签名提交 |
| 配合维保人员 | 微信小程序 | 协同签到、配合签名 |
| 班组长 | 小程序+管理端 | 任务转派、班组概览、异常初审 |
| 维保部管理员 | 管理端 | 计划管理、排班调度、异常终审、报表导出、参数配置 |
| 使用单位安全管理员 | 微信小程序 | 接收通知、查看记录、签名确认、服务评价 |
| 系统管理员 | 管理端 | 用户权限、接口配置、日志审计、数据备份 |

## 2.3 系统架构约束

- 前端：微信小程序（维保端、使用单位确认端）+ Web管理后台（管理端）

# 3. 功能需求

## 3.1 认证与权限模块

### 3.1.1 平台认证服务对接

**功能描述**：系统调用智慧平台认证服务获取token，后续所有业务接口调用均需携带token。

**接口约束（依据V1.5规范2.1）**：

| 项目 | 要求 |
|---|---|
| URL | `https://{AUTH_ROOT}/login` |
| 请求方式 | POST |
| 请求参数 | username（平台分配）、key（平台分配）、appcode（平台分配）、secret（平台分配） |
| 返回格式 | JSON |
| 返回字段 | code（200成功）、message、data.access_token、data.expires_in（秒） |

**业务规则**：
- token有效期默认3599秒（约1小时），以返回的expires_in为准
- 【2026-09-28平台提示】**在有效期内请勿重复调用登录接口**——系统采用"被动获取"策略：Redis缓存token（TTL=expires_in−60秒），缓存存在直接使用，过期后按需重新登录，不做定时主动刷新
- token失效时业务接口返回认证失败，系统应清除缓存、重新登录并重试原请求（最多重试1次）
- 多实例并发获取token需通过分布式锁保证同一时刻仅一个实例调用登录接口
- 认证凭证（username/key/appcode/secret）由智慧平台分配，存储于系统配置中，不得硬编码在前端

### 3.1.2 用户登录与身份绑定

- 维保人员首次使用：微信授权登录 → 手机号验证 → 绑定人员档案
- 使用单位安全管理员首次使用：接收短信/微信邀请 → 微信授权登录 → 绑定手机号 → 关联使用单位
- 管理端：账号密码登录 + 可选短信二次验证

> 【V2.2 修订】原"人脸采集入库"步骤取消。

### 3.1.3 权限控制

按2.2节角色定义实现功能级权限控制，接口层校验用户身份和角色权限。

## 3.2 单位与主体管理模块

### 3.2.1 维保单位档案

**功能描述**：维护本维保公司基础信息，用于向智慧平台注册和后续接口调用。

**字段要求**：
- 单位名称、统一社会信用代码（organizationCode）、联系人、联系电话、资质证书编号及有效期
- **维保经理姓名（maintainerName）与手机（maintainerPhone）**——必填，依据见下
- 单位名称和统一社会信用代码必须与智慧平台注册信息一致

> **【V2.5 新增】维保经理是平台强制必填项，且必须是"独立的第三个人"**
>
> 依据 V1.5 规范 2.6：`workMenegerName`（维保经理）与 `workMenegerPhone`（维保经理手机）**均标注(必填)**。
>
> 经原文复核，2.4（updateWorkState）**没有职位/角色字段**，其入参仅 `workManName`/`workManCertificate`/`workStartDate`/`workEndDate`/`changState`/`workManPhone`/`certificateFile` 七项；2.5（queryWorkList）返回的字段中同样**无角色标识**。因此：
> 1. `workMenegerName`/`workMenegerPhone` 是**纯文本，不引用平台人员ID**，平台侧不对其做人员存在性校验——这也意味着 2.6 的 `workMan1Id`/`workMan2Id`（平台人员ID）与维保经理是**两套不同的标识体系**；
> 2. 规范 2.6 备注要求维保经理与维保人员1、维保人员2的手机号**不能重复**，故维保经理**不能兼任**本次作业的维保人员；
> 3. 维保经理为**单位级角色**（非工单级），维护在 `company` 档案，变更不影响历史记录。
>
> 详见 3.2.4 手机号约束、2.4（`workMeneger*` 拼写说明）。

### 3.2.2 获取主体ID

**接口约束（依据V1.5规范2.2）**：

| 项目 | 要求 |
|---|---|
| URL | `https://{API_ROOT}/entity/queryID` |
| 请求方式 | POST |
| 请求参数 | organizationCode（统一社会信用代码，必填）、unitName（单位名称） |
| 返回字段 | code（"200"成功/404未查询到，字符串型）、message、unitName、organizationCode、**entityID（主体ID，已核对原文确认字段名）** |

> **【V2.5 更正】2.2 是"通用主体查询接口"，不限于维保单位**
>
> 原文服务说明为「通过**单位**名称查询**单位**主体的ID」，且接口位于 `entity/` 命名空间下（与 2.3 updateServiceState 同级），**未对单位类型作任何限制**。因此本接口被调用**两次**：
>
> | 调用对象 | 入参 | 落库字段 | 用途 |
> |---|---|---|---|
> | 维保单位（本单位） | 本单位 organizationCode + unitName | `company.entity_id` | 单位主体标识 |
> | **使用单位**（每一家） | 使用单位 organizationCode + unitName | `use_unit.entity_id` | **2.3 updateServiceState 的必填入参 `useUnitEntityID`** |
>
> 此前文档仅在 3.2.1 语境下描述本接口，导致使用单位主体ID来源不明，现予明确。

**业务规则**：
- 系统首次配置时调用，将返回的主体ID持久化存储
- 单位信息变更后需重新调用获取最新主体ID
- 查询失败（code=404）时提示管理员核对单位名称和统一社会信用代码
- **使用单位建立服务关系（2.3）前，必须先通过本接口取得其 `use_unit.entity_id`**

### 3.2.3 使用单位档案与维保服务关系维护

**使用单位档案字段**：
- 使用单位名称、统一社会信用代码、使用单位主体ID（useUnitEntityID，**来源见3.2.2：调用2.2接口获取**）
- 使用单位负责人姓名及手机（unitPrincipal、unitPrincipalPhone）

**接口约束（依据V1.5规范2.3）**：

| 项目 | 要求 |
|---|---|
| URL | `https://{API_ROOT}/entity/updateServiceState` |
| 请求方式 | POST |
| 必填参数 | useUnitEntityID、changState（0建立/1终止）、serviceStartDate、serviceEndDate |
| 选填参数 | useUnit（使用单位名称）、contractFile（维保合同PDF**文件流**，≤20M；含文件时为multipart/form-data请求） |

**业务规则**：
- 建立维保服务关系时changState=0，终止时changState=1
- 合同起始和截止日期格式为yyyy-MM-dd
- 合同文件为PDF格式，大小不超过20M
- 服务关系变更需记录操作日志
- **建立服务关系前必须已完成 3.2.4 全部手机号互斥校验**，不通过则不调用平台接口

### 3.2.4 手机号互斥约束（V2.5 已重新核实，重要）

**依据V1.5规范2.6备注**（原文）：
> 「使用单位单位负责人、使用单位安全管理员、维保经理、维保人员1、维保人员2手机号码不能重复。严重事故隐患代码列表内可包含多种严重事故隐患码。」

> **【V2.5 更正】此前版本将本条表述为"会导致上报失败的规范缺陷"，属于判断过重。经原文逐字复核，准确结论如下。**

**互斥字段的精确范围**——备注仅列举 5 项，**其余含手机号字段不在互斥范围内**：

| 字段 | 是否参与互斥 | 说明 |
|---|---|---|
| `unitPrincipalPhone` 使用单位负责人手机 | ✅ 参与 | |
| `elevatorAdministerPhone` 使用单位安全管理员手机 | ✅ 参与 | |
| `workMenegerPhone` 维保经理手机 | ✅ 参与 | |
| 维保人员1、维保人员2 手机 | ✅ 参与 | |
| **`emergencyPhone` 紧急联系电话** | ❌ **不参与** | 原文备注未列举，可与其他字段重复 |
| **`recorderPhone` 维保记录填写人手机** | ❌ **不参与** | 原文备注未列举；填写人通常就是维保人员1/2之一 |

**业务含义**：该规则与"电梯维保作业须两人以上"的行业惯例一致，属**合理的业务约束而非规范缺陷**。无论按"记录内互斥"还是"平台人员身份唯一"两种读法，均收敛到同一结论：

| 单位侧 | 要求 |
|---|---|
| 使用单位 | 负责人 ≠ 安全管理员（需 **2 名不同人员**） |
| 维保单位 | 维保经理 ≠ 维保人员1 ≠ 维保人员2（需 **3 名不同人员**） |

**业务规则（关键设计点：校验时机前移）**：

> 若只在 2.6 上报前校验，将导致"工单已生成 → 人员已到场作业 → 签退自检通过 → 上报失败"，且失败根因是数月前使用单位资料填写有误，**现场无法补救、无法追溯**。因此校验必须前置。

| 时机 | 校验内容 | 失败处理 |
|---|---|---|
| ① 使用单位建档（`use_unit` 维护） | 负责人手机 ≠ 安全管理员手机 | 阻止保存，返回明确提示 |
| ② 维保单位建档（`company` 维护） | 维保经理手机必填且格式合法 | 阻止保存 |
| ③ 建立服务关系（2.3 前） | ① + 维保经理手机与该单位全部在册人员手机比对 | 阻止调用平台接口 |
| ④ 排班派工前 | 主/配合维保人员手机互斥、且均 ≠ 维保经理手机 | 阻止排班，提示改派 |
| ⑤ 上报前（2.6 提交前） | 上述五项全量复核 | 阻止提交，**并直接给出可操作的原因**（如"使用单位负责人与安全管理员手机号相同，请到使用单位档案中修正"） |

- 人员档案维护时即进行手机号唯一性校验，从源头避免冲突
- **不满足条件时，电梯不得进入排班池**——避免维保人员白跑现场
- 相关待确认事项见清单 #2、#3

**接口约束（依据V1.5规范2.5）**：

| 请求方式 | POST |
| 参数 | changState（默认0正常）、workEndDate（大于当前系统日期） |
| 返回 | 人员列表，含id、workManName、workManCertificate、workStartDate、workEndDate、workStat、workManPhone |

> **【V2.5 重要】响应结构为非标准 JSON，必须实现容错解析**
>
> 原文返回示例如下（已逐字提取）：
> ```json
> {
>   "code":"200",
>   "message":"操作成功"
>   [ { "id":"123456", ... }, ... ]
> }
> ```
> **数组与 `code`/`message` 平级并列，这在 JSON 中是非法的。** 这是规范原文的书写错误，但平台实现可能确实是这种形态。适配层必须按**三级回退**解析，并把原始响应报文完整留存以便追溯：
>
> | 优先级 | 解析路径 |
> |---|---|
> | 1 | `data` 为数组 → 取 `data` |
> | 2 | 根级为数组 → 取根级数组 |
> | 3 | `data` 为对象且含列表字段（如 `list`/`rows`/`records`） → 取该字段 |
> | 4 | 以上皆失败 → 判定为解析失败，**记录原始报文并告警，不静默返回空列表** |
>
> ⚠️ 特别提醒：**解析失败时严禁当作"空列表"处理**。若误判为空会导致 `platform_id` 全量同步失败，进而使所有维保人员不可派工（因为 `workMan1Id` 缺失），且故障现象隐蔽。

> **【V2.5 重要】2.4 不返回人员ID，必须经 2.5 同步**
>
> 原文 2.4（updateWorkState）的返回值示例**只有** `{"code":"200","message":"操作成功"}`，**不包含任何人员ID**。此前接口文档写"平台建立成功后返回/分配的人员ID"属于**事实错误**。
>
> 而 2.6 的 `workMan1Id`/`workMan2Id` **必须是平台人员ID**。因此正确的同步链路是：
>
> ```
> 2.4 建立人员（certificateFile 必传）
>        ↓  仅返回 code/message，无ID
> 2.5 queryWorkList 轮询查询
>        ↓  返回含 id 的完整人员列表
> 按 workManCertificate 精确匹配 → 取得 id
>        ↓
> 写入 employee.platform_id
>        ↓
> 2.6 上报时 workMan1Id / workMan2Id 引用该ID
> ```
>
> **实现要求**：
> - 匹配键为 `workManCertificate`（证书编号，平台内唯一），**不可用姓名匹配**（可能重名）
> - 2.4 建立后**状态置为"待同步"**，同步任务在 5~30 秒内重试 2.5，最多等待 5 分钟
> - 同步到 ID 后人员方可**启用与派工**；未同步到 ID 的人员**不可分配工单**（否则 2.6 上报必然失败）
> - 匹配不到或多条匹配（证书编号重复）→ 告警管理员人工处理，不自动选第一条

**业务规则**：
- 系统定期同步平台人员列表，与本地档案比对
- 本地新增人员需先通过updateWorkState在平台建立，**再经2.5同步取得 platform_id**，成功后本地方可启用
- 人员状态（workStat）为normal**且 `platform_id` 非空**方可被分配工单

## 3.4 电梯信息管理模块

> **【V2.5】TSG T5002 第二条的品种例外**
>
> 原文：「**消防员电梯、防爆电梯的维保单位，应当按照制造单位的要求制定维保项目和内容。**」
>
> 含义：这两类电梯**不能套用附件 A—D 的标准模板**，须按其制造单位说明书单独制定。
>
> 实现：检查项模板支持 `source=STANDARD(标准附件)` / `source=CUSTOM(自定义)`。品种为消防员电梯或防爆电梯时：
> - 建档时必须上传该机型的《安装使用维护说明书》；
> - 检查项模板**禁止使用标准附件**，须走自定义模板流程（基于标准模板复制后增删改）；
> - 管理端在排班时提示"该品种需按制造单位要求配置模板"，未配置则不允许排班。
>
> 附件 A—D 仅覆盖曳引/强制驱动、液压、杂物、扶梯人行道四类，故此项为必需而非可选。

### 3.4.1 电梯电子档案

**字段要求**：
- 电梯编码（elevatorCode）、电梯注册代码（registrationCode）、电梯设备代码（deviceCode）、电梯出厂编号（factoryNumber）
- 使用单位主体ID（useUnitEntityId）、单位内编号（insideNumber）
- 使用单位安全管理员（elevatorAdminister）及手机（elevatorAdministerPhone）、紧急联系电话（emergencyPhone）
- 安装地址（含经纬度，用于签到定位校验）
- 电梯类型、品牌型号、制造单位
- 下次检验日期、下次维保日期（nextMaintenanceDate）

> **【V2.5 新增】基本技术参数——TSG T5002 第七条、八条法定必填**
>
> 第七条要求维保记录必须包含"电梯的基本情况和技术参数"，第八条按**电梯品种**分别规定了具体参数。**此前版本的电梯档案缺失全部这些字段**，将导致维保记录不满足法定要求，也无法生成合规报表。
>
> | 电梯品种 | 必录技术参数（TSG T5002 第八条） |
> |---|---|
> | 曳引与强制驱动电梯（曳引乘客/曳引载货/强制驱动载货） | 驱动方式、额定载重量、额定速度、层站门数 |
> | 液压驱动电梯（液压乘客/液压载货） | 额定载重量、额定速度、层站门数、**油缸数量**、**顶升型式** |
> | 杂物电梯 | 驱动方式、额定载重量、额定速度、层站门数 |
> | 自动扶梯与自动人行道 | 倾斜角、名义速度、提升高度、名义宽度、主机功率、**使用区段长度**（仅人行道） |
>
> 另据第七条，维保记录还须包含：**整机制造/安装/改造/重大修理单位名称**、电梯品种（型式）、产品编号、设备代码、电梯型号或改造后型号。
>
> 实现要点：
> - **设备品种（category）是主数据字段**，直接决定 3.7.3 检查项模板取哪一套（TSG T5002 附件 A/B/C/D 四个品种、四套模板），必须先于其他参数确定；
> - 参数按品种**动态显隐**，只展示该品种法定项目；
> - 数值型参数支持正常范围提示（如额定载重量 1000kg），并在维保时提示"与登记参数是否一致"。

> **【V2.5 重要】安装地址与经纬度没有平台数据来源**
>
> 经逐字核对 V1.5 规范 2.7，其返回字段**仅有** `elevatorCode`、`useUnitEntityId`、`elevatorAdminister`、`registrationCode`、`deviceCode`、`elevatorAdministerPhone`(脱敏)、`emergencyPhone`(脱敏)、`factoryNumber` —— **不含安装地址、不含经纬度、不含使用单位名称、不含下次检验日期**。
>
> 结论：**平台无法提供电梯位置**。3.7.2 的 200 米定位校验所依赖的坐标只能由以下途径获得：
>
> | 途径 | 优先级 | 说明 |
> |---|---|---|
> | 使用单位建档时提供（物业系统导出/Excel导入） | 首选 | 建立服务关系时批量导入 |
> | 新梯首次建档时由维保人员现场采集并回填 | 兜底 | 现场定位 + 人工确认地址文字 |
> | 缺失时的降级策略 | — | 允许建档但标记"位置待补"，**该电梯可作业但签到仅作定位留痕、不做超阈拦截**，并在管理端高亮待补 |
>
> 该条同时是 3.7.2 定位校验失败率的主要来源，须在实施阶段重点关注坐标质量。

> | 维保记录**已上报成功** | 平台侧日期已固化且**无法修正**；延期仅在本系统内生效（计划日期、预警、考核均按新日期），并生成《计划变更说明》留档 |
>
> 实现要求：延期审批通过时**必须检查该电梯最近一次维保记录的上报状态**，已上报的批次额外标注"平台侧日期未同步"，管理端在工单监控中可筛出此类记录，避免误以为平台侧已同步。
>
> 该限制已列入待确认清单向平台提问：是否存在维保记录更正/计划变更接口。

## 3.7 维保工单与现场作业模块（核心模块）

### 3.7.1 工单生成与推送

- 工单编号规则：WD + 年月日 + 流水号
- 工单通过微信订阅消息推送至维保人员服务通知
- 工单内容：电梯信息、维保类型、计划日期、检查项清单、历史故障摘要

### 3.7.2 现场签到——双重验证 + 存证（V2.2 修订）

> 【V2.2 修订】取消人脸识别环节，签到验证由"三重"调整为"两步验证 + 现场存证"。

**第一步：扫码/NFC识别**
- 扫描电梯二维码或靠近NFC标签（仅Android），自动识别电梯并进入工单
- 扫码响应时间≤1秒

**第二步：定位校验**
- 获取当前位置坐标，与电梯登记地址坐标计算距离
- 阈值默认200米（管理端可配置，**支持按电梯/按设备品种单独设置**——地下室与地面机房定位漂移差异大，全局单一阈值会大量误判）
- 超出阈值禁止签到，允许提交"定位异常说明"并附照片，由管理端审核
- **【V2.5】电梯坐标缺失时的降级**：按 3.4.1，平台不返回经纬度。若该电梯标记为"位置待补"，签到**只记录定位留痕、不做超阈拦截**，并在管理端高亮提示补录坐标

**第三步：现场存证（替代原人脸识别）**
- 签到时拍摄水印自拍照片（叠加时间、定位、电梯编号、姓名）
- 照片仅作作业留痕与人工抽检依据，不做任何生物特征比对
- 未上传存证照片的签到记录标记"待核查"，不影响签到流程

> **【V2.5 口径统一】"待核查"的判定标准**
>
> 此前 3.3.5 写"**连续**未上传存证照片"、3.7.2 写"未上传"、接口文档写"`selfPhotoKey` 为空"，三处口径不一。现统一为：
>
> | 规则 | 内容 |
> |---|---|
> | 判定 | **单次签到**未上传存证照片 → 该次签到标记"待核查" |
> | 升级 | 同一维保人员**连续3次**签到未上传 → 标记"重点核查"，推送管理员 |
> | 闭环 | 管理端抽检通过后人工解除标记，保留操作日志 |
>
> 该口径与 3.3.5 一致，接口层以 `selfPhotoKey` 是否为空为唯一判据。

**双人到场验证**：
- 主维保人员和配合人员分别签到
- 两者签到时间间隔建议不超过30分钟
- 两者定位坐标均应在电梯地址附近
- 支持主维保人员生成动态二维码由配合人员扫描，验证同时到场

### 3.7.3 作业记录——检查项逐项执行

> **【V2.5 重要】检查项模板的结构依据：TSG T5002 附件 A—D（257行）**
>
> 经逐字核对 TSG T5002—2017 原文，检查项**不是一张固定表**，而是 **4 个设备品种 × 4 个维保频次** 的**累加式**结构：
>
> - **附件 A** 曳引与强制驱动电梯 ／ **B** 液压驱动电梯 ／ **C** 杂物电梯 ／ **D** 自动扶梯与自动人行道
> - 原文对各频次均写明：「**除符合 X 半月维保的项目(内容)和要求外，还应当符合表 X-2 的项目(内容)和要求**」——即**取并集**，而非 4 张互不相干的表
>
> 各品种各频次的实际项目数（半月基础 + 增量 = 累计）：
>
> | 附件 | 品种 | 半月 | 季度 | 半年 | 年度 | 种子行数 |
> |---|---|---|---|---|---|---|
> | A | 曳引与强制驱动 | 31 | +13 = **44** | +15 = **59** | +17 = **76** | 76 |
> | B | 液压驱动 | 30 | +13 = **43** | +9 = **52** | +14 = **66** | 66 |
> | C | 杂物电梯 | 20 | +8 = **28** | +10 = **38** | +14 = **52** | 52 |
> | D | 自动扶梯与自动人行道 | 33 | +5 = **38** | +12 = **50** | +13 = **63** | 63 |
> | | | | | | **合计** | **257** |
>
> 例：曳引与强制驱动电梯做**季度维保**时，检查项 = 表A-1的31项 + 表A-2的13项 = **44项**。

**检查项结构**：

| 字段 | 说明 |
|---|---|
| 设备品种 | A/B/C/D，决定取哪一套模板（与 3.4.1 的 `category` 一致） |
| 生效频次 | 半月/季度/半年/年度，决定是否为增量项 |
| 检查项编码 | 如 `A-1-29`（附件-频次-序号），对应TSG T5002附件中的项目编号 |
| 检查项名称 | 如"层门锁紧元件啮合长度" |
| 检查要求 | TSG 原文的"维护保养基本要求" |
| **判定依据类型** | 绝对值／标准值／制造单位要求／定性描述（见下） |
| **正常范围** | 仅"绝对值"类填写；**随品种而异**（见下） |
| 是否关键项 | 依 TSG 注 A-2 规则自动判定（见下） |
| 结果选项 | 正常/异常/不涉及 |
| 异常描述 | 异常时必填 |
| 照片要求 | 关键项强制附照片 |
| **执行周期/季节约束** | 少数条目非每次都做（见下） |
| 备注 | 选填 |

**填写约束**：
- 不允许"一键全选正常"，每项必须手动选择
- 关键安全项强制至少1张照片，**判定依据见下方注A-2，不再靠举例法**
- 照片通过水印相机拍摄，自动叠加时间、地点、电梯编号水印
- 照片上传前压缩：长边≤1200px，单张≤500KB
- 读数型检查项提供数值输入框，支持正常范围提示
- "不涉及"项需选择原因

> **【V2.5 依据一】关键项判定规则——TSG T5002 注 A-2（原文）**
>
> 「维护保养项目(内容)和要求中**对测试、试验有明确规定的，应当按照规定进行测试、试验**，**没有明确规定的，一般为检查、调整、清洁和润滑**。」
>
> 实现：种子数据中凡基本要求含"试验/测试/校验/检测"字样的条目自动标记 `is_key=true` 且 `photo_required=true`（例：制动器动作试验、限速器安全钳联动试验、上行超速保护装置动作试验、轿厢意外移动保护装置动作试验、导电回路绝缘性能测试、制动器制动能力）。其余为一般检查项。**此规则使"关键项"有客观依据，避免主观标注争议。**

> **【V2.5 依据二】"符合标准值"不等于固定数值——TSG T5002 注 A-3/A-4（原文）**
>
> 「规定为"符合标准值"的，是指符合对应的**国家标准、行业标准和制造单位要求**」
> 「规定为"制造单位要求"的，按照制造单位的要求」
>
> 全表中大量条目为「磨损量不超过制造单位要求」「间隙符合制造单位要求」——**没有绝对数值**。维保人员若手上没有对应机型的《安装使用维护说明书》，无法独立判定。
>
> 实现：
> - `判定依据类型=制造单位要求` 的条目，UI 展示为「**按本机说明书判定**」而非数值输入框，并提示"未维护说明书时可拍照留证并备注"；
> - 电梯档案新增"说明书是否已上传"标记，未上传时该类条目允许填"正常"但**自动打标待复核**，汇总到管理端抽检清单。

> **【V2.5 依据三】正常范围随品种而异**
>
> 原文同名条目的阈值在不同品种下不同，例：
> - 表 A-1 序号29「层门锁紧元件啮合长度」**不小于 7mm**（曳引/强制驱动）
> - 表 C-1 序号17「层门锁紧元件啮合长度」**不小于 5mm**（杂物电梯）
>
> 故 `正常范围` 必须按 **附件 + 频次 + 序号** 三级维度配置，**不可设为全局唯一**。

> **【V2.5 依据四】部分条目是周期性/条件性/季节性执行**
>
> 原文存在非"每次维保都做"的条目，当前模型无法表达，需增加 `执行周期`、`季节约束`、`年限条件` 三个字段：
>
> | 原文条目 | 约束类型 | 内容 |
> |---|---|---|
> | 表A-4 序号6 限速器安全钳联动试验 | **按使用年限** | 年限≤15年：每2年一次限速器动作速度校验；>15年：每年一次 |
> | 表C-4 序号6 限速器安全钳联动试验 | **按周期** | 每5年一次限速器动作速度校验 |
> | 表B-4 序号4 限速器安全钳联动试验 | **按周期** | 每2年一次 |
> | 表D-2 序号5 防灌水保护装置 | **季节** | **雨季到来之前必须完成** |
> | 表D-3 序号12 梯级踏板加热装置 | **季节** | **冬季到来之前必须完成** |
>
> 实现：满足周期的条目显示为"本次**无需执行**（下次执行：YYYY-MM）"，仍可人工点选执行；季节性条目在对应季节前自动进入待办并在预警中提示。

> **【V2.5 依据五】"不涉及"选项有原文支撑——TSG T5002 注 A-1（原文）**
>
> 「如果某些电梯没有表中的项目(内容)，如有的电梯不含有某种部件，项目(内容)可适当进行调整。」
>
> 这正是 3.7.3"不涉及+原因"设计的法规依据。实现要求：选择"不涉及"时，**必须填写原因**，并允许上传该电梯的部件配置说明（如加装/拆除记录）作为佐证；管理端可按"不涉及"比例异常偏高的电梯/人员做抽检。

> **【V2.5 重要】维保明细数据不会上报平台**
>
> V1.5 规范 2.6 只接收汇总性字段（电梯编码、5个角色、起止时间、维保类别、人员ID、隐患码、下次维保日期），**不接收任何检查项结果、现场照片、电子签名、故障描述或视频**。
>
> 结论：3.7.3 的逐项检查记录、3.7.5 的签名、3.9.1 的故障照片视频**全部为本系统内部数据**，仅用于存档、抽检、绩效与合规报表（3.10.6），**永不到达监管平台**。请勿在对外沟通或招标材料中表述为"平台可查看现场照片"。

### 3.7.4 离线作业支持

- 进入作业界面后自动缓存检查项清单到本地
- 离线填写数据存储于小程序本地存储（wx.setStorage）与本地文件系统（FileSystemManager，照片）
- 离线期间GPS坐标和时间戳在本地持续记录
- 顶部显示网络状态标识和已缓存数据量
- 网络恢复后按时间顺序批量补传，**保留原始时间戳**
- 补传接口支持幂等性，通过originalRecordId去重
- 本地缓存支持至少50台电梯的维保记录，上传成功后自动清理对应缓存

> **【V2.5 口径明确】离线补传后 2.6 的 `startTime`/`endTime` 填什么**
>
> 此前 01 写"保留原始时间戳"、02 写"服务端以上报时间为准"，两处冲突会导致实现分歧。现明确：
>
> | 字段 | 取值 | 理由 |
> |---|---|---|
> | `startTime` / `endTime`（上报给平台） | **本地采集的原始时间戳** | 这是维保作业的真实发生时间，是监管核验的对象；用上报时间会掩盖实际超期 |
> | 作业时长、绩效统计（系统内部） | 同上，用原始时间戳 | 保证口径一致 |
> | 上报时刻（系统内部留痕） | 服务端接收时间，单独存 `report_time` | 用于响应时效与审计，不影响作业时间口径 |
>
> 实现：`maintain_record` 同时保存 `start_time`/`end_time`（原始采集）与 `report_time`（上报时刻），两者不可混用。
>
> ⚠️ 附带风险：V1.5 未定义平台对 `startTime`/`endTime` 与当前时间偏差的校验规则。若离线跨越数日（如井下作业信号中断后次日补传），可能触发平台的时间合理性校验。已列入待确认清单 #6，需在联调中验证。

### 3.7.5 电子签名

- 主维保人员和配合人员分别手写签名
- 签名带时间戳，发生在签到之后、签退之前
- 签名数据以图片形式存储于对象存储，与工单关联

### 3.7.6 签退与完工自检

- 签退时再次定位校验
- 签退后工单状态变更为"待确认"
- 作业时长 = 签退时间 - 签到时间
- 签退前自动检查：所有检查项已填写、关键项已附照片、异常项已填描述、双人签名已完成
- 未完成项红色标记，确认后方可签退

- 手机号码互斥规则见 3.2.4（**校验前移至建档期，提交前做最终复核**）

- originalRecordId为维保作业系统内部记录ID，需唯一
- 上传成功后记录平台返回状态，失败时进入重试队列（**自动重试受 `reg.retry.auto` 开关控制，默认关闭**）

### 3.8.2 存量维保记录提交（临时接口）

**接口约束（依据V1.5规范2.8）**：

| 项目 | 要求 |
|---|---|
| URL | `https://{API_ROOT}/record/uploadMaintainRecord` |
| 请求方式 | POST |
| Header | Authorization: Bearer TOKEN |
| 返回 code 类型 | **数字型 200**（与2.6的字符串"200"不同，适配层须统一转字符串比较） |
| 用途 | 仅用于维保单位提交已有存量电梯维保记录，后续将适时关闭 |

**必填参数**：elevatorCode、workType、startTime、endTime、workManName1、workManName2、originalRecordId、recorder、recorderPhone

> **【V2.5】本接口的时间格式与 2.6 不一致**
>
> 2.8 写 `yyyy-MM-dd hh24:mi:ss`（Oracle/Java Date 风格），2.6 写 `yyyy-mm-dd hh:MM:ss`。两处**不是同一种写法**，适配层对存量接口与正式接口**分别配置格式化器**，不要共用一个。
>
> **本接口的 workManName1/Name2 传姓名而非 ID**（与2.6的 `workMan1Id`/`workMan2Id` 不同），实现时勿混用。

**业务规则**：
- 该接口为临时接口，仅用于存量数据迁移
- 后续新产生的维保记录必须使用2.6接口
- 系统需在配置中标记该接口的启用状态，以便平台关闭后自动停用

### 3.8.5 上传策略

- **实时上传**：维保记录完成后即时上传
- **批量补传**：离线数据网络恢复后批量补传，保留原始时间戳（口径见 3.7.4）
- **幂等性**：通过 originalRecordId 保证重复提交不产生重复记录（**待平台确认，见下方风险提示**）
- **失败重试**：由开关 `reg.retry.auto` 控制，见下方分支策略

> **【V2.5 重要】确认状态不另行上报**
>
> 此前版本 3.8.5 写有"确认状态更新：使用单位确认后单独更新上传"。经逐字核对 V1.5 原文确认：**该能力不存在**。
>
> | 核对结论 | 依据 |
> |---|---|
> | 2.6 的 20 个必填参数中**无任何确认/签字/评价字段** | 原文参数表逐项核对 |
> | **全文关键词扫描**：`确认` 0 命中、`签名` 0 命中、`评价` 0 命中 | 全文 387 段文本扫描 |
> | **规范止于 2.8，不存在 2.9** | 目录结构 |
> | 2.6 以 `originalRecordId` 为记录标识，重复提交同一 ID 不构成"更新" | 原文无更新语义 |
>
> **处理决定（已确认）**：使用单位确认状态**仅在本地留存并纳入归档与合规报表**，不尝试上报平台。使用单位确认模块（3.12）继续保留——它是 **TSG T5002 第七条的法定要求**（"维保记录应当经使用单位安全管理人员签字确认"），由本系统内部满足并留痕。
>
> 同时**删除技术架构文档 5.2 状态机中的 `REPORTED → CONFIRMED（再次上报更新）` 环节**，`CONFIRMED` 仅作为本地终态存在。
>
> 已列入待确认清单 #5，向平台询问是否提供确认状态回传通道；若后续平台开放该能力，再评估对接。

> **【V2.5 最高风险】幂等未定义 → 两条分支策略**
>
> V1.5 未对 `originalRecordId` 作任何幂等声明（详见 3.8.1 风险提示）。在平台书面答复（待确认 #1）之前，**按保守分支实现**：
>
> | 分支 | 条件 | 行为 |
> |---|---|---|
> | **保守（默认，当前实现）** | `reg.retry.auto = false` | 上报失败**立即挂起**，状态置 `FAILED_MAX`，管理端异常清单展示，人工确认后再重传。**绝不自动重试**——宁可漏报，不可产生虚假维保记录 |
> | 乐观（联调确认幂等后开启） | `reg.retry.auto = true` | 恢复自动重试3次（间隔30秒、2分钟、10分钟），上报前先查 `reg_upload_log` 是否已有成功记录 |
>
> **联调验证方法**（必须执行）：用同一条测试维保记录，向 2.6 连续提交 3 次相同的 `originalRecordId`，观察平台侧记录数——若仍为 1 则幂等成立，方可开启乐观分支。**测试记录使用专用测试电梯编码，严禁用生产电梯验证。**

### 3.9.3 隐患分级响应

> **【V2.5 重大更正】困人救援为最高等级，法定时限 30 分钟**
>
> TSG T5002 第五条(四) 原文：
> 「设立 24 小时维保值班电话，保证接到故障通知后及时予以排除；**接到电梯困人故障报告后，维保人员及时抵达所维保电梯所在地实施现场救援，直辖市或者设区的市抵达时间不超过 30 分钟**，其他地区一般不超过 1 小时」
>
> **重庆为直辖市，法定抵达时限为 30 分钟。** 此前版本仅定义"紧急停梯 2 小时内响应"，与法定要求相差 4 倍，**属合规缺陷，现予更正**。

| 等级 | 响应时限 | 通知范围 | 依据 |
|---|---|---|---|
| **困人救援** | **接警后立即出动，抵达 ≤30 分钟** | 公司负责人+管理员+班组长（电话+短信，不依赖订阅消息） | **TSG T5002 第五条(四)** |
| 紧急停梯 | 2小时内响应 | 管理员+班组长+公司负责人 | 本系统内控标准 |
| 严重隐患 | 24小时内 | 管理员+班组长 | 3.8.3 隐患上报要求 |
| 一般隐患 | 限期整改 | 班组长 | 本系统内控标准 |

**配套要求（3.9.3.1 困人救援工单）**：
- **必须登记 24 小时值班电话**（公司级配置项），并保证电话畅通；系统对外披露该号码
- 困人事件**不走订阅消息**（推送可能不可达），采用电话告警 + 短信 + 管理端弹窗三通道
- 工单强制记录：**接警时间、出动时间、抵达时间、解救时间、解困人数、故障原因、处置措施**
- **系统自动计算并留痕各节点耗时**，抵达时间超30分钟自动标记为"超时"并上报公司负责人，超时记录不可删除
- 每月统计困人救援达标率，纳入 3.10.5 绩效考核
- 困人事件同时按 3.9.1 生成故障工单进入闭环流程

### 3.9.4 严重事故隐患码关联

- 故障上报时若涉及严重事故隐患，需选择对应的S1—S7代码

### 3.12.5 确认状态归档（V2.5 新增）

> TSG T5002 第七条：「**维保记录应当经使用单位安全管理人员签字确认**」——这是法定要求，与平台是否提供上报通道无关，**本系统必须完整实现并留痕**。
>
> 但 V1.5 规范无任何确认/签名/评价字段或接口（3.8.5 已列出核对证据），**确认结果不上报平台**。因此本系统的职责是"**内部满足 + 可举证**"：

| 要求 | 实现 |
|---|---|
| 确认主体 | 必须是该电梯 `elevatorAdminister`（使用单位安全管理员）本人或其授权代签人，**代签须留痕授权关系** |
| 确认凭据 | 手写签名图（COS 存储）+ 确认时间戳 + 确认人身份（OpenID+手机号） |
| 不可篡改 | 确认后签名与时间戳**只读**；撤销确认须走管理端审批并保留原确认记录（`01 §3.14.1`） |
| 举证输出 | 归档记录进入 **3.10.6 合规报表**与电子档案，可导出 PDF 作为 TSG 第五条(六)「归入电梯安全技术档案」及检查时的举证材料 |
| 记录留存 | 随维保记录一并保存**不少于4年**（TSG T5002 第五条(六)） |
| 超时管理 | 24小时未确认进入 3.11 预警表"使用单位确认超时" |

> ⚠️ **合规风险提示**：由于确认结果无法上报监管平台，若监管检查要求"确认状态在平台可查"，本系统无法满足。此为平台侧能力缺口，已列入待确认清单 #5 向平台提出。若平台确认无此要求，则本系统的本地留存 + 电子档案导出即可满足举证要求。

### 3.13.2 认证与Token管理

- 调用认证服务获取token（2.1接口）
- **token有效期以返回的 `expires_in` 为准（默认3599秒）**
- **【V2.5 更正】采用"被动获取+缓存"策略：Redis缓存 token，TTL = `expires_in` − 60秒；缓存命中直接使用，过期后按需重新登录；不做定时主动刷新、不提前刷新**
- 多实例并发获取通过 Redis 分布式锁保证同一时刻仅一个实例调用登录接口
- token失效时清除缓存、重新登录并重试原请求**1次**
- 本节与 3.1.1 口径一致（此前 3.13.2 仍写"提前刷新"，与平台"有效期内禁止重复调用登录接口"的提示直接冲突，现已更正）

### 3.13.3 上传失败处理

- **自动重试受开关 `reg.retry.auto` 控制，默认关闭**（原因见 3.8.5 幂等风险）
- 乐观分支下：自动重试3次（间隔30秒、2分钟、10分钟）
- 仍失败标记"待人工处理"
- 管理端展示异常清单，支持手动重传

### 3.13.4 接口安全

- **HTTPS传输**（规范1.1明确要求HTTPS，2.1认证地址亦为`https://`；2.2—2.8的`http://`前缀经核对确为笔误，平台3.20分配的地址亦全部为HTTPS。适配层保留`reg.protocol`开关兜底，默认HTTPS）
- 敏感字段脱敏或加密；**上报报文日志（`reg_upload_log`）中含5个明文手机号，须脱敏或加密存储**
- 操作日志保留不少于3年

> **【V2.5 补充】接口规范本身未定义的安全与稳定性参数**
>
> V1.5 全文对 `频率`／`限制`／`超时` 关键词**均为 0 命中**，即未定义任何限流、超时、并发约束。适配层须自行设定并在配置中可调（见 02 文档）：
>
> | 参数 | 建议值 | 说明 |
> |---|---|---|
> | 连接超时 / 读取超时 | 3s / 30s | 普通JSON接口 |
> | 大文件接口超时（2.3/2.4，≤20M） | 读取超时 ≥120s | multipart 流式转发 |
> | 令牌接口超时 | 5s | 2.1 |
> | 限流 | 平台侧未知，初版不做客户端限流，仅记录QPS日志 | 联调后按平台实际约束补充 |

- 更正需管理端审批

### 3.14.2 操作日志

记录：登录/登出、工单接收/转派、签到/签退、记录提交、签名确认、故障上报、配件申领、数据导出

日志字段：操作人、时间、类型、工单编号、IP地址

保留期限：不少于3年

### 3.14.3 数据备份与容灾

- 每日自动备份
- 支持按时间点恢复
- 照片采用对象存储，冗余备份

### 3.14.4 数据保存期限

- 维保记录保存**不少于4年**（TSG T5002 第五条(六)原文：「建立每台电梯的维保记录，及时归入电梯安全技术档案，并且**至少保存 4 年**」）
- 自行检查记录与报告（3.17）随维保记录一同保存 ≥4年
- 应急演练记录（3.18）、困人救援记录（3.9.3.1）保存 ≥4年

### 3.14.5 无纸化数据不可变更（TSG T5002 第十条，法定）

**依据原文**——TSG T5002 第十条：
> 「采用信息化技术实现无纸化电梯维保记录的，其维保记录格式、内容和要求应当满足相关法律、法规和安全技术规范的要求。**使用无纸化电梯维保记录系统的，其数据在保存过程中不得有任何程度和任何形式的更改**，确保储存数据的公正、客观和安全，**并可实时进行查询**。」

实现要求（对应 3.14.1）：
- "不得有任何程度和任何形式的更改" → 维保记录一经提交即**物理只读**，无任何更新接口
- "实时进行查询" → 维保记录查询**不得依赖归档介质**，近4年数据须在线可查（约束存储方案，见技术架构文档）
- 3.17 自行检查、3.12.5 确认签名同受此约束

## 3.17 自行检查（V2.5 新增，TSG T5002 法定要求）

**依据原文**——TSG T5002 第五条(九)：
> 「**每年度至少进行一次自行检查**，自行检查在特种设备检验机构进行定期检验之前进行，自行检查项目及其内容根据使用状况确定，**但是不少于本规则年度维保和电梯定期检验规定的项目及其内容**，并且**向使用单位出具有自行检查和审核人员的签字、加盖维保单位公章或者其他专用章的自行检查记录或者报告**」

> **【V2.5】此前版本完全缺失自行检查功能。** 该项为年度法定动作，且强制要求"签字+盖章"的正式报告，属合规硬缺口。

**功能要求**：

| 项 | 要求 |
|---|---|
| 检查计划 | 每台电梯每年至少1次；**须在下次定期检验之前完成**（系统按 `next_check_date` 反推排期） |
| 检查项来源 | **默认取年度维保项 + 定期检验项的并集**（依原文"不少于"要求），且**可按使用状况增项**；不得少于年度维保项 |
| 执行 | 现场作业模式（可复用 3.7 的检查项执行组件），结果、照片、读数留痕 |
| 报告输出 | 自动生成《自行检查记录/报告》PDF，内容含：电梯基本情况与技术参数（3.4.1）、检查项目与结果、发现问题与处置、**检查人员签字 + 审核人员签字 + 维保单位公章**（电子签章或预留盖章位） |
| 报告送达 | 送达使用单位并留痕（送达时间、接收人、方式） |
| 归档 | 归入电梯安全技术档案，与维保记录一同保存**≥4年** |
| 逾期 | 未在定期检验前完成 → 预警并上报管理员；**逾期记录不可删除** |

**与 3.7.3 的关系**：自行检查**复用**年度维保检查项模板（附件A-4/B-4/C-4/D-4），但作为**独立记录类型**存储（`inspect_record`），不占用维保记录标识，不触发 2.6 上报（V1.5 无对应接口）。

## 3.18 应急演练（V2.5 新增，TSG T5002 法定要求）

**依据原文**——TSG T5002 第五条(三)：
> 「制定应急措施和救援预案，**每半年至少针对本单位维保的不同类别(类型)电梯进行一次应急演练**」

> **【V2.5】此前版本缺失。** 注意"**不同类别(类型)**"——即演练须覆盖本单位在保的不同电梯品种（如同时维保曳引梯与扶梯，则两类均须演练），不能只演练一种。

**功能要求**：

| 项 | 要求 |
|---|---|
| 周期 | 每半年至少1轮，**覆盖本单位在保的全部电梯品种**（对照 3.4.1 的 `category`） |
| 预案 | 每种品种对应救援预案文档（困人救援、火灾、被困、停电等场景），预案可上传归档 |
| 演练记录 | 登记：演练日期、品种、场景、参与人员、演练过程、发现问题、整改措施、整改闭环 |
| 覆盖检查 | **自动校验半年内是否每种在保品种均有演练记录**，未覆盖的品种高亮提示 |
| 逾期 | 超期未演练 → 预警上报公司负责人 |
| 统计 | 演练达标率纳入 3.10.5 绩效考核与年度合规报表（3.10.6） |

## 3.19 维保质量不定期检查（V2.5 新增）

**依据原文**——TSG T5002 第九条：
> 「维保单位的**质量检验(查)人员或者管理人员应当对电梯的维保质量进行不定期检查，并且进行记录**」
