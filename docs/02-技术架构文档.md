## 1. 设计目标

1. **合规优先**：维保记录上报智慧平台是硬需求，上报链路的可靠性、幂等性、可追溯性最高优先级
2. **现场可用**：弱网/离线可作业，操作步骤少、输入少，户外强光可读
3. **数据可信**：记录不可变、留痕完整、按TSG T5002保存≥4年
4. **平滑扩展**：监管接口版本变更可配置化切换

## 5. 关键设计

### 5.1 双Token中控（最容易出错的地方）

系统涉及**两套互不相同的凭证**，严禁混淆：

| 凭证 | 用途 | 有效期 | 获取方 |
|---|---|---|---|
| 智慧平台 access_token | 调V1.5业务接口（Bearer） | 3599秒 | `GET https://{AUTH_ROOT}/login?username=…&key=…&appcode=…&secret=…`（实测为 GET+查询串） |
| 微信 access_token（stable_token） | 发订阅消息等微信开放接口 | 7200秒 | 微信API |

设计（平台2026-09-28提示：**有效期内请勿重复调用登录接口**）：
- **被动获取**：Redis 存储 `reg:token`，TTL = expires_in − 60秒（留网络余量）；缓存命中直接使用，**不做定时主动刷新、不提前刷新**
- 未命中时以 **Redis 分布式锁**（`SET NX EX`）保证多实例只有一个线程真正调用登录接口，其余等待后读缓存
- 业务调用收到 token 失效响应 → 清缓存重新登录 → 重试原请求**1次**（异常路径允许）
- 微信侧 `stable_token` 普通模式（有效期内重复调用返回同一token，天然防冲突）；微信接口返回 40001 时同样"清缓存重取 重试1次"

### 5.2 上报状态机与重试（record   regulatory）

```
维保记录状态机：
DRAFT(草稿) → SUBMITTED(已提交待上报) → REPORTING(上报中)
  → REPORTED(平台成功)
  → RETRY_WAIT(等待重试) → FAILED_MAX(待人工处理)
使用单位确认后：REPORTED → CONFIRMED(本地终态，仅本地留存，不上报)
```

> **【V1.1 更正】删除"确认后再次上报"环节**
>
> 经逐字核对 V1.5 原文：2.6 的 20 个必填参数中无任何确认/签名/评价字段；全文 `确认`/`签名`/`评价` 关键词**均 0 命中**；规范止于 2.8 无 2.9。**上报确认状态的能力不存在**，V1.0 中的 `CONFIRMED（已更新确认状态→再次上报更新）` 无法实现。
>
> `CONFIRMED` 现为**本地终态**，服务于 TSG T5002 第七条"维保记录应当经使用单位安全管理人员签字确认"的法定举证要求（见 01 文档 §3.12.5）。已列入待确认清单 #5。

> **【V1.1 最高风险】`originalRecordId` 幂等性未定义**
>
> V1.5 对该字段的全部说明仅一句"原始维保记录ID（维保作业系统原始维保记录ID）"，**无"幂等/去重/唯一"任何表述**；2.6 只返回 `code`/`message`，**不返回平台侧记录ID**，也未定义重复提交的返回码。
>
> **架构决策：默认按"平台不幂等"设计。**

| 分支 | 开关 | 行为 |
|---|---|---|
| **保守（默认）** | `reg.retry.auto: false` | 上报失败**立即置 `FAILED_MAX`**，人工确认后手动重传。**绝不自动重试**——避免在监管平台产生虚假维保记录 |
| 乐观 | `reg.retry.auto: true` | 3次重试（30秒/2分钟/10分钟）；仅在联调**实测幂等成立后**开启 |

- **幂等（乐观分支）**：`originalRecordId`（雪花ID）作为本地唯一键；上报前查 `reg_upload_log` 是否已有 `success=1` 记录，重复请求直接返回成功
- **幂等验证方法（联调必做）**：用专用测试电梯编码，向 2.6 连续提交 3 次相同 `originalRecordId`，核对平台侧记录数是否为 1。**严禁用生产电梯验证**
- 重试队列：Redis ZSet（score=下次重试时间戳），定时任务每30秒扫描；**保守分支下不写入 ZSet**
- 每次上报写 `reg_upload_log`（请求/响应报文、耗时、结果），日志保留≥3年
- **⚠️ `reg_upload_log` 报文含 5 个明文手机号，存储时须脱敏或加密**（见 §8.6）

### 5.3 离线作业方案（小程序端）

| 数据 | 存储位置 | 容量策略 |
|---|---|---|
| 检查项清单、工单数据、填写的记录 | `wx.setStorage`（按工单分key） | 总量10MB，约50台电梯记录 |
| 水印照片、签名图 | `FileSystemManager` 用户目录 | 本地约200MB，**上传COS成功后即清理** |
| 待补传队列 | `wx.setStorage` 的 `offline_queue` | 按时间戳排序 |

> **【V1.1 口径明确】"上报成功"指 COS 上传成功，不是平台上报成功**
>
> 此前 §5.3 写"上报成功后即清理"存在歧义（可能被理解为平台上报成功）。照片/签名**永远不会被上报到平台**（V1.5 的 2.6 不接收任何文件与明细，见 §5.8.9），其归档完全依赖本系统的 COS。因此清理条件是"**已成功上传 COS 且服务端已确认落库**"，与平台状态机无关。这样即使平台侧长期失败，本地照片也不会被误删导致数据丢失。
>
> 平台上报失败的记录，其 COS 资源由生命周期策略兜底，**不依赖客户端清理**。

**时间口径（消除 V1.0 与需求文档的冲突）**：

| 字段 | 取值 | 用途 |
|---|---|---|
| `start_time` / `end_time` | **本地采集的原始时间戳** | 上报 2.6、作业时长、绩效统计 |
| `report_time` | 服务端接收时间 | 响应时效、审计留痕 |

V1.0 写"服务端以上报时间为准"与需求文档"保留原始时间戳"冲突。**统一以原始采集时间为准**——维保作业的真实发生时间是监管核验对象，用上报时间会掩盖实际超期。`report_time` 独立存储，两者不可混用。

⚠️ V1.5 未定义平台对时间偏差的校验规则；离线跨日补传可能触发平台时间合理性校验，已列入待确认 #6。

补传流程：网络恢复监听（`wx.onNetworkStatusChange`）→ 按 originalRecordId 顺序批量提交 → 服务端幂等去重 → 逐条删除本地缓存。

### 5.4 签到定位校验

- Haversine 公式计算签到坐标与电梯档案登记坐标的球面距离
- **阈值三级配置**（V1.1 新增）：全局默认200米 → 设备品种级覆盖 → 电梯级覆盖。理由：地下室机房与地面机房的定位漂移差异极大，全局单一阈值会产生大量误拦截与大量申诉，管理成本反而更高
- 阈值存于系统参数表   `elevator.checkin_threshold` 字段（为空则回退品种级，再回退全局）

> **【V1.1 重要】平台不提供经纬度**
>
> 经逐字核对 V1.5 规范 2.7，返回字段仅有 `elevatorCode`、`useUnitEntityId`、`elevatorAdminister`、`registrationCode`、`deviceCode`、`elevatorAdministerPhone`(脱敏)、`emergencyPhone`(脱敏)、`factoryNumber` —— **不含地址、不含经纬度**。
>
> 这意味着 `elevator.lng/lat` 的唯一来源是使用单位提供或现场采集。架构上必须支持：
> - `elevator.geo_status`：`UNKNOWN`（未采集）/ `PROVIDED`（使用单位提供）/ `SELF_COLLECTED`（现场采集）
> - `geo_status = UNKNOWN` 时：允许建档与作业，签到**只记录定位留痕、不做超阈拦截**，管理端高亮"位置待补"
> - 采集质量治理：提供批量导入   坐标纠偏（首次由维保人员现场采集并人工确认），并监控超阈申诉率作为坐标质量指标

### 5.8 平台对接报文细节（已逐字核对V1.5原文，2026-09-29）

1. **返回码类型不统一**：2.1/2.7/2.8 返回**数字** `200`，2.2/2.3/2.4/2.6 返回**字符串** `"200"` → 适配层统一 `String.valueOf(code).trim().equals("200")` 比较。
   > **【V1.1 补充】V1.0 遗漏了 2.8**——原文 2.8 返回值示例为 `{"code": 200, "message": "操作成功", "data": null}`，同为数字型。
   > **【V1.2 实测补充】** 2.2 实际成功响应的业务数据在 **`data[]` 数组**中（规范示例写在顶层）；2.2 的 `entityID` 与 JWT `orgid` 是两个不同 ID（…360 vs …362），均落库存档。
2. **文件流上传**：2.3 的 contractFile、2.4 的 certificateFile 规范定义为"文件流"（≤20M PDF）→ 请求为 `multipart/form-data`，后端从 COS 取文件后**流式转发，不做本地落盘**（避免20M×N 的临时磁盘压力）。**读取超时须≥120s**。
   > **【V1.2 实测补充·参数格式】** 2.2—2.8 实际接收 **`application/x-www-form-urlencoded` 表单**，规范 1.1 所写"JSON 格式"与实现不符——JSON body 被当作空 body（报 10001）。仅含文件的 2.3/2.4 用 `multipart/form-data`（2.4 实测确认缺证书文件返回"关系状态为建立，作业人员电子证书或证书扫描件必传"）。
3. **2.7 返回脱敏手机号**（如 `1582****892`）：平台查询结果仅作比对参考，**不可回填用于 2.6 上报**；真实号码由本地档案维护。
4. **协议确认**：规范1.1明确HTTPS，2.1认证地址亦为 `https://`；平台实际分配的认证地址与服务根路径均为 `https://tzsb.scjgj.cq.gov.cn:1443`（1443端口）→ **2.2—2.8 的 `http://` 前缀确认为规范笔误**，按 HTTPS 实现，`reg.protocol` 开关保留兜底；若证书为自签/国密，需在客户端配置信任。
5. **workMan1Id / workMan2Id** 为平台人员ID（2.5 返回的 `id`），即 `employee.platform_id`。
6. **规范3.2码表笔误**：S3出现两次、缺S4行 → 暂按 S0—S7 连续编码，待平台确认（#9）。
7. **时间格式**：
   - 2.6 写作 `yyyy-mm-dd hh:MM:ss`（`MM` 按 Java/JS 语义为**月份**）
   - 2.8 写作 `yyyy-MM-dd hh24:mi:ss`（Oracle/Java `Date` 风格）
   - **两处互不相同**，适配层为两个接口**分别配置格式化器**，不要共用；均按 `yyyy-MM-dd HH:mm:ss` 输出，联调时以平台实际校验为准（#6）。
8. 2.8 存量接口启用开关：`reg.legacy-upload.enabled`
9. **【V1.1 重要】2.6 不接收任何维保明细**
   2.6 只收：电梯编码、5个角色姓名/手机、3个时间、维保类别、2个人员ID、隐患码、下次维保日期。
   **不接收**检查项结果、现场照片、电子签名、故障描述/视频、使用单位确认结果。
   → 01 文档 §3.7.3 的逐项记录、§3.7.5 的签名、§3.9.1 的故障照片视频**全部为本系统内部数据**，只用于存档/抽检/绩效/合规报表。**对外表述不可称"平台可查看现场照片"。**
10. **【V1.1 事实更正】2.4 不返回人员ID**
    原文 2.4 返回值示例仅 `{"code":"200","message":"操作成功"}`，**无任何ID字段**。V1.0 文档"平台建立成功后返回/分配的人员ID"属**事实错误**。
    正确链路：**2.4 建立（无回执）→ 2.5 queryWorkList 轮询 → 按 `workManCertificate` 精确匹配取 `id` → 写 `employee.platform_id`**。
    匹配键必须是证书编号（平台内唯一），**不可用姓名匹配**（重名）。详见 §5.9。
11. **【V1.1】2.2 是通用主体查询接口**
    原文服务说明为"通过**单位**名称查询**单位**主体的ID"，位于 `entity/` 命名空间，**不限维保单位**。对维保单位与每一家使用单位**各调用一次**，分别落 `company.entity_id` 与 `use_unit.entity_id`（后者是 2.3 的必填入参 `useUnitEntityID`）。
12. **【V1.1】2.5 响应是非标准 JSON，必须三级回退解析**
    原文示例将数组与 `code`/`message` 平级并列，这在 JSON 中非法。解析顺序：`data` 数组 → 根级数组 → `data` 内列表字段（list/rows/records）→ **失败则告警并留存原始报文**。
    **⚠️ 解析失败严禁当作空列表**：误判为空会导致 `platform_id` 全量同步失败、所有人员不可派工，且故障隐蔽。
13. **【V1.1】2.6 未声明 Authorization Header**
    规范仅 2.7/2.8 显式声明。适配层**无条件携带** `Authorization: Bearer TOKEN`（多余 Header 无害），待确认 #7。
14. **【V1.1】`nextMaintenanceDate` 无更新通道**
    2.6 必填该字段但无任何修改接口。延期发生在上报之后时，**平台侧日期已固化且无法修正**。实现：延期审批通过时检查最近一次维保记录的上报状态，已上报的批次标注"平台侧日期未同步"，管理端可筛选。

### 5.9 人员 platform_id 同步任务（V1.1 新增）

`workMan1Id`/`workMan2Id` 完全依赖 `employee.platform_id`，而该值**只能从 2.5 获取**。这是一条**必须实现且必须监控**的链路：

| 项 | 设计 |
|---|---|
| 触发 | ① 2.4 建立人员成功后立即触发；② 定时任务每5分钟全量比对 |
| 匹配 | 按 `workManCertificate` 精确匹配；匹配不到或**多条匹配**（证书号重复）→ 告警人工处理，**不自动取第一条** |
| 重试 | 2.4 返回后按 5s/15s/60s 重试 2.5，最多等待 5 分钟（平台入库有延迟） |
| 人员状态 | 新建人员初始为 `PENDING_SYNC`，同步到 ID 后转 `ACTIVE`；**非 `ACTIVE` 或 `platform_id` 为空的人员不可派工**（否则 2.6 必然失败） |
| 监控 | 管理端"平台同步"看板：待同步人数、同步失败清单、最近同步时间 |
| 契约证书到期 | 2.5 按 `workEndDate > 当前日期` 过滤，**合同到期人员会从平台列表中消失**，此时本地 `platform_id` 保留但人员不可派工（与 3.3.4 预警联动） |

### 7.1 凭证管理（V1.1 新增）

> 平台已于 2026-09-29 分配登录四参数。**凭证值属最高敏感信息**，以下为强制约定：

| 约定 | 说明 |
|---|---|
| **存储** | 仅存于环境变量或密钥管理服务（生产环境建议用 KMS/配置中心加密项） |
| **不入库** | `.env` 已在 `.gitignore` 排除；提供 `.env.example` 作为变量名模板，**只含变量名与格式说明** |
| **不入文档** | 代码、注释、配置样例、测试用例中一律使用 `${REG_*}` 占位符 |
| **不入日志** | HTTP 客户端日志须过滤 `Authorization` 头；异常堆栈、APM 埋点同样过滤 |
| **不入错误信息** | 认证失败时**禁止**把请求体回显到异常消息中（否则凭证进日志系统） |
| **联调抓包** | HAR/报文抓取含 `Authorization: Bearer <token>`，`.gitignore` 已排除 `*.har` 与 `reg-capture/` |
| **轮换** | 若凭证曾经聊天、邮件、即时通讯等非受控渠道传递，应要求平台轮换 |
| **拼写** | 平台通知中 `secret` 被写作 `scret`，属笔误，配置以规范 2.1 的 `secret` 为准 |

**验证平台编号对应关系的做法**（无需我方猜测）：用平台分配的凭证调用 2.1，若返回 `code=200` 即凭证组合正确。若平台编号 `821102379226763264` 既不等于 `appcode` 也不等于 `username`/`key`，则以平台明确答复为准，勿擅自替换参数。

> **【V1.1 实测结论】登录成功**
>
> 2026-09-29 实测确认：
> - `appcode` **即**企业平台编号 `821102379226763264`
> - `username` 为本公司**统一社会信用代码**（非随机串），可与 2.2 的 `organizationCode` 复用
> - `ORG_ID`（token JWT 中含 `orgid: 311715940563362`）为平台组织机构号，**规范未提及**，建议落 `company.org_id`

> **【V1.1 实测更正】登录接口为 `GET` + URL 查询串**
>
> 规范 2.1 示例写作 `POST { "username":… }`，但平台实际实现为：
> ```
> GET /api/authService/login?username=…&key=…&appcode=…&secret=…
> ```
> **按 POST + JSON body 调用会持续返回 `{"code":500,"message":"操作失败!"}`**（2026-09-29 实测），且该文案与"参数错误"完全相同，极易误导排查方向。
>
> 实现要求：
> - `RegTokenClient` 使用 `GET` + `UriComponentsBuilder` 拼装查询串，**参数需 URL 编码**；
> - ⚠️ **凭证出现在 URL 中** → 必须在 HTTP 客户端日志、APM 埋点、异常堆栈处**统一屏蔽认证路径的完整 URL**，否则凭证会经日志系统泄露；
> - 建议对 `/api/authService/login` 的 URL **只记录路径、不记录查询串**。

> **【V1.1→V1.2】接口地址全部配置化（404 + DNS 阻塞已于 2026-09-29 第五轮解决：根路径 `/api/wlw/maintenance/`、参数表单化；配置化机制保留）**
>
> 2026-09-29 实测：业务接口按平台下发地址调用**全部返回 404**（已扫描 40 种路径组合），而 `/api/actuator/health` 与 `/api/wlw/actuator/health` **均返回 `{"status":"UP"}`**。404 报文为业务格式 `{"code":404,"message":"404 NOT_FOUND"}`，说明请求已到达应用层被判路由不存在。
> **同时域名 DNS 记录失效**（系统 DNS + 阿里/腾讯/Google 三个公共 DNS 均无法解析，IP 直连正常）。准确 URL 与正式地址待平台确认（见 01 文档 #12）。
>
> 为避免此问题阻塞开发，`{API_ROOT}` 与**每个接口的路径**均改为配置项：
>
> ```yaml
> reg:
>   api-base-url: ${REG_API_BASE_URL}     # ✅ V1.2 实测确认：https://tzsb.scjgj.cq.gov.cn:1443/api/wlw/maintenance/
>   endpoints:
>     query-id:               /entity/queryID              # 2.2 获取主体ID
>     update-service-state:   /entity/updateServiceState   # 2.3 维保服务关系
>     update-work-state:      /entity/updateWorkState      # 2.4 维保人员管理
>     query-work-list:        /entity/queryWorkList        # 2.5 人员查询
>     maintenance-record:     /elevator/maintenanceRecord  # 2.6 维保记录上传
>     query-elevator-info:    /equipment/queryElevatorInfo # 2.7 电梯信息查询
>     upload-maintain-record: /record/uploadMaintainRecord # 2.8 存量记录
> ```
>
> **平台确认后仅需改配置，无需改代码**，可立即恢复联调。同时新增 `reg_token_log` 表记录 token 的 `jti`/`orgid`/`appcode`/`expires_in`（token 本体加密存储），便于多环境/多账号场景排查串用问题。
>
> **⚠️ 域名/IP 变更时的应对**：
> - 生产环境**禁止硬编码 IP**，域名是唯一入口（IP 变更即失效，且绕过 DNS 无法做证书校验）；
> - 开发/联调环境若 DNS 短期不可用，可通过 hosts 临时指向已知 IP，但**必须在平台确认后立即回退**；
> - 地址与 DNS 均应纳入 `sys_config` 或配置中心，**支持不重启刷新**，避免每次地址变更都要发版。
## 8. 安全设计

1. 传输：全站 HTTPS。**平台侧协议已确认为 HTTPS**（规范1.1明确 + 2.1认证地址为https + 3.20平台分配地址），V1.0 写的"待确认"已关闭；适配层仍保留 `reg.protocol` 开关兜底
2. 认证：小程序 OpenID 手机号绑定；管理端账号密码 JWT（可选短信二次验证）
3. 授权：RBAC，接口级权限注解（`@PreAuthorize`）
4. 数据：维保记录上传后置为只读，修正走"更正记录 审批"（TSG T5002 第十条：**不得有任何程度和任何形式的更改**）
5. 审计：op_log 全量操作留痕≥3年；reg_upload_log 报文留痕≥3年
6. 敏感信息：手机号展示脱敏（138\*\*\*\*8000）
7. **【V1.1】`reg_upload_log` 报文脱敏/加密**：上报报文含 5 个明文手机号（单位负责人、安全管理员、维保经理、维保人员1/2）。实现：
   - `req_body` 存**脱敏版**（`1582\*\*\*\*892`）用于日常排查；
   - 原始明文报文如需留存，存 `req_body_enc`（应用层 AES 加密），密钥走 KMS/环境变量，**禁止落库明文**；
   - `resp_body` 原样留存（平台响应不含手机号）。
   - V1.0 只写"数据库层手机号加密存储可后置到二期"，但**上传日志的明文手机号不能后置**——它每次上报都在产生。

## 10. 检查项模板数据准备方案（V1.1 新增）

> 背景：TSG T5002 附件 A—D 共 **257 行**标准维保项，是 `check_item_tpl` 的种子数据，也是现场作业开发的前置依赖（见 01 文档 §8.1 第4项）。

### 10.1 数据量与结构

| 附录 | 品种 | 半月 | 季度 | 半年 | 年度 | 行数 |
|---|---|---|---|---|---|---|
| A | 曳引与强制驱动 | 31 |  13 |  15 |  17 | 76 |
| B | 液压驱动 | 30 |  13 |  9 |  14 | 66 |
| C | 杂物电梯 | 20 |  8 |  10 |  14 | 52 |
| D | 自动扶梯与自动人行道 | 33 |  5 |  12 |  13 | 63 |
| | | | | | **合计** | **257** |

- `frequency` 取值：`HALF`(半月基础) / `QUARTER` / `HALF_YEAR` / `YEAR`（**增量项**）
- 季度/半年/年度的检查项 = 半月   各级增量（**取并集**，依 TSG 原文"除符合…外，还应当符合表X-2"）
- 举例：曳引季度维保 = 31   13 = **44 项**

### 10.2 整理流程

| 步 | 内容 | 责任 | 产出 |
|---|---|---|---|
| 1 | 从 TSG T5002 PDF 逐表提取 A-1~A-4/B-1~B-4/C-1~C-4/D-1~D-4 的序号、项目名称、维护保养基本要求 | 项目组 | 原始 Excel |
| 2 | 按 §6.2 字段补齐 `judge_type`（依注A-2/A-3 判定 NUMERIC/STANDARD/MANUFACTURER/QUALITATIVE） | 项目组   维保专家 | 增强 Excel |
| 3 | 依注A-2 规则自动标记 `is_key`/`photo_required`，**人工复核关键项**（法务/维保主管签字确认） | 维保主管 | 定稿 Excel |
| 4 | 录入种子 SQL / CSV 导入（管理端提供导入模板与校验） | 开发 | 257 行入库 |
| 5 | 抽样验收：各品种各频次抽 5 项核对原文 | 测试 | 验收报告 |

### 10.3 需要人工判断的部分（不可自动化）

| 情形 | 出处示例 | 处理 |
|---|---|---|
| `judge_type=MANUFACTURER`（按说明书判定） | "磨损量不超过制造单位要求" | 填"按本机说明书判定"，配 `elevator.manual_upload` 标记生成待复核清单 |
| 同名条目阈值随品种不同 | A-1-29 层门锁紧啮合 ≥7mm；C-1-17 同名 ≥5mm | **`value_min/max` 按行独立配置，不可全局唯一** |
| 周期性/条件性条目 | A-4-6 限速器校验（≤15年每2年/ >15年每年）；C-4-6（每5年）；B-4-4（每2年） | 填 `exec_cycle_month` / `age_condition` |
| 季节性条目 | D-2-5 防灌水（雨季前）；D-3-12 踏板加热（冬季前） | 填 `season_window` |
| 法定不适用 | TSG第二条：消防/防爆电梯按制造单位要求定 | **禁止用标准附件**，走 `check_item_extra` 自定义模板 |

### 10.4 消防员/防爆电梯（TSG 第二条）

原文：「**消防员电梯、防爆电梯的维保单位，应当按照制造单位的要求制定维保项目和内容。**」

- 附件 A—D **不覆盖**这两类，故自定义能力是必需而非可选
- 建档时该品种必须上传《安装使用维护维护说明书》
- 排班前校验：品种为消防/防爆 且未配置自定义模板 → 阻止排班
- 实现路径：复制对应标准模板 → 按说明书增删改 → 存 `check_item_extra`（保留 `tpl_id` 引用以复用 `is_key`/`judge_type` 规则）

## 11. 容量测算与数据留存（V1.1 新增）

> V1.0 仅写"4C8G 起步"无依据。本节按可配置的假设给出测算框架，**实际值需业务方提供在保台数后重算**。

### 11.1 测算参数（假设，需业务确认）

| 参数 | 假设值 | 说明 |
|---|---|---|
| 在保电梯台数 | 2,000 台 | **待业务确认** |
| 维保频次分布 | 半月50% / 季度25% / 半年15% / 年度10% | 行业常见 |
| 年均维保工单 | ≈ 2,000 × (0.5×24   0.25×4   0.15×2   0.1×1) ≈ **27,800 单/年** | |
| 单单检查项 | 平均 40 项（曳引半月31 → 年度76，均值约40） | |
| 单项记录 | ≈ 300 B（结果 描述 值 JSON） | |
| **维保明细年增** | 27,800 × 40 × 300B ≈ **334 MB/年** | 含索引约 **600 MB/年** |
| 照片 | 单单均 8 张 × 200KB ≈ 1.6 MB → **≈ 45 GB/年**（COS） | 压缩后 |
| 上报快照 | 单单 ≈ 1.5 KB → **≈ 42 MB/年** | |
| 上报日志 | 单均 3 次尝试（请求 响应）≈ 6 KB → **≈ 170 MB/年** | 3年 ≈ 510 MB |

### 11.2 存储规划

| 项 | 方案 | 依据 |
|---|---|---|
| MySQL 主库 | 4C8G 起步，**近 1 年数据在线**；`maintain_record`/`work_order_item` 按年分区 | TSG 第十条要求"**可实时进行查询**" |
| 归档 | 按年归档到**对象存储（COS 归档类存储）**  索引表 | ⚠️ V1.0 只写"按年归档"未定义介质 |
| 归档可查性 | 归档数据**须能在 5 分钟内检索返回**（先查索引定位分区 → 拉取归档 → 返回），不可设计为"需人工调档" | 满足 TSG 第十条"实时可查询" |
| 备份 | 每日全量   binlog 增量，**在线保留 30 天**；归档数据本身即副本 | |
| 保留期 | 维保记录/自行检查/确认签名 **≥4 年**（TSG 第五条(六)）；操作日志 **≥3 年** | |
| COS | 照片/签名/报告，**生命周期策略**：热存 1 年 → 低频 3 年 → 归档（≥4年） | 保障 4 年留存且控制成本 |

> **【V1.1 关键修正】"MySQL 备份保留30天"≠"数据保存30天"**
>
> V1.0 的部署图标注"MySQL 备份保留30天；记录表按年归档"，未说明归档到哪、能否按 TSG 第十条实时查询。归档介质与可查性必须显式定义，否则 4 年留存与实时查询的法定要求无法验证。

### 11.3 性能与容量校验

- 上年估算，主库 4C8G 满足；但**照片与明细增速需按季度复核**
- 每新增 1,000 台在保电梯，资源增量约：MySQL  300MB/年、COS  22GB/年
- 若实际台数显著高于 2,000 台，需重新评估分库分表（`maintain_record` 按 `elevator_id` 哈希分片）
