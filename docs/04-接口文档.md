## B.1 登录获取 token（规范2.1）

> ### 🔴 【V1.1 重大实测更正】本接口使用 **GET + 查询串**，不是 POST + JSON body
>
> 规范 2.1 的示例写作 `Body: { "username": "", "key": "", "appcode": "", "secret": "" }`，**与平台实际实现不符**。
> 平台实际为 **GET 请求、参数拼在 URL 查询串中**：
>
> ```
> GET https://{AUTH_ROOT}/login?username={}&key={}&appcode={}&secret={}
> ```
>
> **2026-09-29 实测对照**：
>
> | 调用方式 | 实际返回 |
> |---|---|
> | **GET + 查询串** | ✅ `{"code":200,"message":"操作成功","data":{"access_token":"…","expires_in":3599}}` |
> | POST + JSON body | ❌ `{"code":500,"message":"操作失败!","data":null}` |
> | POST + 表单编码 | ❌ HTTP 415 `Unsupported Media Type`（框架默认格式） |
>
> **该差异曾是我方联调的主要阻塞点。** 按规范用 POST 调用会持续返回 500；更麻烦的是平台对"参数错误"与"调用方式错误"返回**完全相同的 500 文案**，导致排查方向被误导到"凭证/账号/网络"上。
>
> 平台提示"在浏览器上直接访问接口地址"实为**字面意思**——把四个参数拼到 URL 后面直接打开即可。
>
> ✅ **【V1.2 已确认】** 2.2—2.8 业务接口为 **POST**（部分接口 GET 返回 405 "不支持GET方法请求"），参数用**表单编码**（见统一约定），完整根路径见上表。

```
GET https://{AUTH_ROOT}/login?username={}&key={}&appcode={}&secret={}
Resp: { "code": 200, "message": "操作成功",
        "data": { "access_token": "<JWT>", "expires_in": 3599 } }
```

**✅ 2026-09-29 实测结论**

| 项 | 实测结果 |
|---|---|
| **请求方式** | **GET + 查询串**（见上） |
| 证书 | `CN=*.scjgj.cq.gov.cn`，签发方 WoTrus（**商业 CA，非国密/非自签**），无需跳过校验 |
| 协议 | 1443 端口**仅支持 HTTPS**，`http://` 报 `HTTP/0.9 when not allowed` → 规范 `http://` 前缀确为笔误 |
| `appcode` | **已确认** = 平台编号 `821102379226763264` |
| `username` | **为统一社会信用代码**（非随机串），可与 2.2 的 `organizationCode` 复用 |
| `secret` 拼写 | 平台通知写作 `scret`；GET 方式下以规范 `secret` 为准（已验证可用） |
| **当前状态** | ✅ **登录成功，token 已获取**，`expires_in=3599` |

**token 结构（JWT，RS256）** —— 实测解码 payload：

```json
{
  "aud": ["openService", "authService"],
  "user_name": null,
  "scope": ["all"],
  "appcode": "821102379226763264",
  "orgid": "311715940563362",
  "client_id": "821102379226763264",
  "exp": 1790657707,
  "jti": "<每次登录唯一>"
}
```

| 字段 | 我方用途（规范未提及，实测稳定存在） |
|---|---|
| `appcode` / `client_id` | 校验"取到的 token 属于本账号"，防止多环境/多账号串用 |
| `orgid` | **平台组织机构号**，建议落 `company.org_id` 作为单位档案补充标识 |
| `scope: ["all"]` | 权限范围，初版按全权限处理 |
| `exp` | 过期时间戳（Unix 秒），与 `expires_in` 交叉校验 |
| `jti` | token 唯一标识，建议记入 `reg_token_log` 便于故障追溯 |

> **实现注意**：token 本身属敏感信息，落库须加密；**凭证在 URL 查询串中，因此 HTTP 访问日志、APM 埋点、异常堆栈必须过滤完整 URL**，否则凭证会经由日志系统泄露。

**实测发现的错误码与报文格式**（规范均未记载）：

| 码值 | 场景 | HTTP | 报文 |
|---|---|---|---|
| `200` | 登录成功 | 200 | `{"code":200,"message":"操作成功","data":{…}}`（**数字型**） |
| `10001` | username 缺失 | 200 | `{"code":10001,"message":":username 不能为空","data":null}` |
| `401` | 业务接口 token 缺失/无效 | **401** | `{"code":401,"message":"认证失败"}` |
| `500` | 以 POST 方式调用本接口 | 200 | `{"code":500,"message":"操作失败!","data":null}` |
| `404` | 业务接口路径不存在 | 404 | **Spring Boot 默认格式**：`{"timestamp":…,"status":404,"error":"Not Found","path":"/entity/queryID"}` |
| `415` | Content-Type 非 JSON | 415 | **Spring Boot 默认格式** |

> ⚠️ **两种错误报文格式并存**，HTTP 客户端须同时兼容，否则框架层错误（404/415）会被误判为未知异常。
> ⚠️ **401 使用 HTTP 状态码而非仅业务码**，适配层须将 HTTP 401 作为独立分支触发"清缓存重登 + 重试 1 次"。
> ⚠️ 平台使用 API 网关（响应头 `Server: sansec/3.20.3`），CORS 白名单含 `X-Auth-Key`/`X-Auth-Signature`/`X-Auth-Timestamp`/`x-auth-token`/`appkey`，**是否存在签名鉴权机制待平台确认**。

- 此接口 code 为**数字型**（实测确认），与 2.2—2.6 的字符串型不同 → 适配层统一 `String.valueOf(code).trim().equals("200")`
- **凭证已分配（2026-09-29）**，经环境变量 `REG_USERNAME`/`REG_KEY`/`REG_APPCODE`/`REG_SECRET` 注入，**禁止硬编码**

中控策略（平台提示：**有效期内请勿重复调用**）：Redis 缓存 TTL = `expires_in` − 60s，**被动获取、不提前刷新**；多实例用分布式锁防并发重复登录；收到 token 失效（HTTP 401）时清缓存重登并重试 1 次。
## B.2 获取主体ID（规范2.2）

```
POST https://{API_ROOT}/entity/queryID
Content-Type: application/x-www-form-urlencoded    // 🔴 表单，不是 JSON（V1.2 实测）
Body: organizationCode=<统一社会信用代码(必填)>&unitName=<单位名称>
Resp(2026-09-29 实测): {
  "code": "200", "message": "操作成功",
  "data": [{ "entityID": "311715940563360",
             "unitName": "重庆博威电梯有限公司",
             "organizationCode": "91500106MAABU3795M" }]
}
```
- ⚠️ **实测响应结构差异（V1.2）**：2.2 的业务数据在 **`data` 数组**中（规范示例把 unitName/organizationCode/entityID 写在顶层，与实测不符）——适配层按 `data[0].entityID` 解析，保留顶层字段三级回退
- ⚠️ 本方 `entityID=311715940563360` 与 JWT `orgid=311715940563362` **数值相近但不同**（两个 ID 体系），关联以 entityID 为准，两者均落库存档
- code=404 → 提示管理员核对单位名称与统一社会信用代码
- **【V1.1 更正】本接口是"通用主体查询"，调用两次**：
  - 对**维保单位**调用 → 落 `company.entity_id`
  - 对**每一家使用单位**调用 → 落 `use_unit.entity_id`，**这是 2.3 的必填入参 `useUnitEntityID` 的来源**

  依据：原文服务说明为「通过**单位**名称查询**单位**主体的ID」，且 URL 在 `entity/` 命名空间（与 2.3 同级），**未对单位类型作任何限制**。V1.0 仅在维保单位语境描述本接口，导致使用单位主体ID来源不明。
- 🔴 **【V2.16 实测更正（2026-10-04，以本条为准）】`organizationCode` 为被查单位自己的统一社会信用代码**，不是调用方（维保单位）的。三口径实测：我方代码+对方名称 → `data:[]`；对方代码+对方名称 → 命中 `entityID`；仅对方名称 → `10001 organizationCode 不能为空`。因此查询使用单位主体ID必须先在 `use_unit` 档案维护其信用代码（V13 迁移）；上方 V1.1 更正的"调用两次"结论不变，但对使用单位调用时传的是该使用单位自己的代码。

> **【V1.1】`useUnitEntityID` 大小写**
> 2.3 入参为 `useUnitEntityID`（**大写 ID**），2.7 返回为 `useUnitEntityId`（**小写 d**）。两接口写法不同，**序列化时勿混用**。

## B.4 维保人员管理（规范2.4）

```
POST https://{API_ROOT}/entity/updateWorkState
Content-Type: multipart/form-data（携带 certificateFile 时）
字段: {
  "workManName": "", "workManCertificate": "",
  "workStartDate": "yyyy-MM-dd", "workEndDate": "yyyy-MM-dd",
  "changState": 0, "workManPhone": "",
  "certificateFile": <PDF文件流>    // changState=0 时必填，PDF ≤20M
}
Resp: { "code": "200", "message": "操作成功" }
```

> **【V1.1 事实更正】2.4 不返回人员ID**
>
> V1.0 写"平台建立成功后返回/分配的人员ID需保存至 `employee.platform_id`"——**这是错误的**。原文 2.4 的返回值示例**只有** `{"code":"200","message":"操作成功"}`，**不含任何 ID 字段**。
>
> 而 2.6 的 `workMan1Id`/`workMan2Id` **必须是平台人员ID**。因此 platform_id 只能通过 **2.5 轮询查询**获得：
>
> ```
> POST /employees/{id}/platform-register
>   → 2.4 建立人员（certificateFile 必传）→ 仅 code/message，无 ID
>   → 人员状态置 PENDING_SYNC
>   → 后台按 5s/15s/60s 重试 2.5，最长等 5 分钟
>   → 按 workManCertificate 精确匹配取 id
>   → 写 employee.platform_id，状态转 ACTIVE
> ```
>
> **实现约束**：
> - 匹配键必须是 `workManCertificate`（证书编号，平台内唯一），**严禁用姓名匹配**（会重名）
> - 匹配不到或**匹配到多条**（证书号重复）→ 告警人工处理，**不自动取第一条**
> - `platform_id` 为空的人员**不可派工**（否则 2.6 必然失败），报 `1004`
> - 2.5 按 `workEndDate > 当前日期` 过滤，**合同到期人员会从平台列表消失**，此时本地保留 platform_id 但同样不可派工

> **【V1.1】2.4 无职位/角色字段**
>
> 原文入参仅 7 项，**无"维保经理"标识**；2.5 返回亦无角色字段。故 `workMenegerName`/`workMenegerPhone`（2.6 必填）**无法从平台获取**，只能是本系统维保单位档案上的**单位级角色**（纯文本），详见 B.6 与 01 §3.2.1。
>
> 2.6 备注要求维保经理与维保人员1、2手机号**不能重复** → **维保经理不能兼任本次作业的维保人员**。

## B.5 单位维保人员查询（规范2.5）

```
POST https://{API_ROOT}/entity/queryWorkList
Body: { "changState": 0, "workEndDate": "大于当前系统日期" }
Resp: { "code": "200", "message": "操作成功",
  [ { "id": "123456",              // 平台人员ID → employee.platform_id
      "workManName": "李四",
      "workManCertificate": "...",
      "workStartDate": "2021-03-01", "workEndDate": "2025-02-28",
      "workStat": "normal",        // normal=正常
      "workManPhone": "136xxxx" } ]
}
```

> **【V1.1 重要】原文示例是非标准 JSON，必须三级回退解析**
>
> 上面这段是**从 V1.5 原文逐字提取的真实示例**（由核对）：

> ```json
> {
>   "code":"200",
>   "message":"操作成功"
>   [ { "id":"123456", ... }, ... ]
> }
> ```
>
> **数组与 `code`/`message` 平级并列，这在 JSON 规范中是非法的**（JSON 对象内不允许无名数组成员）。这是平台文档的书写错误，但**平台实现可能确实是这种形态**。
>
> V1.0 只写"实现时按此结构解析"，未给出解析策略，开发无从下手。V1.1 明确**三级回退 + 失败告警**：

| 优先级 | 解析路径 |
|---|---|
| 1 | `data` 为数组 → 取 `data` |
| 2 | 根级为数组 → 取根级数组 |
| 3 | `data` 为对象且含列表字段（`list`/`rows`/`records`/`result`）→ 取该字段 |
| 4 | 以上皆失败 → **解析失败：记录原始报文 + 告警，返回错误而非空列表** |

> **⚠️ 致命陷阱：解析失败严禁当作"空列表"处理**
>
> 若把解析失败误判为空列表，后果是：`platform_id` 全量同步"成功"但一条没同步 → 所有人员 `platform_id` 为空 → **全部不可派工** → 整个系统停摆，且现象隐蔽（接口返回 200、日志无异常）。V1.1 强制：解析失败抛 `REG_PARSE_ERROR`，写入告警并在 `GET /reg/sync-status` 暴露。

仅 `workStat=normal` **且本地 `platform_id` 非空** 的人员可分配工单；定期同步比对本地档案。

> **全文未出现"幂等""去重""唯一"任何表述。** 且 2.6 返回值**只有 `code`/`message`，不返回平台侧记录ID**，规范也未定义重复提交时的返回码。
>
> | 风险 | 后果 |
> |---|---|
> | 平台**不幂等** | 自动重试将在**监管平台产生多条重复维保记录**。在监管场景中，虚假维保记录的后果**远重于**上报失败 |
> | 平台**幂等** | 现有重试与去重策略成立 |
>
> **实现（联调确认前）**：`reg.retry.auto = false` —— 上报失败立即置 `FAILED_MAX`（待人工处理），**绝不自动重试**。仅 `POST /records/{originalRecordId}/manual-retry` 可人工重传。
>
> **联调验证方法（必做）**：用**专用测试电梯编码**，向 2.6 连续提交 **3 次相同的 `originalRecordId`**，核对平台侧记录数是否为 1。**严禁用生产电梯验证。** 确认幂等后方可将开关改为 `true`，恢复 30s/2min/10min 自动重试。

# A.8 后端实现映射（V1.6 新增）

> 本节记录 `backend/`（Spring Boot 3.3.4）对 A.0.1 契约的实现形态，供前后端联调对照。
> 路径与方法与 A.0.1 完全一致（无前缀），统一响应 `{ code, message, data }`，业务码见 A.0.1 码表。

## 实现要点

1. **鉴权**：除 `/auth/login`、`/auth/wx-login`、`/auth/bind-*`、`/auth/logout`、`/unit/records/*/sign-view`、`/unit/records/*/confirm-by-token`、`/files/upload`、`/files/{id}`、`/location/reverse`、`/health`、`/api/count` 外，均要求 `Authorization: Bearer <JWT>`（自建 JWT，非平台 token）。登录态由云托管免鉴权 `X-WX-OPENID` 绑定账号后签发。
2. **幂等**：全部写接口要求 `X-Idempotency-Key`（`utils/request.js` 已自动携带）；同 key 重放返回首次响应。
3. **派单**：定时任务每日 09:00 扫描"到期前 24h 内"电梯一次性派单（计划时间=到期日 09:00；同项目同日到期一次性全部派单，`scripts/verify-dispatch.js` 验收口径）+ 列表/汇总/扫码识单触达时即时补派；保养类型按时间自动升级（OY/SM/TM/HM）；派单同时写消息中心。
4. **检查项**：工单 checklist 按品种附件（A—D）与频次链累加式生成（257 行模板随包内置 `checklist-template.json`）；TSG 注 A-1/A-2 校验（NA 必填跳过原因、关键项照片留证）与签退 30 分钟时长下限在服务端强制。

### A.9.0 批量绑定维保人员与电梯（V2.7 契约，V2.10 实现落地，docs/09 V3.2）

> 自动派单的数据前提：自动派单引擎（每日 09:00 定时扫描 + 触达即时补派）按电梯绑定的 维保人员1（主）/维保人员2（配合）派工；**未绑定人员的电梯不进自动派单**。本接口用于多台电梯一次绑定，单台改绑仍走 `PUT /elevators/{id}` 字段级更新。**V2.10 已实现（V8 收敛）：逐台校验 1004 platform_id / 1002 手机互斥 / 1007 证件有效期与主配同人 / 电梯停用（INACTIVE 拒绝），返回 `{success[], failed[]}` 逐台明细。**

#### POST /elevators/batch-assign-workers

| 项 | 说明 |
|---|---|
| 鉴权 | JWT，管理端角色（ADMIN+ 写） |
| 幂等 | 要求 `X-Idempotency-Key`（批量操作防重放） |
| 校验 | **逐台执行，单台失败不阻塞其余成功台** |

```json
// 请求
{
  "elevatorIds": [1001, 1002, 1003],   // 目标电梯档案 ID 数组（非空，≤200）
  "principalId": 1001,                 // 维保人员1（主）employee.id，必填
  "assistantId": 1002                  // 维保人员2（配合）employee.id，可选
}
// 响应 data（成功 + 失败逐台明细）
{
  "success": [
    { "elevatorId": 1001, "principalId": 1001, "assistantId": 1002 }
  ],
  "failed": [
    { "elevatorId": 1003, "code": 1004, "message": "人员 platform_id 未同步，不可派工" }
  ]
}
```

**逐台校验（与单台指派同口径，docs/01 §3.2.4）**：

| 码 | 场景 |
|---|---|
| 1004 | 人员 `platform_id` 未同步（不可派工） |
| 1002 | 手机号互斥冲突（principal/assistant 与电梯相关角色冲突，`conflicts[]` 具体到角色对） |
| 1007 | 配置冲突禁止排班（证件有效期早于计划日 / 主配合互斥且均 ≠ 维保经理 / 一梯一单） |
| 404 | 电梯或人员档案不存在 |
| 422 | 电梯已停用（`status=INACTIVE`）；`elevatorIds` 为空或超限；`principalId` 缺失 |

**效果**：写入电梯档案维保人员分配字段（维保人员1/2，字段名以 A.0.1/后端实现为准）；绑定后自下一次 09:00 定时扫描（或触达补派）起纳入自动派单；返回失败明细供管理端逐台纠偏（如先完成 2.4 人员登记 → 2.5 回填 platform_id 后再绑定）。

**互斥口径**（docs/01 §3.2.4）：参与互斥的仅五个角色——使用单位负责人、使用单位安全管理员、维保经理、维保人员1、维保人员2；emergencyPhone/
ecorderPhone 不参与。同一手机号跨 ≥2 个不同角色判定冲突；同角色（如两单位同一负责人）不算冲突。
