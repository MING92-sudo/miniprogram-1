# A. 系统内部 API

## A.0 通用约定

| 项目 | 约定 |
|---|---|
| Base URL | `https://api.{domain}/v1` |
| 鉴权 | `Authorization: Bearer <JWT>`（登录接口除外） |
| 请求/响应格式 | `application/json; charset=utf-8` |
| 时间格式 | `yyyy-MM-dd HH:mm:ss`，时区 GMT+8 |
| 统一响应 | `{"code": 0, "message": "success", "data": {...}}` |
| 分页 | 请求 `page`(从1起) / `size`(默认20)，响应 `data.list` + `data.total` |
| 幂等 | 所有写接口支持 `X-Idempotency-Key` 头（离线补传场景必传） |
| 请求超时 | 小程序端 15s；管理端 30s；文件上传 120s |

## A.0.2 平台写链路（V1.8 新增，后端已实现，docs/07 实测口径）

> 以下三条路由为 P3 后端沉淀的内部端点（JWT 鉴权）。转发层行为：POST 表单 + Bearer 平台 token、
> 401 清缓存重登重试 1 次、code 兼容数字/字符串 "200"（复用 `PlatformClient`）。
> `REG_RETRY_AUTO` 保持 `false`：2.6 失败不自动重试，仅人工触发（AGENTS §2.3）。

| 接口 | 说明 |
|---|---|
| `POST /platform/records/{id}/reupload` | **手动重报 2.6**：仅 `reportStatus=FAILED` 的维保记录（其余返回 `1003`）。`{id}` 为维保记录 ID；报文直接取签退冻结快照 `reportPayload`（20 字段不重新组装）。响应 `{ok, id, reportStatus}`。前端入口：工单详情页"手动重报平台"按钮（仅 FAILED 显示） |
| `POST /platform/register/service` | **2.3 建立维保服务关系**（multipart）：表单字段 `useUnitName`（实测参数名，docs/07）、`useUnitEntityID`、`changState=0`、`serviceStartDate`、`serviceEndDate` + 文件 `contractFile`。一次性登记动作，不做前端页面，经端点/脚本触发 |
| `POST /platform/register/worker` | **2.4 登记维保人员**（multipart）：表单字段 `workManName`、`workManCertificate`、`workStartDate`、`workEndDate`、`workManPhone`、`changState=0` + 文件 `certificateFile` |
| `POST /platform/query/elevator` | **2.7 单梯查询（V1.10 追加）**：`{deviceCode 或 factoryNumber 或 registrationCode}` 至少一项（实测平台不支持按 elevatorCode 查询，docs/06 #8 结论已修正）；凭证未配置返回 `{found:false, reason}`，未查到返回 `{found:false, reason:"平台未查询到该电梯"}`，命中返回 `{found:true, elevator:<平台原始字段>}`。前端入口：管理端 新建/编辑电梯 "平台查询(2.7)" 按钮，回填 电梯编号/设备代码/应急电话/安全管理员/使用单位主体 |

**上报状态口径（V1.8）**：签退后自动转发 2.6——成功 `REPORTED`、失败 `FAILED`（落 `reg_upload_log`，action=UPLOAD）、平台凭证未配置 `SUBMITTED`（待上报，本地/演示流程不受影响）。台账与记录视图新增归一字段 `uploadStatus`：`REPORTED→SUCCESS`、`FAILED→FAILED`、其余 `PENDING`。

> 平台实际为 **GET 请求、参数拼在 URL 查询串中**：

> GET https://{AUTH_ROOT}/login?username={}&key={}&appcode={}&secret={}

>
> **2026-09-29 实测对照**：
>
> | 调用方式 | 实际返回 |
> |---|---|
> | **GET + 查询串** | ✅ `{"code":200,"message":"操作成功","data":{"access_token":"…","expires_in":3599}}` |

**实测发现的错误码与报文格式**（规范均未记载）：

| 码值 | 场景 | HTTP | 报文 |
|---|---|---|---|
| `200` | 登录成功 | 200 | `{"code":200,"message":"操作成功","data":{…}}`（**数字型**） |
| `10001` | username 缺失 | 200 | `{"code":10001,"message":":username 不能为空","data":null}` |
| `401` | 业务接口 token 缺失/无效 | **401** | `{"code":401,"message":"认证失败"}` |

| `404` | 业务接口路径不存在 | 404 | **Spring Boot 默认格式**：`{"timestamp":…,"status":404,"error":"Not Found","path":"/entity/queryID"}` |
| `415` | Content-Type 非 JSON | 415 | **Spring Boot 默认格式** |

> ⚠️ **两种错误报文格式并存**，HTTP 客户端须同时兼容，否则框架层错误（404/415）会被误判为未知异常。

> V1.0 写"平台建立成功后返回/分配的人员ID需保存至 `employee.platform_id`"——**这是错误的**。原文 2.4 的返回值示例**只有** `{"code":"200","message":"操作成功"}`，**不含任何 ID 字段**。
>
> 而 2.6 的 `workMan1Id`/`workMan2Id` **必须是平台人员ID**。因此 platform_id 只能通过 **2.5 轮询查询**获得：
>
> ```
> POST /employees/{id}/platform-register
>   → 2.4 建立人员（certificateFile 必传）→ 仅 code/message，无 ID
>   → 人员状态置 PENDING_SYNC
>   → 后台按 5s/15s/60s 重试 2.5，最长等 5 分钟
>   → 按 workManCertificate 精确匹配取 id
>   → 写 employee.platform_id，状态转 ACTIVE
> ```
>
> **实现约束**：
> - 匹配键必须是 `workManCertificate`（证书编号，平台内唯一），**严禁用姓名匹配**（会重名）
> - 匹配不到或**匹配到多条**（证书号重复）→ 告警人工处理，**不自动取第一条**
> - `platform_id` 为空的人员**不可派工**（否则 2.6 必然失败），报 `1004`
> - 2.5 按 `workEndDate > 当前日期` 过滤，**合同到期人员会从平台列表消失**，此时本地保留 platform_id 但同样不可派工

> **【V1.1】2.4 无职位/角色字段**
>
> 原文入参仅 7 项，**无"维保经理"标识**；2.5 返回亦无角色字段。故 `workMenegerName`/`workMenegerPhone`（2.6 必填）**无法从平台获取**，只能是本系统维保单位档案上的**单位级角色**（纯文本），详见 B.6 与 01 §3.2.1。
>
> 2.6 备注要求维保经理与维保人员1、2手机号**不能重复** → **维保经理不能兼任本次作业的维保人员**。

      "workStat": "normal",        // normal=正常
      "workManPhone": "136xxxx" } ]

```

> **【V1.1 重要】原文示例是非标准 JSON，必须三级回退解析**
>
> 上面这段是**从 V1.5 原文逐字提取的真实示例**（由核对）：

> ```json
> {
>   "code":"200",
>   "message":"操作成功"
>   [ { "id":"123456", ... }, ... ]
> }
> ```
>
> **数组与 `code`/`message` 平级并列，这在 JSON 规范中是非法的**（JSON 对象内不允许无名数组成员）。这是平台文档的书写错误，但**平台实现可能确实是这种形态**。
>
> V1.0 只写"实现时按此结构解析"，未给出解析策略，开发无从下手。V1.1 明确**三级回退 + 失败告警**：

| 优先级 | 解析路径 |
|---|---|
| 1 | `data` 为数组 → 取 `data` |
| 2 | 根级为数组 → 取根级数组 |
| 3 | `data` 为对象且含列表字段（`list`/`rows`/`records`/`result`）→ 取该字段 |
| 4 | 以上皆失败 → **解析失败：记录原始报文 + 告警，返回错误而非空列表** |

> **⚠️ 致命陷阱：解析失败严禁当作"空列表"处理**
>
> 若把解析失败误判为空列表，后果是：`platform_id` 全量同步"成功"但一条没同步 → 所有人员 `platform_id` 为空 → **全部不可派工** → 整个系统停摆，且现象隐蔽（接口返回 200、日志无异常）。V1.1 强制：解析失败抛 `REG_PARSE_ERROR`，写入告警并在 `GET /reg/sync-status` 暴露。

仅 `workStat=normal` **且本地 `platform_id` 非空** 的人员可分配工单；定期同步比对本地档案。

# A.8 后端实现映射（V1.6 新增）

> 本节记录 `backend/`（Spring Boot 3.3.4）对 A.0.1 契约的实现形态，供前后端联调对照。
> 路径与方法与 A.0.1 完全一致（无前缀），统一响应 `{ code, message, data }`，业务码见 A.0.1 码表。

## 实现要点

1. **鉴权**：除 `/auth/login`、`/auth/wx-login`、`/auth/bind-*`、`/auth/logout`、`/unit/records/*/sign-view`、`/unit/records/*/confirm-by-token`、`/files/upload`、`/files/{id}`、`/location/reverse`、`/health`、`/api/count` 外，均要求 `Authorization: Bearer <JWT>`（自建 JWT，非平台 token）。登录态由云托管免鉴权 `X-WX-OPENID` 绑定账号后签发。
2. **幂等**：全部写接口要求 `X-Idempotency-Key`（`utils/request.js` 已自动携带）；同 key 重放返回首次响应。
3. **派单**：定时任务每日 09:00 + 列表/汇总/扫码识单触达时即时补派；到期前一天自动派单，保养类型按时间自动升级（OY/SM/TM/HM）；派单同时写消息中心。
4. **检查项**：工单 checklist 按品种附件（A—D）与频次链累加式生成（257 行模板随包内置 `checklist-template.json`）；TSG 注 A-1/A-2 校验（NA 必填跳过原因、关键项照片留证）与签退 30 分钟时长下限在服务端强制。
5. **签退**：冻结维保记录快照（检查项明细/照片/隐患码，无隐患填 S0）+ 2.6 报文 20 字段快照落库（`reportPayload`，P3 上报直接取用，不重新组装）；生成 `shareToken` 支撑使用单位签字链接。
6. **文件**：`/files/upload` 代理上传腾讯云 COS（`COS_*` 环境变量）；未配置时回退本地磁盘（仅开发）。
7. **平台同步**：`POST /platform/sync` 触发 2.2（维保单位 + 各使用单位 entityID）、2.7（按 elevatorCode/出厂编号/注册代码/设备代码回填，实测未脱敏电话直接落库）、2.5 人员 platform_id 同步（按证书号匹配）落库；2.8 存量推送受 `REG_LEGACY_UPLOAD_ENABLED` 开关控制（默认关）；`REG_RETRY_AUTO` 保持 false。
8. **平台写链路（V1.8/P3）**：签退成功后自动转发 2.6（报文取 `reportPayload` 冻结快照，失败不自动重试）；`POST /platform/records/{id}/reupload` 手动重报（仅 FAILED）；2.3/2.4 登记端点 multipart 转发（详见 A.0.2）；每次转发落 `reg_upload_log`（`request_digest` 脱敏，手机号打码、不含 token）。
