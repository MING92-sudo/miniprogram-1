【另外有几个问题想一并确认】
这些都是我们开发过程中发现的规范没写清楚的地方，想请帮忙确认一下，免得我们做错了：

一、上报数据的重复提交（这个比较要紧）
规范说 originalRecordId 是"维保作业系统原始维保记录ID"，但没说它是不是幂等键。想确认：
· 相同的 originalRecordId 重复提交，平台这边会生成几条记录？
· 如果不幂等，有没有办法按这个 ID 查重或者撤销？
· 这个 ID 有格式要求吗？必须纯数字吗？最长多少位？
· 我们现在用的是 19 位雪花算法 ID，不知道符不符合要求

我们不敢贸然试，因为如果平台不幂等，每重试一次监管平台就会多一条维保记录，万一删不掉就很麻烦。所以暂时把自动重试关掉了，全部转人工，但这样效率太低了。

二、手机号不能重复的边界
2.6 的备注说"使用单位单位负责人、使用单位安全管理员、维保经理、维保人员1、维保人员2手机号码不能重复"。想确认几点：
· 这个"不能重复"是指同一条记录里这五个互不相同吗？
· 使用单位的负责人和安全管理员能不能是同一个人？（我们遇到好几个小物业就是这样）
· 维保经理能不能同时兼任这次的作业人员？
· workMan2Id 标注必填，如果是单人作业该怎么填？空着、填一样的、还是填 0？
· emergencyPhone 和 recorderPhone 这两个不在备注里，应该不受这个限制吧？

三、隐患码 S4
3.2 的码表里 S3 出现了两次，没有 S4。第二条"使用应当予以报废或者经检验判定为不合格的特种设备"这个，是 S3 还是 S4？麻烦给一份准确的码表。

另外想确认下 problemCode 是不是必须是数组格式，比如 ["S0"]？还有没发现隐患填 S0 的时候，如果同时有其他隐患，还需不需要带上 S0？

四、elevatorCode 怎么拿
我们理解是：调 2.7 查询要提供出厂编号、注册代码、设备代码其中之一，查完返回 elevatorCode；然后 2.6 上报必须要 elevatorCode。

问题是：新装的电梯如果这三个编码我们手上都没有，就没法调 2.7 拿 elevatorCode，也就永远报不上去。这个流程是不是哪里理解错了？新电梯的 elevatorCode 从哪条途径获取？

另外 2.7 的服务说明里写了可以按"电梯编码"查询，但参数表里没有这个参数，到底支不支持？

五、维保记录传上去之后能改吗
规范里 8 个接口都是单向提交的，没有查询、修改、删除的接口。想确认：
· 有没有查询维保记录的接口？没有的话我们对账很困难
· 传错了能不能改或者撤销？
· 2.6 必填的 nextMaintenanceDate，如果传完之后又延期了，平台这边能同步吗？
· 使用单位签字确认的结果，需要传到平台吗？还是我们自己存就行？

六、几个小的
· 有没有测试环境？还是只能拿生产环境联调（那样我们怕把测试数据写进监管库）
· 完整错误码表能给一份吗？现在返回失败只有一句中文"操作失败!"，我们没法判断哪些能重试、哪些不能
· 有没有调用频率限制？
· 生产部署需要配 IP 白名单吗？

问题有点多，您可以分几次回复，不着急，我们自己也在往前推其他模块。主要是登录那个问题比较急，麻烦优先帮忙看看 🙏

## 为什么"浏览器试试"这个建议帮上了忙（已验证）

这条建议**是对的**，而且是突破口。

登录接口实际是 **GET + 参数拼在 URL 上**，不是规范里写的 POST + 请求体。
所以浏览器地址栏直接打开就能测——**平台当时的建议是字面意思，不是敷衍**。

**教训（对我方的）**：第一次试 GET 时，URL 里的 `&` 被 PowerShell 当成命令分隔符，URL 被截断导致请求失败，我当时误判成"路径问题"就放过了，没有重试。
**教训：排除法要穷尽**——每种"可能的原因"都应该有一个能证实或证伪的测试，而不是试一次就下结论。

## 404 的说服力在哪

关键在于**状态码的变化**，这个细节能证明问题不在我方：

| 场景 | 返回 | 说明 |
|---|---|---|
| 不带 token | **401** 认证失败 | token 校验在这一步 |
| 带上有效 token | **404** Not Found | **token 已通过校验**，问题在路由层 |

加上 `/actuator/health` 返回 `{"status":"UP"}`（服务健康）+ GET/POST 均为 404（不是 405）→ **可以比较有把握地说：不是凭证问题、不是网络问题、不是方法问题，而是路由/地址问题。**

## 404 报文的格式差异（很关键，容易被忽略）

平台在两种情况下返回了**不同格式**的 404：

| 场景 | 报文格式 | 含义 |
|---|---|---|
| 打 `/api/wlw/...`（错误前缀） | `{"timestamp":…,"status":404,"error":"Not Found","path":"/entity/queryID"}` | **Spring Boot 默认格式** → 请求可能没进业务应用 |
| 打 `/api/...`（正确前缀） | `{"code":404,"message":"404 NOT_FOUND","data":null}` | **平台业务格式** → **已穿过网关到达应用层**，被业务代码判定路由不存在 |

**第二种格式是更有力的证据**——说明请求确实到了应用，是应用自己说"没这个路由"，而不是被网关挡在外面。跟平台说清楚这个区别，能避免他们把问题推给"网关配置"。

## DNS 失效这件事怎么说

不要只说"解析不了"，要说清**排除了我方网络**：

> "我用系统 DNS、阿里 DNS、腾讯 DNS、Google DNS 都试了，全都解析失败，报 DNS 域名不存在。但用之前的 IP 直连，服务是正常的，能登录能拿 token。"

这样说的好处：
1. 表明你查得足够彻底，不是随便一试
2. "IP 直连正常"这句直接证明**后端在线、不是服务挂了**
3. 隐含地把问题定位到 DNS/运维侧，对方更容易往对的方向推

⚠️ 但**不要说成抱怨**。用"想确认下是不是在调整"这种中性问法，因为对方很可能真的在部署或迁移。
