# 三、★踩坑记录（请勿重复）★

## 坑 1：按规范用 POST 调登录接口 ❌

**错误做法**（照规范 V1.5 原文）：
```bash
curl -X POST "…/api/authService/login" -H "Content-Type: application/json" \
  -d '{"username":"…","key":"…","appcode":"…","secret":"…"}'
```
**结果**：`{"code":500,"message":"操作失败!"}`

**正确做法**：
```bash
curl "…/api/authService/login?username=…&key=…&appcode=…&secret=…"
```
**结果**：`{"code":200,…}`

> **为什么会踩**：规范 2.1 明确写 `Body: {...}`，且 1.1 写"统一采用POST请求类型"。
> **更坑的是**：平台对"调用方式错"和"凭证错"返回**完全相同的 500 文案**，导致排查方向被误导到账号/凭证/网络上，浪费大量时间。

## 坑 2：PowerShell 中 `&` 被当作命令分隔符 ❌

**错误做法**：
```powershell
curl "https://…/login?username=x&key=y&appcode=z&secret=w"
```
**结果**：URL 被 PowerShell 截断 → 请求失败

**正确做法**（用变量拼接）：
```powershell
$q = "username=" + [uri]::EscapeDataString($U) + "&key=" + [uri]::EscapeDataString($K) + …
curl "https://…/login?$q"
```

> **为什么会踩**：PowerShell 需要 `&` 转义或用变量拼接。
> **更坑的是**：当时误判成"路径不对"就放过了，**没有回头重试 GET**——如果当时重试，登录问题当场就解决了。
> **教训**：每提出一个"可能原因"，必须有对应的**证实/证伪测试**；一个假设只能试一次不算排除。

## 坑 3：PowerShell 中 `$Host` 是只读内置变量 ❌

```powershell
$Host = "tszb.scjgj.cq.gov.cn"   # ❌ 报错：Cannot overwrite variable Host
```
**正确**：用其他变量名，如 `$hn` / `$hostName`。

## 坑 4：用 `-o NUL -w "%{http_code}"` 判断 404 会误判 ❌

PowerShell 中 curl 输出为空数组时，`$r -ne "404"` 判断恒为真，**导致"全部路径都非404"的假阳性**。

**正确**：
```powershell
$r = (& curl.exe -sS -k -m 10 … -w "CODE%{http_code}" 2>&1) -join ''
if ($r -match 'CODE(\d{3})$') { $code = $matches[1] }
```
或直接**输出完整响应报文**人工判读（本文档所有测试均采用此方式）。

## 坑 5：PowerShell 管道传 curl 输出给 `Write-Output` 会报错 ❌

```powershell
(& curl.exe …) | Write-Output "   $_"   # ❌ 管道对象无法绑定
```
**正确**：先 `-join ''` 合并为字符串再输出。

# 四、★响应报文速查（按格式判读）★

| 报文 | 格式 | 含义 | 该怎么办 |
|---|---|---|---|
| `{"code":200,"message":"操作成功","data":{…}}` | 业务 | ✅ 成功 | — |
| `{"code":10001,"message":":username 不能为空"}` | 业务 | 参数校验失败 | 检查必填项（注意 message 前有个多余的 `:`） |
| `{"code":401,"message":"认证失败"}` + **HTTP 401** | 业务 | **网关拦截**：token 缺失/无效 | 查 token 是否获取、是否过期、是否带 `Bearer ` 前缀 |
| `{"timestamp":…,"status":404,"error":"Not Found","path":"/entity/queryID"}` | **框架(Spring)** | **已进入应用，但路由未注册** | 找平台确认接口是否上线 |
| `{"code":404,"message":"404 NOT_FOUND","data":null}` | 业务 | 网关/业务层未匹配到路由 | 检查路径前缀 |
| `{"code":500,"message":"操作失败!"}` | 业务 | 业务处理失败 | ⚠️ **文案不区分原因**，不可据此判断 |
| `{"timestamp":…,"status":415,"error":"Unsupported Media Type"}` | 框架 | Content-Type 不支持 | 改用 `application/json` |
| `<html>…404 Not Found…<center>nginx` | nginx | **未经过 `/api/` 网关** | 路径缺少 `/api` 前缀 |
| `{"status":"UP"}` | actuator | 服务健康 | — |

# 五、★诊断决策树★

```
调用平台接口失败
   │
   ├─ 返回 nginx HTML 404？
   │     → 路径缺少 /api 前缀，改为 /api/... 或 /api/wlw/...
   │
   ├─ 返回 {"code":401}（HTTP 401）？
   │     → 网关拦截。检查：①是否已调登录拿 token
   │                       ②是否带 "Authorization: Bearer " 前缀
   │                       ③token 是否过期（3599秒）
   │                       ④登录是否用了 GET（POST 会 500）
   │
   ├─ 返回 {"code":500,"message":"操作失败!"}？
   │     → ⚠️ 该文案不区分原因。逐一排查：
   │       ① 登录接口：是否误用 POST（应 GET+查询串）
   │       ② 业务接口：路径/参数/权限
   │
   ├─ 返回 Spring 格式 {"timestamp":…,"status":404,"path":"…"}？
   │     → ✅ 网络正常 ✅ 鉴权通过 ✅ 已进入应用层
   │     → 但应用未注册该路由 → 【找平台确认接口是否上线】
   │
   ├─ 返回 {"code":404,"message":"404 NOT_FOUND"}？
   │     → 网关层未匹配到路由 → 检查路径前缀是否 /api/wlw/
   │
   └─ 连接失败？
         ├─ curl: (6) Could not resolve host
         │     → DNS 问题（2026-09-29 曾出现：4个DNS均无法解析，IP直连正常）
         └─ curl: (28) Connection timed out
               → 端口不通/防火墙
```

# 六、★已排除的原因（不要再浪费时间重查）★

针对「业务接口 404」，以下均已**实测排除**：

| 排除项 | 验证方式与证据 |
|---|---|
| ❌ **token 无效** | 无 token 返回 **401**，带 token 变 **404** → token 已被接受 |
| ❌ **服务未启动** | `/api/actuator/health` 与 `/api/wlw/actuator/health` 均 `{"status":"UP"}` |
| ❌ **调用方式错误** | 1.1 四项要求（HTTPS/POST/JSON/Restful）逐项验证均正常 |
| ❌ **Header 缺失** | 补齐 `Content-Type` + `Authorization` + `Accept` 后 404 类型从网关 401 变为应用层 404 |
| ❌ **路径前缀错误** | 5 种前缀（`/api/wlw` `/api` `/wlw` `/` `/api/v1` 等）× 7 条规范路径 = **35 组合**全 404 |
| ❌ **请求方法错误** | GET 与 POST 均为 404（方法问题应返回 405） |
| ❌ **路由名不对** | 规范中 7 个相对路径逐个测试，均未命中 |
| ❌ **网关没配路由** | 网关确实有 `wlw` 路由（health=UP），否则请求不会到达应用层 |

> **唯一剩下的可能**：**业务 Controller 未注册到路由** → 平台侧业务接口尚未上线。

| `/api/{appcode}/entity/queryID`、`/api/open/...`、`/api/service/...`、`/api/elevator/...` | 同上 |

## 10.3 关键对照实验（区分 404 来源）

| 探测 | 返回 | 判定 |
|---|---|---|
| `/api/entity/queryID` 无 token | `{"code":401,"message":"认证失败"}` | 网关鉴权在前，路径本身能过鉴权层 |
| `/api/entity/queryID` 带真实参数 | 统一格式 404 | 与下一行完全一致 |
| `/api/definitely-not-exist-xyz123`（明显不存在的路径） | **完全相同**的统一格式 404 | `/api/entity/queryID` 未进入任何业务 Controller，是**网关兜底 404** |
| `/api/wlw/definitely-not-exist-xyz123` | Spring 默认错误格式（timestamp/error/path） | `/api/wlw/**` 才真正转发到 wlw 应用 |

## 10.4 结论

1. **平台给的根路径 `/api/` 实测不成立**：该前缀下所有规范路径均返回与随机不存在路径完全相同的网关兜底 404，业务请求未到达任何应用层 Controller。
2. 真正被网关转发到业务应用的路径仍是 `/api/wlw/**`（其下任何路径都会返回 Spring 应用层 404，证明流量已进 wlw 服务）。
3. **业务 Controller 2.2—2.8 未上线的结论在第三轮后仍然成立**，且新增证据：平台口头给出的根路径与网关实际路由配置不符，说明平台侧网关路由/文档/部署三者未对齐（更新到 06 清单问题 13 的跟进材料）。
4. **建议向平台索要一个可复制的完整调用示例**（任一只读接口的 curl 全文，含 Host、路径、Header、Body），以平台实际抓包/自测通过的请求为准，而非口头根路径描述。

  }

$q = "username=$env:REG_USERNAME" +

$r = (& curl.exe -sS -k -m 20 "$env:REG_AUTH_LOGIN_URL`?$q" 2>&1) -join '' | ConvertFrom-Json

## 12.4 2.3 写入实测（2026-09-30，已获用户确认，对象：星禹佳 311753437688189）
