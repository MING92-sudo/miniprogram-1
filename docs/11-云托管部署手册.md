# 云托管部署手册（微信云托管）

> 目标形态：微信云托管承载「后端服务（容器）」+「管理端 SPA（静态托管）」+「云 MySQL」，三者在同一自定义域名下按路径路由实现同域（`/api/* → 后端`，`/* → 静态托管`）。
> 小程序端代码另走微信开发者工具上传（与后端无关）。
> 创建：2026-10-01。部署凭证（REG_*、JWT_SECRET、DB 密码）只允许进云托管控制台环境变量，严禁写入仓库（AGENTS §2）。

## 0. 新镜像首次发布探针超时（2026-11-12 实测，必读）

**现象**：源码构建成功、镜像推送成功，但部署状态 `deploy_failed`，进程日志只有一行

```
check_eks_virtual_service : process, 部署版本失败：Liveness probe failed: dial tcp <pod-ip>:80: connect: connection refused
```

拉「启动日志」能看到 JVM 比 Pod 创建**晚约 180 秒**才启动（镜像从 CCR 拉取慢），而探针窗口只有
`InitialDelaySeconds=2` + 约 30 次 × 5s ≈ **150 秒**——应用还没监听端口就被判死。

**已验证不可行**（2026-11-12/13 实测）：

- `updateConfig` 只传 `InitialDelaySeconds`（不碰 Port，避免触发自动重发布）：返回成功、任务号下发，但 `detail` 里该字段**恒为 2**；
- `deploy` 时通过 `ServerConfig` 下发 `InitialDelaySeconds:240`：同样被忽略，仍为 2；
- **新建服务**同样默认 2 秒（在另一环境新建同名服务验证），即创建期也没有该参数入口；
- 每次改配置会自动用**上一个成功镜像**重发布，容易与新镜像发布互相打断（曾因此连续失败两次）。

**已做的镜像侧优化**（commit `c9787fc`）：`pom.xml` 开启 Spring Boot `layers`，根 `Dockerfile` 改为分层 COPY（dependencies 48MB / application 3.4MB）并用 `JarLauncher` 启动。效果是**一旦有一次发布成功**，之后每次只变更 3MB 业务层，拉取可落进探针窗口；但**首次**分层发布仍需拉取 48MB 依赖层，实测仍会超窗口。

**结论**：在探针初始延迟固定为 2 秒、控制台无健康检查入口的前提下，新镜像首发无法通过重试稳定解决，需要平台侧调整（工单）或改用不受该探针约束的部署形态。

**判定方法**：`detail` 的 `latestDeploy.Status` 与「启动日志」里 `Starting MaintenanceBackendApplication` 的时间戳对比 Pod 创建时间；差距 > 150s 即本问题，与代码无关。

## 1. 部署拓扑

```
小程序(微信端) ──► https://<自定义域名>/api/* ──► 云托管「后端服务」(Spring Boot :80)
管理端SPA ──────► https://<自定义域名>/* ────────► 云托管「静态托管」(admin/dist)
                            ▲
                      云 MySQL(内网，Flyway 自动建表)
```

## 3. 部署步骤

### 步骤 A：数据库（Flyway 自动建表，无需手工 SQL）

1. 云托管控制台创建「MySQL」实例，库名 `maintenance`，字符集 `utf8mb4`。
2. 记录内网地址（云托管容器内可直连）供步骤 B 环境变量使用。
3. 表结构由后端启动时 Flyway 自动执行 `V1–V12` 迁移 + 演示种子（`SEED_DEMO_DATA=true` 首启后改 `false`）。
   （V6 急修单整改、V7 班组数据权限、V8 电梯停用状态、V9 签到定位阈值与坐标来源、V10 双人动态码与配合人员签到留痕、V11 记录预览上下文、V12 系统参数表 `sys_param`（签到阈值品种级/全局级）；均已按云开发 MySQL 5.7 兼容写法。）
   > 已裁模块端点删除（docs/04 V2.15）**不伴随删表迁移**：`location_appeal`/`alert_rule`/`alert_record`/`op_log` 等表保留，满足留存要求，云端无需手工处理。

> ⚠️ **删库后必须重建**（2026-10-01 云托管首部署踩坑）：后端 JDBC URL 已带 `createDatabaseIfNotExist=true`，目标库不存在时由驱动自动建库（账号需对该库有 CREATE 权限）；但**若手动删库排障**，务必重建同名空库，否则 Hikari 连接失败、容器启动失败（liveness probe 报 `connection refused`）。重建：`CREATE DATABASE IF NOT EXISTS maintenance CHARACTER SET utf8mb4;`（**勿**指定 `utf8mb4_0900_ai_ci`，该排序规则仅 MySQL 8 支持，5.7 会报错）。
>
> ⚠️ **云端 MySQL 版本**：云开发 MySQL 为托管 5.7（不可自助升级）；迁移脚本已全部兼容 5.7（V2 的 JSON 列已改 `LONGTEXT`）。

### 步骤 B：后端服务（容器）

1. 云托管控制台「服务管理 → 新建服务」：
   - 部署方式：**代码仓库 / 本地代码**（仓库根 `Dockerfile` 即“云托管流水线构建入口”，自动构建 `backend/` 源码）。
   - 或「本地镜像」：本机 `docker build -f backend/Dockerfile -t maintenance-backend .` 后推送到云托管镜像仓库。
2. 服务设置（`backend/container.config.json` 提供初始值）：端口 `80`，最小实例 `0`，规格 1C2G，扩缩容 cpu 50%。
3. **环境变量**（控制台「服务设置 → 环境变量」逐个填，禁止写进任何文件）：

   | 变量 | 值 |
   |---|---|
   | `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` | 云 MySQL 内网地址与账号 |
   | `JWT_SECRET` | ≥32 字节强随机串 |
   | `WX_APPID` / `WX_APPSECRET` | 小程序 AppID 与 AppSecret（服务端 `jscode2session` 换 openid 用）；**不入库**，缺失时 `bind-wechat`/`wx-login` 返回 `2001`（AGENTS §2.1） |
  | `SEED_DEMO_DATA` | `false`（默认即 false；演示库可临时 `true`，生产禁止；别名 `DB_SEED_DEMO`） |
   | `APP_WORK_DURATION_MINUTES` | `30`（待业务确认） |
   | `REG_AUTH_LOGIN_URL` / `REG_API_BASE_URL` | 见 `.env.example` |
   | `REG_USERNAME` / `REG_KEY` / `REG_APPCODE` / `REG_SECRET` | 平台凭证（本地 `.env` 中有，**手工粘贴，勿经聊天/文档**） |
  | `REG_LEGACY_UPLOAD_ENABLED` | `false` |
   | `COS_BUCKET` / `COS_REGION` / `COS_AUTH_URL` | 托管桶（`COS_AUTH_URL` 默认值即可） |
   | `COS_SECRET_ID` / `COS_SECRET_KEY` | **仅自建 COS 桶**（本地联调）需要；云托管托管桶走内网临时凭证，留空即可 |
   | `LBS_AMAP_KEY` | 高德 Web 服务 key（`GET /location/reverse` 逆地址解析）；**不入库**，只在控制台配置（AGENTS §2.2） |
   | `APP_CHECKIN_THRESHOLD_METERS` | 签到定位阈值全局默认（米），默认 `200`；电梯级 `elevator.checkin_threshold` 优先（docs/04 A.0.4） |
   | `SERVER_PORT` | 容器端口，云托管填 `80` |
   | `JWT_EXPIRE_HOURS` | 会话有效期（小时），默认 `72`（可选） |
4. 部署后 `GET https://<域名>/health` 应返回 `UP`。

### 步骤 C：管理端 SPA（静态托管）

1. 本机构建：`cd admin && npm run build`（产物 `admin/dist/`；Windows 下用工作区内临时目录作 TMP/TEMP，见 admin/README）。
2. 云托管「静态托管」上传 `admin/dist/`。
3. 生产 API 基址已内置 `VITE_API_BASE` 默认 `/api`（同域），无需额外改。

### 步骤 D：同域路径路由

云托管「自定义域名」下配置**路径路由**：
- `/api/*` → 后端服务（**无需** strip 前缀：后端 `ApiPrefixFilter` 已统一把 `/api/**` 改写为 `/**`，小程序直连根路径与管理端带 `/api` 前缀可同域共存）；
- `/*` → 静态托管（SPA）。

### 步骤 E：小程序端切生产

1. `config/index.js`：`ENV='prod'`、`useMock=false`，并填 `cloud.env`（云开发环境 ID）与 `cloud.service`（云托管服务名）。
   接口统一走 `wx.cloud.callContainer`（`utils/request.js`，服务名经 `X-WX-SERVICE` 头传递，`app.js` 的 `onLaunch` 先 `wx.cloud.init`），**无需**给 `request` 配合法域名；低版本基础库无 `wx.cloud` 时自动回退 `wx.request → apiBaseUrl`。
   文件上传仍走 `wx.uploadFile`（`callContainer` 只支持 JSON），需把云托管域名加入「服务器域名 → uploadFile 合法域名」。
2. 微信开发者工具「上传」→ 小程序后台「提交审核/发布」。

## 7. 云托管联调已知问题（2026-10-02 验证）

1. **照片/签名回显断链（P4 范围）**：COS 模式下 `GET /files/{id}` 对云端对象返回 1404（serve() 对 url 以 http 开头的记录直接判不存在），私有桶直连 403。上传本身正常（fileId 已签发、对象已落桶）。待 P4 照片归档时统一改为 302 跳转 COS URL 或签名 URL。
2. **演示种子 emergencyPhone 含连字符超 11 位**：平台 2.6 校验直接拒绝（首次云端真实转发即暴露）。已修种子（commit 68e3dce）+ 云端存量经管理端 PUT 修正；注意 2.6 报文为签退冻结快照，修数据只对**之后的签退**生效。
3. 实例数 0（自动暂停）时冷启动约 30–60 秒，首个请求可能 503，重试即可；每日 09:00 派单定时任务在缩零期间不会执行。

## 8. 迁移中断自愈与排查（2026-11-10）

MySQL 5.7 的 DDL 没有事务，迁移中途被打断会在 `flyway_schema_history` 留下 `success=0` 的行；此后每次启动都会在 Flyway Validate 阶段直接失败，容器进入崩溃重启循环（2026-10-05 V19、2026-11-10 V22 各踩中一次）。

**现有自愈**：后端启动时在 `migrate()` 之前查询 `flyway_schema_history`，把 `success=0` 的行按主键 `installed_rank` 逐条删除，再让 Flyway 重跑这条迁移。只删失败行，**不改已成功迁移的 checksum**（`FLYWAY_REPAIR` 的 M6 口径不变）；历史表不存在（首次部署）时静默跳过。

日志关键字：

```
清理 N 条失败迁移记录 [22 (elevator project name)]，本次启动将重跑；已成功迁移的 checksum 仍严格校验（M6）
```

重跑仍失败时，日志会打印 `Migration V22__elevator_project_name.sql failed` 及 SQL State / Error Code，按码表处理：

| errorCode | 含义 | 处理 |
|---|---|---|
| 1205 | 元数据锁/锁等待超时（旧实例长事务压着表） | 停旧实例后重试 |
| 1142 | 数据库账号无 `ALTER` 权限 | 补权限 |
| 1050 | 列已存在（DDL 已生效但历史行没更新） | 把该行 `success` 置 1 |
| 1054 | 列名不存在（线上表结构与迁移脚本不一致） | 先 `SHOW CREATE TABLE` 比对 |

手工兜底（能拿到数据库写权限时）：`DELETE FROM flyway_schema_history WHERE installed_rank = ? AND success = 0;`——用主键是为了绕开控制台/服务端 `sql_safe_updates=1` 的限制。`FLYWAY_REPAIR=true` 仅在需要对齐 checksum 时临时开启，启动成功后必须删除该变量。

> 注意：云 MySQL 是内网地址（如 `10.25.110.38:3306`），本地和公网都连不上；控制台 SQL 必须确认 `DATABASE()` 是 `maintenance`、且能看到那条 `version=22, success=0` 的记录，否则改的是另一个库。
