# 电梯无纸化维保系统——账号权限与组织角色设计

**文档编号**：DM-ELEV-RBAC-2026-001
**文档版本**：V1.1
**编制日期**：2026 年 11 月 12 日
**编制依据**：用户组织架构（系统权限下设安装部、维保部、使用单位三个平级部门）
**关联文档**：《01-需求文档.md》§3.2 角色、《04-接口文档.md》A.9、《09-管理端设计.md》§三、《13-维保与急修记录表单设计.md》、`docs/superpowers/plans/2026-11-12-handover-filing-unit-portal.md`（移交/外接建档/使用单位门户在飞计划）

> 本文定义账号体系、部门与岗位层级、数据可见范围与功能权限矩阵。核心结论：**三个部门平级 → 数据域互斥；部门内上下级 → 上级可见下级、下级只见本人业务。** 权限判定顺序固定为「身份 → 部门域 → 部门内数据域 → 业务归属」，任何一层不过即 `1403` 且无副作用。

## 1. 现状与本次要解决的问题

| 现状 | 代码位置 | 缺口 |
|---|---|---|
| 5 个角色：`WORKER / ASSISTANT / LEADER / UNIT_ADMIN / ADMIN / SYS_ADMIN` | `constants/index.js`、`auth/AdminRoles.java` | 无"部门"概念，安装部/维保部/使用单位分不开 |
| 管理端门禁只有两档：读=LEADER+，写=ADMIN+ | `auth/AdminRoleInterceptor.java` | 无法表达"商务能写合同但不能看工单照片" |
| 数据权限只有班组：组长看本组，组员看本人 | `service/EmployeeScopeService.java` | 无部门隔离、无上级链、无使用单位域 |
| 使用单位账号走员工表角色 `UNIT_ADMIN` | `entity/Employee.java` | 与"使用单位是一个平级部门"不对应（在飞计划改为 `use_unit` 账号） |
| 管理端菜单全部角色可见 | `admin/src/layout/AdminLayout.vue` | 菜单未按角色下发 |

本次不改业务规则，只把"谁是谁、能看什么、能改什么"定义清楚。

## 2. 组织架构（三层部门 + 岗位树）

```
系统权限（平台层：ADMIN / SYS_ADMIN）
│
├─ 安装部 INSTALL ─────────────── 平级，互不可见
│   └─ 安装项目经理 INSTALL_MANAGER
│       ├─ 安装文员 INSTALL_CLERK
│       └─ 安装员 INSTALL_WORKER
│
├─ 维保部 MAINT ───────────────── 平级，互不可见
│   └─ 维保经理 MAINT_MANAGER
│       ├─ 维保商务 MAINT_BIZ
│       ├─ 维保班组长 LEADER
│       │   └─ 维保人员 WORKER（配合人员 ASSISTANT 为工单属性，不单独建号）
│       └─ 维保质量负责人 MAINT_QUALITY
│
└─ 使用单位 UNIT ───────────────── 平级，一间单位一个账号
    └─ 安全管理员 UNIT_ADMIN（账号落在 use_unit，绑定 useUnitId）
```

层级关系落在 `sys_employee.manager_id`（直属上级），用于"上级可见下级"的判定；`department` 用于部门域隔离。使用单位不建在本公司员工目录，账号落在 `use_unit`（在飞计划 Task 9），但权限模型上与另两个部门平级。

## 4. 平级的含义：数据域互斥（第一优先级）

三个部门"平级"= 无隶属关系、**默认互不可见**。任何跨部门可见都必须显式设计，不能顺手放开。

| 业务对象 | 安装部 | 维保部 | 使用单位 |
|---|---|---|---|
| 电梯档案 `elevator` | 本部门发起且已归档的电梯：读 + 建档 | 本部门全部负责电梯：读写 | 仅 `useUnitId` 名下电梯：读 |
| 维保工单 `work_order` | **不可见** | 全部/本班组/本人（见 §5） | 仅本梯记录：读 |
| 维保记录 `maintain_record` | **不可见** | 全部/本班组/本人 | 仅本梯：读 + 确认签字 |
| 急修单 `fault` | **不可见** | 全部/本班组/本人 | 仅本梯：报修 + 查看 |
| 移交单 `handover_order` | 本部门：读写 | 待确认/已接收：读 + 确认 | 不可见 |
| 外接建档单 | 本部门：读写 | 合同前置校验 + 确认 | 不可见 |
| 维保合同 `maintenance_contract` | 本部门相关项目：读 | 经理读 / 商务读写 | 本单位合同：读 |
| 使用单位档案 `use_unit` | 不可见 | 经理读 / 商务读写 | 本单位信息：读 |
| 人员档案 `sys_employee` | 本部门下属：读写 | 本部门下属：读写 | 仅本单位账号 |
| 上报日志 `reg_upload_log` | 不可见 | 经理读 / 班组本组 / 质量读 | 不可见 |

**唯一的部门交接面是移交单**：归档前数据归安装部，`handover_order.archive()` 之后电梯与首保工单归维保部（在飞计划 Task 5）。

## 5. 部门内数据可见范围（第二优先级）

| 角色 | 可见范围谓词（伪代码） | 写范围 |
|---|---|---|
| `MAINT_MANAGER` | `department = MAINT`（全部门） | 部门内全部业务写 |
| `LEADER` | `department = MAINT AND group_name = 本人班组` | 本班组工单的延期/转派、质量整改确认 |
| `WORKER` / `ASSISTANT` | `worker_platform_id = 本人platformId`（本人作业的工单） | 本人签到/清单/签退/急修登记 || `MAINT_QUALITY` | `department = MAINT`（跨班组，读全量） | 仅「抽检记录/复检结论/模板启停」；**不得签退、不得重报、不得改工单** |
| `MAINT_BIZ` | `department = MAINT AND 合同/客户域`（合同、使用单位）；工单域只见汇总统计，**不见现场照片/定位/签字** | 合同与使用单位档案写 |
| `INSTALL_MANAGER` | `department = INSTALL AND (initiator_id = 本人 OR project_name ∈ 本人项目)` | 移交/外接建档发起、文档提交、指派接收人 |
| `INSTALL_CLERK` | `department = INSTALL AND initiator_id = 本人上级`（经理名下单据） | 仅 3 类必传资料上传/替换（`submit-docs`），不改状态机 |
| `INSTALL_WORKER` | `department = INSTALL AND 本人在被指派/查验名单` | 现场查验、整改前后照片 |
| `UNIT_ADMIN` | `use_unit_id = 本人绑定单位` | 本梯记录确认签字、报修 |

**读范围与写范围必须分开实现**（2026-11-12 落地时发现的红线）：区域只能扩大**读**（列表/台账），不能扩大**写**。`EmployeeScopeService` 因此有两个谓词——`visibleReadPlatformIds`（区域 ∪ 本班组 ∪ 本人，供电梯列表与工单列表）与 `visibleWorkerPlatformIds`（本人/本组，签到/清单/签退/签字共用）。若把区域并进写谓词，同区域同事即可凭工单 id 代签到、代签退，签退会自动上报平台 2.6（AGENTS §3.1 Blocker）。

**能力码口径（实现时必须遵守，前端 `admin/src/utils/permission.js` 与后端 `PermissionMatrix` 逐字同名）**

- `console:read` / `console:write` 是管理端"进得来 / 能改"的粗粒度闸门；细粒度动作看下面各业务码。
- `order:write` / `fault:write` 指**现场作业写**（签到/清单/签退/急修登记，班组长受本组范围约束）。管理端的"延期/转派"属计划调度，用 `plan:write`；"重报"用 `report:retry`——**不要**用 `order:write` 给管理端按钮授权，否则会把现场作业权和调度权混成一档。
- `handover:write` / `filing:write` 含"资料上传"这一档：安装文员（`INSTALL_CLERK`）持有该码，但只允许调 `submit-docs`；状态机流转（发起/指派/查验/确认）由端点级动作码在 P3 收敛。
- `template:write` 对质量负责人只开放"启停"，不含模板内容编辑；P3 拆 `template:toggle`。
- 未知能力码/未知角色一律拒绝（`PermissionMatrix` 类初始化校验 + 前端 `can()` 返回 false）。

## 8. 关键规则（实现时逐条落地，缺一即缺陷）

| # | 规则 | 落点 |
|---|---|---|
| R1 | 三部门平级互斥：跨部门读即 `1403`，不得在列表里"顺便"返回 | 每个列表/详情统一走部门谓词 |
| R2 | 上级可见下级、下级不可见上级的管理数据（合同金额、人员薪酬、上报失败原因等） | 管理链谓词 + 字段级脱敏 |
| R3 | 质量负责人只读 + 抽检写：不得签退、不得重报、不得改工单状态 | 写端点按"动作"而非"角色等级"授权 |
| R4 | 商务不见现场作业数据（照片/定位/签字），只做合同与客户 | 响应字段按角色裁剪 |
| R5 | 使用单位只见 `useUnitId` 名下电梯；他人电梯 `1403` | 使用单位门户谓词（在飞计划 Task 10） |
| R6 | 安装部与维保部的交接点是移交单归档：归档前归安装、归档后归维保 | `archive()` 事务内切换负责人 |
| R7 | 一人一号；跨部门兼任默认禁止，确需兼任须建第二个账号（避免一个账号两套数据域） | 建档校验 |
| R8 | 停用/离职立即失效：`enabled=false` + 会话清除（`session_id`/`session_admin` 置空） | 账号启停端点 |
| R9 | 越权一律 `1403` 且无副作用（先校验后落库，不产生半成品状态） | 写端点校验顺序（AGENTS §4.2） |
| R10 | 列表过滤 + 详情校验双保险；只做列表过滤等于可枚举主键越权 | 同一谓词两处复用 |

## 9. 落地设计

### 9.1 数据模型（V31 迁移，只追加）

```sql
-- sys_employee 增部门与上级（role 列为字符串，新增码值不需要改表结构）
ALTER TABLE sys_employee
  ADD COLUMN department VARCHAR(16) NULL COMMENT 'INSTALL/MAINT/UNIT/PLATFORM',
  ADD COLUMN manager_id VARCHAR(64) NULL COMMENT '直属上级 empId（上级可见下级）',
  ADD COLUMN job_title  VARCHAR(32) NULL COMMENT '岗位名称（展示用）';
-- 存量回填：LEADER/WORKER/ASSISTANT → MAINT；ADMIN/SYS_ADMIN → PLATFORM；UNIT_ADMIN → UNIT
```

使用单位账号按在飞计划落 `use_unit.account / password_hash / openid`（V30），角色固定 `UNIT_ADMIN`，不进 `sys_employee`。

### 9.2 鉴权链（四层，顺序不可调）

```
AuthInterceptor（JWT → empId/role/useUnitId）
   → RoleCatalog（角色 → 部门 + 层级 + 可用端）
   → PermissionMatrix（角色 × 动作 → 允许/拒绝，403）
   → DeptScopeService（部门域 + 上级链 + 班组 + 本人，越权 1403）
   → 业务归属校验（工单/记录/电梯归属，1403）
```

### 9.3 门禁实现改造

| 现状 | 目标 |
|---|---|
| `AdminRoleInterceptor` 内三段 `if` 硬编码读/写两档 | 改为 `@RequirePerm("order:write")` 注解 + `PermissionMatrix` 表驱动，未知权限码启动即失败（防止拼错静默放行） |
| `EmployeeScopeService` 只认 `ADMIN/SYS_ADMIN/LEADER` | 扩为 `DeptScopeService`：`platform / dept / managerChain / group / self / useUnit` 五种谓词，每个业务查询显式声明用哪种 |
| 菜单全量渲染 | `GET /auth/menus` 按角色下发菜单树，前端只渲染下发的项（后端仍强校验） |

### 9.4 前端

- 管理端：路由 `meta.perm` 与后端权限码同名；菜单由 `/auth/menus` 驱动；越权进 `/403`。
- 小程序：`pages/mine/index.js` 的 `buildMenus(role)` 改为按部门+角色映射（安装部三角色新增移交单入口；使用单位安全管理员新增"本梯记录/报修"）。

### 9.5 现有账号迁移

| 现有角色 | 迁移后 | 说明 |
|---|---|---|
| `ADMIN` | `ADMIN`（平台管理员） | 权限不降级，跨部门全权 |
| `SYS_ADMIN` | 不变 | 保留不启用 |
| `LEADER` | `LEADER` + `department=MAINT` | 班组口径不变 |
| `WORKER` / `ASSISTANT` | 不变 + `department=MAINT` | 工单归属不变 |
| `UNIT_ADMIN` | `UNIT_ADMIN`（后续迁到 `use_unit` 账号） | 过渡期双轨：员工表账号可用，门户账号上线后停用员工表账号 |

## 12. 取舍与风险

1. **不给"超级角色"开小门**：`ADMIN` 跨部门全权是唯一例外，且不参与业务签字（签字必须落到具体角色），避免"管理员代签"。
2. **不用前端隐藏代替后端校验**：菜单/路由隐藏只是体验，全部权限码在后端矩阵里再判一次。
3. **部门域不做"借用"**：跨部门临时协作走单据共享（移交单/外接建档单），不给账号加临时部门，避免权限漂移无法审计。
4. **质量负责人不带队**：它的可见范围是"全维保部"，但不是任何人的上级——避免与班组长形成双头管理。
5. **风险**：`ADMIN` 语义升级为平台管理员后，若客户实际需要"维保部经理 vs 平台管理员"分离，必须新开 `MAINT_MANAGER` 账号，不能共用 ADMIN（共用会失去部门边界）。
