# 电梯无纸化维保系统——账号权限与组织角色设计

**文档编号**：DM-ELEV-RBAC-2026-001
**文档版本**：V2.3
**编制日期**：2026 年 11 月 12 日（V2.0 修订：2026 年 11 月 16 日；V2.1 审核修订：2026 年 11 月 16 日；V2.2 代码事实校准：2026 年 11 月 16 日；V2.3 P1 落地回写：2026 年 11 月 16 日）
**文档状态**：**P1 已落地（2026-11-16，分支 codex/permission-p1，不改表/不动登录主体二分）**；P2—P4 待排期（模型口径仍 V2.1）
**编制依据**：用户业务口径（2026-11-16 修正）+ 2026-11-16 逻辑审核结论——维保公司内部设平台管理、安装部、维保部；使用单位是外部客户租户，不是公司部门；客户账号仅用于维保完成后由本单位安全管理员签字；公司可与多家使用单位签维保合同；客户账号只见本单位电梯
**关联文档**：《01-需求文档.md》§3.2 角色、《04-接口文档.md》A.9/A.12、《09-管理端设计.md》§三、《13-维保与急修记录表单设计.md》、《15-安装移交维保检查清单表单设计.md》、《16-管理端重构设计与验收.md》、`docs/superpowers/plans/2026-11-16-development-roadmap.md`

> 本文定义账号体系、组织/客户域、数据可见范围与功能权限矩阵。核心结论：**公司内部按“平台管理 / 安装部 / 维保部”分工；使用单位是外部客户租户，按 `use_unit_id` 隔离；客户账号只做本单位电梯与维保记录的查看、签字/拒签、下载，不参与内部作业与管理。** 客户签字只允许发生在 `PENDING_CLIENT_SIGNATURE` 状态的最新版本记录上；签字更新确认状态、签字文件与归档状态，拒签只更新确认状态与客户拒签字段，均不触发平台 2.6 重报。权限判定顺序固定为「主体类型（员工/客户）→ 内部部门域或客户租户域 → 内部数据域 → 业务归属」，任何一层不过即 `403`/`1403` 且无副作用。
>
> **V2.1 是对 V1.x 主体模型的修正，不是推倒重来。** 13 个规范角色、现有 86 个能力码、`use_unit_id` 锚点、客户本单位查询雏形可继续复用；需要纠正的是“把使用单位当第三部门”、客户账号混入员工表、客户矩阵过宽、记录按电梯当前归属查询、客户与内部共用接口面、客户签字无状态门禁、客户详情字段过曝、文件签名未绑定租户这八件事。客户侧新增/收回的能力码见 §5.4，最终数量以实施后矩阵为准。

## 1. V2.1 修正说明（先读）

### 1.1 修正了什么

| 项目 | V1.x 旧口径（已废弃） | V2.1 新口径 |
|---|---|---|
| 使用单位 | 公司第三个平级部门（安装部 / 维保部 / 使用单位） | **外部客户租户**，不在公司组织树内 |
| 客户账号 | 员工表 `sys_employee` + `CLIENT_*` 角色，`department=UNIT` | **独立客户账号** `client_account`，一个账号绑定一个 `use_unit_id`，不占编制；同一手机号可在多个单位各有一个账号，登录时选择单位 |
| 部门码 | `PLATFORM / INSTALL / MAINT / UNIT` | `PLATFORM / INSTALL / MAINT`；`UNIT` 仅保留为历史兼容别名，不再作为部门 |
| 数据域 | 三部门互斥，客户按 `useUnitId` | 内部：平台 / 部门 / 班组 / 本人；客户：租户 `use_unit_id` + 记录状态 + 记录版本；两套谓词分开 |
| 客户能力 | 含 `USER_CREATE`、`STATS_VIEW`、`AUDIT_VIEW` 等内部能力 | 仅 `client:*` 最小集：本单位电梯/最新版本记录查看、签字/拒签、下载；账号管理/合同/移交/报修/评价默认关闭 |
| 客户签字 | 只判 `confirmStatus`，可绕过复核/双签发起 | 只允许 `PENDING_CLIENT_SIGNATURE` 最新版本 + `confirmStatus=PENDING`；签字/拒签不触发 2.6 重报 |
| 记录归属 | 按电梯当前归属推导 | 记录优先继承工单 `use_unit_id`，修订继承首版；归档 PDF 用记录快照，不按电梯当前归属回查 |
| 客户字段 | 详情返回上报报文、GPS、shareToken 等内部字段 | 客户专用字段白名单；内部字段一律不返回（§4.7） |
| 接口面 | 客户与内部共用部分端点 | 客户令牌业务端点只允许 `/client/**`；认证/文件/健康检查按 §7.3 例外；内部端点对客户令牌 `403` |
| 文件访问 | 签名 URL 只签 `fileId`，无租户绑定 | 客户文件走鉴权代理或短 TTL 签名；签发前校验 `record/fault.use_unit_id`，签名绑定 `useUnitId` |
| 组织树 | `sys_org` 有 `UNIT` 节点/部门 | 内部组织树只保留公司 / 部门 / 班组；`UNIT` 节点保留为历史/外部展示，不作为权限部门 |

### 1.2 为什么改

用户业务口径（2026-11-16）：

1. 公司是电梯维保公司，内部只有安装部、维保部两个业务部门；平台管理是行政/系统层，不是业务部门；
2. 使用单位只是客户，给账号的原因是维保完成后需要本单位安全管理员签字；
3. 一家维保公司可以跟多家使用单位签维保合同；
4. 每个使用单位账号只能看到自己单位的电梯，不能看到其他单位。

因此，“三个平级部门”的模型在主体归属、数据边界、账号生命周期和权限矩阵上都不成立。V2.1 按“内部员工 / 外部客户”二分重建，并补齐 2026-11-16 逻辑审核发现的签字状态、租户快照、字段白名单、文件绑定、迁移与分期问题。

### 1.3 默认决策（2026-11-16）

| # | 决策 | 确认结果 |
|---|---|---|
| D1 | 客户账号权限范围 | **只保留**：查看本单位电梯、查看本单位最新版本维保记录（仅允许状态）、下载本单位记录 PDF、签字确认、拒签（原因必填）；**报修/评价/合同/移交默认关闭**，如后续业务需要再单独开启 |
| D2 | 一个使用单位几个账号 | 默认 **1 个 `CLIENT_ADMIN`（安全管理员）**；允许按需增开 N 个 `CLIENT_SIGNER`（签字人）；开通时只建 1 个。**增开/停用/重置统一由内部有权限人员操作，客户管理员默认不管理账号** |
| D3 | 客户可见电梯范围 | **本单位全部电梯**（`elevator.use_unit_id = 本账号.use_unit_id`）；维保合同只控制客户账号的启用/停用，不按合同切电梯。该单位全部合同到期/终止才进入宽限期，任一有效合同保持启用 |
| D4 | 客户管理员能否自助管理签字人 | **默认不能**：`client:user_manage` 默认 DENY；开通/停用/重置/换绑由内部 `useunit:write/client:edit/client:invite` 执行；如未来按单位开启，仅能管理本单位 `CLIENT_SIGNER` |
| D5 | 同一手机号多个使用单位 | **按单位各一个账号**（同单位内仅活跃账号唯一；停用账号保留历史但不占活跃唯一键），登录先验口令再选单位；不做“一个账号多单位”；员工/客户跨表手机号/openid 互斥 |
| D6 | 客户能否看合同/移交 | **默认不能**：合同即使后续开启也只读、不含金额；移交单 V2.1 收回，如客户需签收另设 `client:handover_*`，不直接复用内部 `handover:*` |

### 1.4 与现有实现的关系

| 现有实现 | V2.1 处理 |
|---|---|
| 13 个规范角色、现有 86 个三态能力码 | **复用**；只调整角色分类与客户能力集（新增/收回码见 §5.4）；`CLIENT_ADMIN/CLIENT_SIGNER` 能力相同，`CLIENT_ADMIN` 仅表示单位主账号/默认联系人，不具账号管理权 |
| `sys_role_scope` 的 `CLIENT_ADMIN/CLIENT_SIGNER = ORG_FLAT` | **客户解析不读该表**：范围只取 `client_account.use_unit_id`；迁移后清理 `CLIENT_*` 行，避免双事实源 |
| `UnitPortalService` 的本单位电梯/记录查询 | **复用查询雏形**；记录查询从“电梯当前归属”改为“记录冻结的 `use_unit_id`”，只返回最新版本 + 允许状态 |
| `UnitRecordService` 的门户读/签端点 | **必须一起改**：`unitOf()` 当前按电梯归属推导、`pendingAs()` 只筛 `confirmStatus`、`toMap()` 暴露内部字段；V2.1 改为记录快照 + 状态门禁 + 客户白名单 |
| `sys_user_role.org_id = use_unit.id` 锚点 | **迁移期只读兼容**；迁出后删除客户角色行，不再作为权限锚点 |
| V41 门户账号并入 `sys_employee` | **客户账号迁出**；内部员工“单账号多角色”不变；旧客户员工行标 `CUSTOMER_ARCHIVED` 并过滤 |
| 文件签名 `fileId:expiry` | **客户文件改为鉴权代理或短 TTL 签名**；签发前校验记录/急修的 `use_unit_id`，签名绑定 `useUnitId` |
| 内部签到/签退/动态码/上报/30 分钟等业务不变量 | **不动**（AGENTS §3） |

## 2. 业务关系与主体模型

### 2.1 组织树

```text
维保公司（单一法人）
├─ 平台管理（PLATFORM_ADMIN / SYS_ADMIN，行政/系统管理，不是业务部门）
├─ 安装部 INSTALL
│  ├─ 安装经理 INST_MGR
│  ├─ 安装项目负责人 INST_PM
│  ├─ 安装资料员 INST_CLERK
│  └─ 安装员 INSTALLER
└─ 维保部 MAINT
   ├─ 维保经理 MAINT_MGR
   ├─ 维保主管/班组长 MAINT_SUP
   ├─ 维保人员 MAINT_TECH
   ├─ 维保商务 MAINT_BIZ
   └─ 维保质量 MAINT_QUALITY

外部客户域（不属于公司组织树）
├─ 使用单位 A（use_unit.id = uu_A）
│  ├─ 客户账号 A-安全管理员（CLIENT_ADMIN）
│  └─ 客户账号 A-签字人（CLIENT_SIGNER，可选）
├─ 使用单位 B
└─ 使用单位 C

公司与 A/B/C 分别签维保合同；
elevator.use_unit_id 决定电梯归属；
client_account.use_unit_id 决定客户账号的租户边界。
```

层级关系：

- `sys_employee.manager_id`：内部员工直属上级，仅用于“上级可见下级”，不扩大写范围；
- `sys_employee.department`：内部部门域，只允许 `PLATFORM / INSTALL / MAINT`；
- `client_account.use_unit_id`：客户租户域，客户账号只认这一个字段；
- `sys_org` 的 `UNIT` 节点：保留为历史/外部客户展示，不进入内部组织树，不作为权限部门。

### 2.2 主体二分

| 维度 | 内部员工 | 外部客户 |
|---|---|---|
| 主体类型 | `EMPLOYEE` | `CUSTOMER` |
| 归属 | 维保公司 | 使用单位（客户） |
| 账号载体 | `sys_employee` + `sys_user_role` | `client_account`（独立表） |
| 角色 | 11 个内部角色 | `CLIENT_ADMIN` / `CLIENT_SIGNER`（能力相同，后者仅称谓不同） |
| 数据域 | 平台 / 部门 / 班组 / 本人 | 仅 `use_unit_id` + 记录状态/版本门禁 |
| 管理端 | 按角色可登录 | **不可登录** |
| 小程序 | 作业工作台 | 客户工作台：待签 / 电梯 / 记录 / 我的；多单位账号登录先选单位 |
| 组织树 | 在 | **不在** |
| 编制/统计 | 计入 | **不计入** |
| 签字 | 不得代客户签字 | 只能签本单位 `PENDING_CLIENT_SIGNATURE` 最新版本记录 |
| 会话 | `sys_employee.session_id` / `session_admin` | `client_account.session_id`（单账号单会话） |

> **这不是恢复旧 `unit_token` 双令牌。** 登录仍走 `/auth/login` 一个入口、返回一个 token；token 带 `principalType=EMPLOYEE|CUSTOMER`。内部员工的多角色并集规则不变；客户账号是独立主体，不参与内部角色并集。同一手机号可对应多个单位的客户账号，但**登录必须先验证口令，再选择单位**；未验证口令前不得返回该手机号下的单位列表。

### 2.3 合同、电梯、账号的关系

```text
维保公司 1 ── N 维保合同 ── N 使用单位
使用单位 1 ── N 电梯
使用单位 1 ── N 客户账号（默认 1 个 CLIENT_ADMIN，可选 N 个 CLIENT_SIGNER）
电梯 1 ── N 维保记录 / 急修单 / 工单（记录冻结 use_unit_id）
```

- `use_unit` 是客户主数据/租户主表；
- `maintenance_contract.use_unit_id` 是合同与客户的关联；
- `elevator.use_unit_id` 是电梯归属；
- `client_account.use_unit_id` 是账号的租户边界；
- 一家使用单位可以有多个合同（历史/续签），客户账号仍只按 `use_unit_id` 看本单位全部电梯；
- **该单位全部合同到期/终止** → 未人工停用的客户账号进入 `GRACE` 宽限期（只读/下载 + 待签签字），宽限期结束转 `DISABLED`；任一有效合同保持 `ACTIVE`（人工停用不自动恢复，见 §6.3）；
- 历史记录按留存策略保留；合同不切电梯，但账号 `DISABLED` 后客户看不到任何电梯/记录。

### 3.3 客户角色职责

| 角色码 | 名称 | 归属 | 职责 | 可登录端 |
|---|---|---|---|---|
| `CLIENT_ADMIN` | 使用单位安全管理员（主账号/默认联系人） | 一个 `use_unit_id` | 查看本单位电梯/最新版本记录、签字/拒签、下载；**默认不管理账号** | 小程序 |
| `CLIENT_SIGNER` | 使用单位签字人 | 一个 `use_unit_id` | 查看本单位电梯/最新版本记录、签字/拒签、下载 | 小程序 |

- 客户角色**不是部门角色**，不参与内部部门互斥、上下级链、同部门兼任规则；
- 一个客户账号只持有一个客户角色；需要多人签字就建多个 `CLIENT_SIGNER`，不把客户角色叠加到员工角色上；
- `CLIENT_ADMIN` 与 `CLIENT_SIGNER` 的能力集相同，`CLIENT_ADMIN` 仅表示单位主账号/默认联系人；**账号开通/停用/重置/换绑由内部人员操作**，客户管理员默认不具账号管理权；
- 同一手机号可在不同 `use_unit_id` 下各有一个客户账号；同一 `use_unit_id` 内仅活跃账号手机号/openid 唯一（停用账号保留历史）；登录时先验口令，再选择单位；
- 客户账号不能被授予任何内部角色；内部员工也不能被授予客户角色去“代签”。

## 4. 数据域

### 4.1 内部数据域（第一层）

| 范围 | 角色 | 读谓词 | 写谓词 |
|---|---|---|---|
| 平台 | `PLATFORM_ADMIN` / `SYS_ADMIN` | 全公司（审计留痕）；客户支持走内部只读端点 | 公司管理；**不代客户签字** |
| 安装部 | `INST_MGR` / `INST_PM` / `INST_CLERK` / `INSTALLER` | 本部门项目/移交/外接建档/相关电梯；关联单位基本信息只读 | 本部门单据；安装资料员仅资料上传 |
| 维保部 | `MAINT_MGR` / `MAINT_SUP` / `MAINT_BIZ` / `MAINT_QUALITY` / `MAINT_TECH` | 维保部全部 / 本组 / 本人（按角色细分） | 派单/复核/合同/本人作业；质量不签退、不重报 |

- **部门互斥**：安装部与维保部默认互不可见；唯一交接面是移交单归档（归档前归安装，归档后归维保）。
- **上级链**：`manager_id` 只用于“上级可见下级”，不用于扩大写范围。
- **维保部多单位可见是正常的**：维保经理/商务/班组可以同时服务多家使用单位，这是公司内部工作范围，不是客户跨租户。
- **安装部使用单位口径**：安装部只可读本项目/移交/外接建档关联单位的基本信息（名称、联系人、电话），不开放全量使用单位档案列表；客户主数据维护仍归维保商务/平台。

### 4.2 客户租户域（第二层）

| 角色 | 读谓词 | 写谓词 |
|---|---|---|
| `CLIENT_ADMIN` / `CLIENT_SIGNER` | `elevator.use_unit_id = 本账号.use_unit_id`；`record.use_unit_id = 本账号.use_unit_id` + 记录链最新版本 + 允许状态 | 本单位 `PENDING_CLIENT_SIGNATURE` 最新版本记录的签字/拒签；账号管理默认无 |

硬约束：

1. `useUnitId` 只从 token 取，请求体/query 指定的单位 id 一律不采信；不一致 `403`；
2. 客户查询/详情/签字/下载全部加 `use_unit_id` 条件；
3. 客户不能看到内部工单、派单、统计、审计、移交、项目、合同金额、上报日志；
4. 客户 A 看不到客户 B 的任何数据，哪怕 A/B 由同一个维保班组服务；
5. 平台管理员通过内部只读端点查看客户数据做支持，**不能调用客户签字接口**；`/client/**` 对内部 token 一律 `403`；支持访问要留审计；
6. 客户签字只允许 `lifecycle_status=PENDING_CLIENT_SIGNATURE` + `confirm_status=PENDING` + 最新版本；其余状态 `422`/`1403`；
7. 客户详情只返回 §4.7 白名单字段；`reportPayload`、`context`、`shareToken`、平台 ID、内部复核/修订字段一律不返回；
8. 文件读取必须能回查到记录/急修的 `use_unit_id`；客户文件走鉴权代理或短 TTL 签名，签发前做租户校验。

### 4.4 记录级租户快照（关键）

`maintain_record`、`fault`、`work_order` 在生成时冻结：

- `use_unit_id`（租户归属）
- `use_unit_name`（展示用，生成时快照；归档 PDF 不再回查当前单位）
- `elevator_id` / `elevator_code`（设备归属）

规则：

1. **记录优先继承工单**：签退生成记录时，取工单 `use_unit_id`（派单/接单时已冻结）写入 `maintain_record.use_unit_id`；无工单的手工补录才取 `elevator.use_unit_id`；
2. 急修登记时：客户报修取 token `useUnitId`；内部登记取电梯/工单当前归属，并立即写入 `fault.use_unit_id`；
3. 派单/工单生成时写入 `work_order.use_unit_id`；工单在作业中电梯过户，工单仍归原单位，记录继承工单，不重新读电梯；
4. 客户查询/签字一律按 `record.use_unit_id = token.useUnitId`，**不再按电梯当前归属 join**；
5. 电梯过户后：历史记录仍归原单位，新记录归新单位；客户记录列表按快照，电梯列表按当前归属，二者允许不一致，UI 明确“历史记录仍可查”；
6. **修订版本继承首版**：`WorkDomainService.amend()` 创建 v2 时复制 `useUnitId/useUnitName/elevatorId`，不得重新读取电梯当前归属；v1 的签字保留在 v1，v2 必须重新走客户签字；
7. **归档/PDF 用快照**：`RecordLifecycleService.archive()`、`RecordPdfService`、`AdminRecordController` 的记录 PDF 必须使用 `record.use_unit_id/use_unit_name`；快照为空时内部 PDF 标注“归属待核对”，客户门户不展示；
8. **回填不能按当前归属静默猜**：凡电梯存在 `biz_elevator_change`/审计过户记录的，其历史记录一律进人工核对清单；无过户记录才可按当前归属回填；无法确定置 `use_unit_id=NULL`，客户门户不展示；
9. 迁移/上线窗口内新生成的记录若快照为空，客户门户隐藏、内部可见；由回填脚本补齐后再开放。

### 4.5 读写分离

- **内部**：区域/部门只扩读，写严格本人/本组/被指派（AGENTS §3.1）；`visibleReadPlatformIds` 与 `visibleWorkerPlatformIds` 继续分离。
- **客户**：读范围 = 本单位全部；写范围 = 本单位待签记录 / 本单位电梯报修（若开启）；不得借读范围扩大写范围。
- **列表过滤 + 详情校验双保险**（R10）：只做列表过滤等于可枚举主键越权。

### 4.6 客户记录可见性、签字状态与版本

客户记录必须同时满足：`record.use_unit_id = token.useUnitId`、是该记录链**最新版本**、状态在允许集合内。

| `lifecycle_status` | 客户可见 | 可签字/拒签 | 说明 |
|---|---|---|---|
| `PENDING_REVIEW` | 否 | 否 | 内部复核中，未发起客户签字 |
| `PENDING_CLIENT_SIGN` | 否 | 否 | 双签未齐/尚未 `signRequest`，客户不应提前看到 |
| `PENDING_CLIENT_SIGNATURE` | 是 | **是** | 唯一可签状态；仍需 `confirm_status=PENDING` + 最新版本 |
| `SIGNED` | 是（只读） | 否 | 签字完成，自动转 `ARCHIVED` |
| `ARCHIVED` | 是（只读） | 否 | 可下载 PDF，不可改 |
| `REFUSED_RETURNED` | 是（只读） | 否 | 客户已拒签；显示原因，等待维保单位修订/重发 |
| `NULL`/其他 | 否 | 否 | 不作为客户可见记录 |

规则：

1. **最新版本**：客户列表/详情只返回记录链末端；判断条件为“不存在 `prev_version_id = 当前记录.id` 的后续版本”。历史版本仅内部/审计可见。
2. **签字门禁**：客户签字/拒签前必须依次校验：`principalType=CUSTOMER` → token `useUnitId` → `record.use_unit_id` → `lifecycle_status=PENDING_CLIENT_SIGNATURE` → `confirm_status=PENDING` → 最新版本 → 账号 `ACTIVE`，或 `GRACE` 且 `now <= grace_until`。任一失败 `403/1403/422`，不产生写副作用。`ACTIVE` 期间不另设待签超时；如业务要求超时，另加配置，不在本方案默认。
3. **一次记录只需一个客户签字**：同一单位多个 `CLIENT_ADMIN/CLIENT_SIGNER` 不要求会签；先签为准，其他账号看到已签只读；落库用条件更新/行锁（`WHERE confirm_status='PENDING' AND lifecycle_status='PENDING_CLIENT_SIGNATURE'`），并发第二个签字返回 `422/已签`，不覆盖首签。
4. **签字落库**：`confirm_status=CONFIRMED` + `signature_file_id/signature_url` + `client_account_id` + `client_signer_name`（快照）+ `client_signed_at`；随后 `onClientSigned` 置 `SIGNED` 并归档。
5. **拒签落库**：`lifecycle_status=REFUSED_RETURNED` + `client_refuse_reason`（必填；与内部复核退回的 `refuse_reason` 分开）+ `refused_by_client_account_id` + `client_refuser_name`（快照）+ `client_refused_at`；退回维保单位修订/重新复核，客户不能自行重签。
6. **不触发 2.6**：客户签字/拒签只改确认状态与签字文件，**不触发平台 2.6 重报、不改签退时的上报快照**；2.6 仍在签退时即报（AGENTS §3.5）。
7. **已签后修订**：`WorkDomainService.amend()` 新建 v2 后，v1 的客户签字保留审计；v2 重新走内部复核/双签/`signRequest`/客户签字；客户只看到 v2，不能签 v1。
8. **匿名分享链接**：目标态（P3/P4）**移除客户详情中的 `shareToken`**，客户签字必须登录；P1/P2 旧 `/unit/**` 兼容期可保留既有 `shareToken` 供旧链接使用，但不再签发新链接；P3 `/client/**` 不返回 `shareToken`；P4 旧 `/unit/**` 410。如业务确需外部分享，另设一次性/短时 token，并同样执行上述状态门禁与审计。

### 4.7 客户字段白名单

客户记录详情只返回：

- 记录标识与版本：`id`、`version`、`prevVersionId`（可选）、`lifecycleStatus`、`amendReason`（脱敏后）
- 设备：`elevatorCode`、`elevatorName`、`useUnitName`
- 作业：`workType`、`workTypeCode`、`workerName`、`assistantName`、`checkinTime`、`checkoutTime`、`duration`
- 内容：`items`（检查项名称/结果/实测值/照片 URL）、`photos`、`problemCodes`、`todoDesc`
- 签字：`workerSignatureUrl`、`assistantSignatureUrl`、`confirmStatus`、`clientSignerName`、`clientSignedAt`、`signatureUrl`
- 下载：`pdfUrl`（鉴权代理或短 TTL 签名）
- 拒签：`clientRefuseReason`（仅 `REFUSED_RETURNED` 时返回；内部复核退回的 `refuseReason` 不返回）

**明确不返回**：`reportStatus`、`uploadStatus`、`retryCount`、`reportPayload`、`context`/`previewContext`、`shareToken`、`originalRecordId`、`workerPlatformId`、`assistantPlatformId`、`refuseReason`（内部复核/退回原因）、`amendReason` 的内部审批链、内部复核意见、幂等键、平台日志。`satisfaction` 默认不返回/不接收（评价关闭）。

客户电梯/单位信息只返回：电梯编码/名称/项目/地址、单位名称、账号姓名/角色；不返回合同金额、内部班组、平台 ID、其他单位信息。

### 4.8 文件访问与签名上传

1. **客户文件不走公共签名直链**：优先 `GET /client/files/{fileId}`（客户 token + 记录/急修租户校验 + 流式下发）；小程序用 `wx.downloadFile`/`wx.request` 带 Authorization 下载后本地展示。
2. 如受 `<image>` 标签限制必须用 URL，则使用**短 TTL（≤10 分钟）签名 URL**，签发前校验 `record/fault.use_unit_id`，客户签名内容绑定 `fileId:useUnitId:expiry`（与内部 `fileId:expiry` 分版本/分端点，不能混用）；`GET /files/{id}?s=` 解析签名中的 `useUnitId` 并复核文件归属，不一致 `403`；不得把签名/log 写入日志。
3. **客户签名上传**：`POST /client/files`（客户 token，绑定记录/单位）或签字端点内联 base64 由服务端落库；不得走无归属的通用 `/files/upload`。
4. **客户 PDF**：`GET /client/records/{id}/pdf` 先校验记录租户/状态，再返回 PDF 或短时 URL；归档 PDF 使用记录快照单位，不按当前电梯回查。
5. 文件归属无法回查（历史 NULL/孤儿文件）时，客户侧 `403`，内部按人工核对流程处理。

| 移交单 | **DENY** | **DENY** | V2.1 收回；如需签收另开能力 |
| 报修 / 评价 | **默认 DENY** | **默认 DENY** | 如开启，仅本单位电梯；评价不塞进签字端点 |
| 内部能力（全部） | **DENY** | **DENY** | 见 §5.4 |

### 5.4 能力码口径

**客户保留（Y）**：

- `client:elevator_view`（复用现有码；本单位信息/电梯只读）
- `client:record_view`（新增；与内部 `record:view` 分开，避免混用；只返回最新版本 + §4.7 白名单字段）
- `client:download`（复用现有码，限本单位记录 PDF；走租户校验）
- `client:sign`（复用现有码；`CLIENT_ADMIN`/`CLIENT_SIGNER` 都给 Y；仅 `PENDING_CLIENT_SIGNATURE` 最新版本）
- `client:refuse`（新增；拒签原因必填；仅 `PENDING_CLIENT_SIGNATURE` 最新版本）

**客户默认 DENY（后续业务确认才开）**：

- `client:user_manage`（账号管理；默认 DENY，内部人员操作）
- `client:contract_view`（合同只读；默认 DENY，且不含金额）
- `client:report` / `client:evaluate`（报修/评价；默认 DENY，且不得混入签字端点）
- `client:invite`（邀请开通；内部码，不下发客户角色）
- `client:handover_*`（移交单；V2.1 收回，如客户需签收另设）

**客户收回（内部能力，必须 DENY）**：

- `console:*`、`user:view/create/disable`、`role:assign`、`invite:manage`
- `stats:view`、`stats:export`、`audit:view`
- `order:*`、`plan:*`、`record:view/sign/refuse`、`record:review`、`record:amend`、`record:archive`、`record:export`
- `handover:*`、`project:*`、`contract:view/edit`、`elevator:view/qr/export`
- `report:*`、`template:*`、`region:*`、`platform:*`、`data:export_sensitive`
- 以及任何未在 §5.3 列出的能力码

> 当前 `PermissionMatrix` 给 `CLIENT_ADMIN` 的 `USER_VIEW/USER_CREATE/USER_DISABLE/ROLE_ASSIGN/INVITE_MANAGE/STATS_VIEW/STATS_EXPORT/AUDIT_VIEW/ORDER_CREATE/ORDER_VIEW_OWN/ORDER_CANCEL/ORDER_EXPORT/PLAN_VIEW/RECORD_EXPORT/HANDOVER_VIEW/HANDOVER_EXPORT/PROJECT_VIEW/CONTRACT_VIEW/ELEVATOR_VIEW/ELEVATOR_QR/ELEVATOR_EXPORT/CLIENT_INVITE/CLIENT_USER_MANAGE/CLIENT_REPORT/CLIENT_EVALUATE` 等全部收回；`CLIENT_SIGNER` 同样收回 `ORDER_CREATE/ORDER_VIEW_OWN/ORDER_CONFIRM/ELEVATOR_VIEW/RECORD_VIEW/RECORD_SIGN/RECORD_REFUSE` 等内部码（CS 当前无 `RECORD_EXPORT`，有 `ORDER_CONFIRM` Y），改用 `client:sign/refuse`。客户矩阵只保留上列 `client:*`，并在 `PermissionMatrix` 中与内部矩阵物理分开。

**内部客户管理能力**：

- 内部开通/停用/重置/换绑客户账号使用 `useunit:write` / `client:edit` / `client:invite`（内部码），不是 `user:create`；
- 客户 `CLIENT_ADMIN` 默认不管理账号；如后续按单位开启 `client:user_manage`，仅可管理本单位 `CLIENT_SIGNER`，不得创建 `CLIENT_ADMIN`、不得跨单位、不得授予内部角色；
- 平台管理员通过内部只读端点查看客户数据，客户签字动作必须由 `principalType=CUSTOMER` 的账号完成；内部 token 调 `/client/**` 一律 `403`。

### 5.5 登录与工作台渲染

- `principalType=EMPLOYEE` → 按内部部门/角色渲染工作台；
- `principalType=CUSTOMER` → 客户工作台：**待签 / 我的电梯 / 记录 / 我的**；合同/移交/报修/评价/账号管理默认不下发；
- 同一手机号多个客户账号：登录后如命中多个单位，先显示**单位选择页**，选定后签发最终 token；选择前不返回任何单位业务数据；
- 账号 `GRACE`：客户工作台显示“合同已结束，仅可查看/下载/签署待签记录”提示；不渲染报修/评价/新数据入口；
- 客户不渲染维保/安装/平台域任何入口；
- 内部员工不渲染“客户签字”按钮；
- `/me/menus` 对客户只返回客户 tabs/quickActions；对内部员工不返回客户签字动作；
- 渲染面=权限面，但后端仍强校验（前端隐藏不作为授权依据）；
- 逐角色 tabs/quickActions 的现有映射见 `MiniappMenuService` / `config/menus.js`；V1.3 的 11 账号渲染矩阵继续作为内部角色基线，客户行按 V2.1 改为“待签 / 电梯 / 记录 / 我的”，报修/评价/合同/移交默认不下发。

## 6. 客户账号生命周期

### 6.1 开通

1. 内部有权限人员（平台管理员 / 维保经理 / 商务）创建 `use_unit` 档案；
2. 签维保合同（`maintenance_contract.use_unit_id`）；
3. 在该单位下开通客户账号：默认 1 个 `CLIENT_ADMIN`，手机号/初始口令；可选增开 `CLIENT_SIGNER`；**开通/增开均由内部人员操作，客户管理员默认无开通权**；
4. 同一手机号可在多个使用单位各开一个账号；同一单位内仅活跃账号手机号/openid 唯一（停用账号保留历史）；开通时做员工/客户跨表互斥校验；
5. 客户首次登录可绑定微信（可选），后续可微信一键登录；多单位账号微信登录后同样先选单位；
6. 客户登录后只看到本单位电梯/最新版本记录/待签。

### 6.2 账号管理

- **内部**：平台管理员/维保经理/商务在“使用单位详情”管理客户账号（开通/停用/重置口令/换绑微信/恢复宽限），不在“组织架构/员工”里操作；
- **客户 `CLIENT_ADMIN`**：默认**不管理账号**；`client:user_manage` 默认 DENY。如后续按单位开启，仅可管理本单位 `CLIENT_SIGNER`（开通/停用/重置），不能创建 `CLIENT_ADMIN`、公司员工或其他单位账号；
- **客户 `CLIENT_SIGNER`**：只能查看/签字/拒签，不管账号；
- 客户账号**不进入** `sys_employee`，不出现在员工列表、组织树、统计人数；
- 所有客户账号操作写 `sys_audit_log`：操作人、单位、账号、动作（开通/停用/重置/换绑/恢复）、时间；
- 重置口令、停用、换绑微信、变更角色/单位后清 `client_account.session_id` 并递增 `scope_version`，旧 token 立即 `401`。

### 6.3 合同结束 / 宽限期 / 停用

客户账号状态三态：

| 状态 | 触发 | 可做什么 | 会话 |
|---|---|---|---|
| `ACTIVE` | 该单位至少一份有效合同，且未人工停用 | 正常客户能力 | 正常 |
| `GRACE` | 该单位**全部**合同到期/终止，且未人工停用 | 只读本单位电梯/历史记录、下载 PDF、签/拒待签记录；不报修/不评价/不新增数据 | 可登录；旧 token 仍有效但按 GRACE 收敛 |
| `DISABLED` | 宽限期结束/人工停用/迁移停用 | 不可登录 | 立即清会话，旧 token `401` |

规则：

1. 宽限期 `grace_until` 取“合同结束日 + 30 天”与“最后一条待签记录归档日”中较晚者；无待签记录时只保留合同结束后 30 天；`GRACE` 期间允许读/下载/签待签，解决“账号已停用却要求窗口内签字”的矛盾；
2. 宽限期结束后转 `DISABLED`（自动停用写 `disabled_reason='GRACE_EXPIRED'`）；若仍有待签记录，平台管理员可按**账号**临时恢复 `GRACE`/延长 `grace_until`（限时、注明待签记录、留审计），不恢复报修/评价/新数据，不得批量恢复；
3. 合同续签/新合同生效 → 恢复 `ACTIVE`，但**仅限因宽限到期自动转 `DISABLED` 的账号**；人工停用（`disabled_reason` 以 `MANUAL` 开头）或迁移停用（`MIGRATED_`）不得被合同聚合自动恢复，必须内部显式启用；`status` 为权限事实源，`enabled` 仅作旧字段兼容（`ACTIVE/GRACE=1`、`DISABLED=0`）；
4. 状态由合同聚合驱动：合同新增/续签/终止时即时重算，另有每日扫描兜底（仅 `ACTIVE→GRACE`、`GRACE→DISABLED`；`grace_until` 到期转 `DISABLED` 并清会话）；扫描不从 `DISABLED` 自动回 `GRACE/ACTIVE`，跳过人工/迁移停用账号；写审计；
5. 历史记录按留存策略保留；`DISABLED` 客户不能登录下载，内部仍可查；如客户需长期留存，由内部导出交付或按 §6.3.2 临时恢复；
6. 客户账号不删除（审计留存），只停用/归档；
7. 重新启用/恢复 `DISABLED` 账号前，校验同单位活跃账号的手机号/openid 是否冲突；冲突时先处理旧账号，不允许同单位双活跃。

### 6.4 一个单位多个账号 / 多单位账号

- 默认：1 个 `CLIENT_ADMIN`；
- 可选：N 个 `CLIENT_SIGNER`（安全管理员换人/多人签字）；
- 所有账号同一 `use_unit_id`，数据范围一致；签字动作记录具体账号，不记“单位”笼统签；
- **同一手机号可在不同单位各有一个账号**；同一单位内仅活跃账号唯一（停用账号不占活跃唯一键）；员工与客户跨表手机号/openid 互斥，避免登录歧义；
- 登录：先验口令，命中多个单位账号时返回单位选择（短时 `selectionToken`），选定后签发最终 token；返回的账号列表只包含口令/openid 校验通过的账号，未验证前不得返回单位列表；
- 同一 openid 可绑定同一自然人在多个单位的客户账号；同一单位内唯一；微信登录命中多个账号时同样选单位；
- 一次记录只需一个客户账号签字，先签为准；多个 `CLIENT_ADMIN/CLIENT_SIGNER` 不要求会签。

## 7. 鉴权链与接口边界

### 7.1 鉴权链（六层）

```text
AuthInterceptor（JWT → principalType / empId 或 clientAccountId / useUnitId；查会话/账号状态）
  → RoleCatalog（角色 → 主体类型 / 内部部门 / 可用端）
  → PermissionMatrix（内部矩阵 / 客户矩阵，403）
  → ScopeResolver（内部部门/班组/本人 或 客户 use_unit_id，1403）
  → 业务归属校验（工单/记录/电梯归属，1403）
  → 客户记录状态/版本/字段门禁（PENDING_CLIENT_SIGNATURE + 最新版本 + 白名单）
```

### 7.2 Token 口径

内部员工：

```json
{
  "sub": "emp_xxx",
  "principalType": "EMPLOYEE",
  "roles": ["MAINT_TECH"],
  "scopeVersion": 5
}
```

客户：

```json
{
  "sub": "ca_xxx",
  "principalType": "CUSTOMER",
  "useUnitId": "uu_xxx",
  "roles": ["CLIENT_ADMIN"],
  "scopeVersion": 1
}
```

- 客户 token 不携带 `department` 作为权限依据；
- 内部 token 不携带客户 `useUnitId`（即使员工表有历史字段也不用于客户域）；
- 单账号单会话：员工 `session_id/session_admin`，客户 `client_account.session_id`；
- 角色/范围/单位变更 → `scopeVersion` 递增，旧 token 失效；`status` 每次请求从 `client_account` 复查，不能只信 token；`ACTIVE↔GRACE` 不强制失效（按新状态收敛），`DISABLED` 清会话并让旧 token `401`；
- 多单位登录：`POST /auth/login` 先验手机号+口令，`wx-login` 先验 openid；**只对校验通过的账号计数**——仅 1 个通过直接签发，多个通过才返回 `needUnitSelection=true` + 短时 `selectionToken` + 可选账号列表；`POST /auth/client/select-unit` 用 `selectionToken + accountId` 换取最终 token（仅 `purpose=LOGIN`）；忘记密码多单位使用独立 `purpose=RESET_PASSWORD` 短时 token，只用于重置、不能换登录 token；换 token 前重新校验账号 `status/use_unit_id/role_code/scope_version`，不复用旧权限；两类 token 均 5 分钟、一次性、只允许各自端点、不含业务权限；
- 客户 `GRACE` 状态 token 可读/下载/签待签，但拦截器拒绝报修/评价/账号管理等写入口。

### 7.3 路由边界

| 路径 | 内部员工 | 客户 |
|---|---|---|
| `/auth/login`、`/auth/wx-login`、`/auth/reset-password*`、`/auth/client/select-unit`、`/auth/me`、`/auth/change-password`、`/auth/logout`、`/auth/bind-wechat` | 允许 | 允许（只操作自身账号/会话） |
| `/auth/menus`、`/auth/bind-employee`、`/auth/bind-use-unit` | 按内部权限/旧兼容 | **一律 `403`** |
| `/me/menus` | 允许（内部菜单） | 允许（客户工作台菜单） |
| `/client/**` | **一律 `403`**（平台支持走内部端点） | 允许（`ACTIVE` 全量；`GRACE` 只读/下载/签待签） |
| `/orders/**`、内部 `/records/**`、内部 `/faults/**`、`/handovers/**`、`/filings/**`、`/admin/**`、`/users/**`、`/org/**`、`/stats/**`、`/audit/**` | 按内部权限 | **一律 `403`** |
| `GET /files/{id}?s=...` | 允许（签名校验） | **默认不走**；客户走 `/client/files/**`，确需 URL 时短 TTL + 签发前租户校验 |
| `POST /files/upload`、`/files/sts` | 按内部权限 | **`403`**；客户签名用 `/client/files` 或签字端点内联 |
| `/health` | 允许 | 允许 |
| `/unit/**`（旧门户） | 迁移期只读兼容 | 迁移期读写兼容（仅现有客户读/签/拒，不新增功能）；P4 后 `410`，新客户只走 `/client/**` |

- 客户令牌**业务端点**只允许 `/client/**`；认证/文件/健康检查按上表例外；P4 前旧 `/unit/**` 作为迁移兼容例外；内部端点在拦截器层直接 `403`，不依赖每个 Controller 记得校验；
- `/auth/me`/`/auth/change-password`/`/auth/logout` 客户分支必须按 `client_account` 处理（不查员工表、不允许改他人）；`/auth/me` 返回客户白名单字段，不返回内部角色/部门/权限码；`/auth/menus` 客户 `403`，客户菜单只走 `/me/menus`；
- `/client/**` 的单位 id 只从 token 取；请求体/query 带 `useUnitId` 时忽略或 `403`；
- 客户不能调用管理端登录（`client=admin` 直接 `403`）；
- 平台管理员通过内部 `/use-units/{id}`、内部记录只读端点支持客户，**不能调用客户签字接口**；`/client/**` 对内部 token 始终 `403`；支持访问要留审计；
- `UnitRecordController` 的 `/unit/records/**` 必须在 P3/P4 迁到 `/client/records/**`；不能只改 `UnitPortalController` 而留下签字端点。

### 7.4 审计

- `sys_audit_log` 新增 `use_unit_id`（内部审计为空，客户审计写租户 id），保留 `actor_type=EMPLOYEE|CUSTOMER`、`actor_id`；**不复用 `org_id`**，避免内部组织与客户租户混淆；
- 客户签字/拒签、跨单位越权尝试、客户账号开通/停用/重置/换绑/恢复宽限、文件越权访问都要留痕；
- 签字审计字段：记录 id、记录版本、单位 id、客户账号 id、签字人姓名（快照）、签字时间、结果（SIGN/REFUSE）、原因（拒签）；
- 客户签字/拒签审计与 `maintain_record.client_account_id/client_signer_name/client_signed_at` 双写；账号后续改名/停用不影响历史签字人展示。

## 8. 关键规则（V2.1 版）

| # | 规则 | 落点 |
|---|---|---|
| R1 | **使用单位是客户租户，不是部门**：不进组织树、不占编制、不参与部门互斥 | `RoleCatalog.principalTypeOf` + 组织树过滤 |
| R2 | 客户账号必须绑定唯一 `use_unit_id`；一个单位 1..N 个账号，默认 1 个 `CLIENT_ADMIN` | `client_account.use_unit_id NOT NULL` |
| R3 | 客户令牌**业务端点**只允许 `/client/**`；认证/文件/健康检查按 §7.3 例外；P4 前旧 `/unit/**` 兼容；内部接口对客户令牌 `403` | `AuthInterceptor` 路由白名单 |
| R4 | 客户数据域只认 token 的 `useUnitId`；请求体/query 单位 id 不采信 | `ScopeResolver` 客户分支 |
| R5 | 记录优先继承工单冻结的 `use_unit_id`；修订继承首版；过户不改历史归属；归档 PDF 用快照 | 快照列 + 查询/PDF/修订改造 |
| R6 | 客户只能签本单位 `PENDING_CLIENT_SIGNATURE` 最新版本；内部员工（含平台管理员）不得代签 | 签字端点主体类型 + 状态 + 版本校验 |
| R7 | 客户账号不进入员工/组织/统计列表；不能被授予内部角色 | `principal_type=EMPLOYEE` 过滤 + 角色分配校验 |
| R8 | 该单位全部合同到期/终止才进 `GRACE`；任一有效合同 `ACTIVE`；`GRACE` 只能只读/下载/签待签；结束转 `DISABLED` | 客户账号三态 + 合同聚合 |
| R9 | 内部“多单位可见”是工作范围；客户“跨单位可见”是越权；两套谓词分开 | `ScopeResolver` 双分支 |
| R10 | 越权一律 `403/1403` 且无副作用；签字/越权留审计 | 先校验后落库 + `sys_audit_log` |
| R11 | 客户能力仅 `client:*` 最小集；内部能力一律 DENY | 客户矩阵 |
| R12 | 同一单位内活跃账号手机号/openid 唯一；同一手机号可跨单位多账号，登录先验口令再选单位；员工/客户跨表互斥 | `UNIQUE(use_unit_id, active_phone/active_openid)` + 选择 token |
| R13 | 客户账号不删除，只停用/归档；签字记录不可改；签字人身份快照 | 留存/审计 + `client_signer_name` |
| R14 | 客户看不到内部工单/派单/统计/审计/移交/项目/合同金额/上报日志 | 路由边界 + 矩阵 + 字段白名单 |

### 9.2 迁移步骤

1. **建表/加列**（版本号按 P2→P3 顺序，不允许跳号/倒序）：
   - V47（P2）：`maintain_record` 增 `use_unit_id/use_unit_name/elevator_id`；`fault` 增 `use_unit_id/use_unit_name`；`work_order` 增 `use_unit_id/use_unit_name`（`work_order` 已有 `elevator_id`）；
   - V48（P3）：`sys_employee.principal_type` + `client_account` + `maintain_record` 客户签字人/拒签字段；
   - V49（P3）：`sys_audit_log.use_unit_id`、索引（`sys_employee.principal_type`、`maintain_record/fault/work_order.use_unit_id`、`sys_audit_log.use_unit_id`）与回填辅助表。
2. **迁出客户账号**：
   - 从 `sys_employee` 识别 `role in (CLIENT_ADMIN, CLIENT_SIGNER)` 或 `sys_user_role.role_code like 'CLIENT%'` 的账号；
   - **先去重**：同一 `use_unit_id + 手机号` 若有多条（V36 同时插 `CLIENT_ADMIN`/`CLIENT_SIGNER`），合并为一个账号；优先 `CLIENT_ADMIN`，保留最新口令/openid；冲突清单人工处理；
   - 用 `sys_user_role.org_id`（`use_unit.id`）作为 `client_account.use_unit_id`；无锚点/锚点非 `use_unit` 的记录进人工清单，不猜；
   - 拷贝姓名/手机号/BCrypt 口令/openid/`enabled`；旧 `enabled=0` 保持 `DISABLED`（`disabled_reason='MIGRATED_DISABLED'`，不因待签自动恢复）；旧启用账号再按合同聚合重算：有有效合同→`ACTIVE`，全部结束→`GRACE`（`grace_until` 按 §6.3），无合同且无待签→`DISABLED`；
   - 旧 `sys_employee` 行不删除，标 `principal_type='CUSTOMER_ARCHIVED'`、`enabled=0`、`department=NULL`、清 `session_id/session_admin`；保留审计；
   - 删除/停用其 `sys_user_role` 客户角色行；`GET /employees`、组织树、统计统一过滤 `principal_type='EMPLOYEE'`。
3. **旧 `UNIT_ADMIN` / `use_unit.account` 账号**：
   - V41 未迁移的 `use_unit.account` 直接写入 `client_account`（`use_unit_id` 已知），并按上一步同一规则重算 `status`；
   - 已迁移到 `sys_employee` 的按上一步迁出；
   - 与 V41 已迁移账号按 `use_unit_id + 手机号` 去重；保留最新口令/openid；旧行停用不删；
   - **`UnitAccountUnifyService` 必须在迁移前停用或加 `account_migrated` 幂等保护**，不得在启动时把客户账号重新并入 `sys_employee`；
   - 旧 `use_unit.account/password_hash/openid` 列保留只读，生产清库时再评估删除。
4. **快照回填**：
   - 先建“过户嫌疑清单”：凡 `biz_elevator_change`、审计日志、合同变更中出现过使用单位变更的电梯，其全部历史记录**不自动回填**，进人工核对；
   - 无过户记录的电梯：`maintain_record` 按 `work_order.elevator_id` 或 `elevator_code` 关联 `elevator.use_unit_id`；`fault` 同上；`work_order` 按 `elevator_id`；
   - 有工单的优先用“工单创建时间 + 当时合同/归属证据”；无法确定置 `use_unit_id=NULL`，客户门户不展示；
   - 输出清单字段：记录 id、电梯编码、当前单位、候选单位、证据、置信度、处理结果；人工签字确认后才能回填；
   - `use_unit_name` 按回填后的单位名称写入；无法确定的留空，PDF 内部标注，客户不展示。
5. **组织/范围清理**：
   - 新组织树只渲染 `COMPANY/DEPT/TEAM`；`UNIT` 节点不再作为部门；后端拒绝新建 `UNIT` 节点；
   - `sys_role_scope` 的 `CLIENT_*` 行迁移后清理；客户范围只取 `client_account.use_unit_id`，不再读 `ORG_FLAT`；
   - `sys_user_role` 的客户行迁出后删除/停用；`user_type=UNIT` 只作历史兼容，不再参与权限。
6. **代码切换**：
   - 登录：先查员工，再查 `client_account`；多单位命中返回 `selectionToken`；`wx-login`/`reset-password-by-wechat`/`bind-wechat` 双主体；
   - 令牌：客户 token 带 `useUnitId`；内部 token 不带客户单位；`status` 每请求复查；
   - 拦截器：客户 token 业务白名单 `/client/**`；`GRACE` 收敛为只读/下载/签待签；
   - 客户服务：`UnitPortalService` + `UnitRecordService` → `ClientPortalService` + `ClientRecordService`，查询按 `record.use_unit_id`、最新版本、允许状态；
   - 管理端：组织树移除使用单位；客户账号管理移到使用单位详情；人员列表过滤 `principal_type=EMPLOYEE`；
   - 小程序：客户工作台只渲染待签/电梯/记录/我的；多单位先选单位。
7. **部署顺序/回滚**：
   - P1 可先上“收回内部能力/签字状态门禁/字段白名单/客户管理员默认关闭”，旧 `/unit/**` 保留兼容；对尚未迁出的 `CLIENT_*` 员工账号加临时门禁（只允许 `/unit/**`，禁管理端/内部工作台），P3 迁出后删除；
   - P2 上快照列、回填、查询/PDF/修订改造；客户门户对 `use_unit_id=NULL` 记录隐藏；
   - P3/P4 同批上线：`client_account` 迁移、登录选择单位、`/client/**`、文件鉴权代理、管理端/小程序切换；用开关控制，避免 P3 单独切登录导致旧页面断链；旧 `/unit/**` 不随 P4 立即 `410`，保留兼容窗口（建议≥30 天或旧版本占比达标），窗口结束再下线；登录响应是破坏性变更，旧版小程序需强制更新或按 `clientVersion` 保留旧 token/旧路由，不能只保留 `/unit/**`；
   - 迁移期不做双写；旧表/旧列不删；脚本幂等、失败不写半成品；生产清库是独立人工步骤，不在本次方案内。

### 9.3 迁移风险

| 风险 | 处理 |
|---|---|
| 旧客户员工未归档，继续出现在员工/组织/统计 | `sys_employee.principal_type=CUSTOMER_ARCHIVED` + 所有员工查询统一 `principal_type='EMPLOYEE'`；迁移后加断言 |
| P1/P2 未迁出的 `CLIENT_*` 员工账号仍可进内部工作台 | P1 临时门禁：只允许旧 `/unit/**` 客户门户，管理端/内部工作台拒绝；P3 迁出后删除该分支；加回归用例 |
| V36 同时插入 `CLIENT_ADMIN`/`CLIENT_SIGNER`，迁移出两个账号 | 按 `use_unit_id + 手机号` 去重；优先 `CLIENT_ADMIN`；保留最新口令/openid；冲突清单人工处理 |
| `UnitAccountUnifyService` 启动时把客户账号重新并入员工 | 迁移前停用或加 `account_migrated` 幂等保护；加回归测试，禁止再写 `sys_employee` 客户行 |
| 客户账号手机号/openid 与员工冲突 | 员工/客户跨表互斥；迁移前输出冲突清单，人工决定保留哪个主体；不自动覆盖 |
| 同一单位内手机号被停用账号占用，新人无法开通 | 唯一键只约束 `ACTIVE/GRACE`（生成列 `active_phone/active_openid`）；停用账号保留历史但不阻塞 |
| 同一手机号多单位登录歧义 | 先验口令再返回单位选择；`selectionToken` 5 分钟、一次性、只允许 `/auth/client/select-unit`；不泄露未匹配单位 |
| 历史记录过户导致快照错误 | 先建过户嫌疑清单；有 `biz_elevator_change`/审计/合同变更的电梯历史记录不自动回填，人工核对；无法确定置 `use_unit_id=NULL`，客户门户不展示 |
| 归档 PDF 按电梯当前单位回查出错 | `RecordLifecycleService.archive()` / `RecordPdfService` 使用 `record.use_unit_id/use_unit_name` 快照；NULL 时内部标注“归属待核对”，客户不展示 |
| 修订版本丢失租户/电梯快照 | `WorkDomainService.amend()` 复制首版 `useUnitId/useUnitName/elevatorId`；v1 签字保留，v2 重新签 |
| 客户看到旧版本并重复签字 | 列表/详情只返回记录链最新版本；旧版本仅内部/审计可见；签字前再校验“无后续版本” |
| 客户签字绕过复核/双签/状态门禁 | 签字/拒签统一先校验 `principalType + useUnitId + lifecycleStatus + confirmStatus + 最新版本 + 账号状态`；失败不落库 |
| 客户详情泄露上报报文/GPS/shareToken/平台 ID | 客户专用 `toClientMap()` 白名单；加字段级回归断言，禁止复用内部 `toMap()` |
| 历史 `refuse_reason` 同时承载内部复核退回/客户拒签，语义混合 | 迁移不回填 `client_refuse_reason`；旧记录客户详情不回显拒签原因，内部按原字段查看；新拒签写独立 `client_refuse_reason`，不覆盖内部 `refuse_reason` |
| 客户 A 拿到 B 的文件 URL | 客户文件走 `/client/files/**` 鉴权代理；必须用 URL 时短 TTL + 签发前校验 `record/fault.use_unit_id` + 签名绑定 `useUnitId`；不把签名写日志 |
| 合同结束立即停用，待签记录无法签 | `ACTIVE/GRACE/DISABLED` 三态；全部合同结束进 `GRACE`（30 天/至归档），宽限内可读/下载/签待签；结束转 `DISABLED` |
| 客户管理员越权开通/停用账号 | `client:user_manage` 默认 DENY；账号操作由内部 `useunit:write/client:edit/client:invite` 执行；客户管理员不得创建 `CLIENT_ADMIN` |
| 平台管理员误调客户签字接口 | `/client/**` 对内部 token 一律 `403`；平台支持走内部只读端点，签字必须客户账号 |
| 客户令牌误访问内部端点 | 拦截器白名单 + 回归测试；不依赖 Controller 自觉；旧 `/unit/**` 仅迁移期兼容 |
| 统计/组织树把客户算进员工 | 员工查询统一 `principal_type=EMPLOYEE` 过滤；组织树只渲染 COMPANY/DEPT/TEAM；加回归断言 |
| 客户角色被内部“新建人员”下拉选中 | `assignableRoles` 按 `principalType=EMPLOYEE` 过滤，不能只排除 `department=UNIT`；客户角色 `department=null` 仍不得可选；加接口断言 |
| 客户签字误触发 2.6 重报 | `onClientSigned` 只置 `SIGNED`/归档，不注入上报服务；加“签字后 `reg_upload_log` 无新增”测试 |
| P3 单独切登录/门户导致旧页面断链 | P3/P4 同批上线或使用开关；P1/P2 保留 `/unit/**` 兼容；切换前跑全链路回归 |
| P4 立即 410 导致旧版小程序客户无法签字/下载 | P4 后保留 `/unit/**` 兼容窗口（建议≥30 天或旧版本占比达标），新客户只走 `/client/**`；窗口结束再 410，并提前公告/强制更新 |
| P3 登录响应变更导致旧版小程序无法登录 | 发布前设最低版本/强制更新；若要兼容窗口，`AuthController` 按 `clientVersion` 返回旧 token/旧路由，不能只保留 `/unit/**`；旧版只允许读/签，不开放新功能 |
| 审计把客户租户写进 `org_id` | `sys_audit_log` 新增 `use_unit_id`；内部审计为空，客户审计写租户 id；不复用 `org_id` |

## 13. 取舍与风险

1. **不恢复双令牌**：一个登录入口、一个 token，主体类型区分；避免前端两套会话。
2. **客户账号独立表 vs 员工表加类型**：选独立表，彻底避免客户出现在员工/组织/统计；代价是 V41 迁移要迁出，旧 `sys_employee` 行保留并标 `CUSTOMER_ARCHIVED`，不删除审计。
3. **同一手机号多单位：按单位多账号 + 登录选单位**，不做“一个账号多单位”。后者需要 `client_account_unit`、按单位角色和 token 切换，复杂度和越权面更高；前者保持“一个账号一个 `use_unit_id`”的简单边界。代价是登录多一步选择，已用短时 `selectionToken` 控制。
4. **合同不切电梯**：客户按单位看全部电梯；合同只控制账号启停。若未来要按合同隔离，需增加 `contract_id` 到电梯/记录，另行设计。
5. **合同结束不立即停用**：全部合同结束先 `GRACE`（30 天/至归档），解决“待签记录未签但账号已停用”的矛盾；宽限结束才 `DISABLED`，临时恢复按账号单条操作并审计。
6. **客户管理员默认不管理账号**：开通/停用/重置由内部人员做，避免客户侧自助扩权；`client:user_manage` 保留为未来按单位开启的开关，默认 DENY。
7. **合同/移交默认不可见**：客户最小面只做电梯/记录/签字/下载；合同金额（即使只读）和移交单先收回，确有业务再单开能力，避免“最小权限”名不副实。
8. **客户签字只认状态+版本**：`PENDING_CLIENT_SIGNATURE` + 最新版本 + `confirm_status=PENDING`，不再只看 `confirmStatus`；签字/拒签不触发 2.6，避免把客户确认误当监管上报。
9. **记录快照优先于当前归属**：记录继承工单、修订继承首版、PDF 用快照；过户后历史仍归原单位。代价是客户“电梯列表按当前、记录列表按历史”可能不一致，UI 需明确说明。
10. **客户文件优先鉴权代理**：`/client/files/**` 可真正校验租户；必须用 `<image>` 直链时退回短 TTL 签名（≤10 分钟、绑定 `useUnitId`），并承认“已泄露 URL 仍是能力链接”的边界，签发前绝不跨租户。
11. **历史回填不静默猜**：有过户嫌疑的电梯必须人工核对；无法确定 `use_unit_id=NULL`，客户不展示、内部保留。比“按当前归属批量填”慢，但避免把 A 单位记录交给 B。
12. **平台管理员不代签**：支持可读，但签字必须客户账号；满足监管真实性要求。
13. **客户账号不删除**：停用/归档保留审计；生产清库另议。
14. **内部多角色并集不变**：客户账号不参与；避免把客户角色混进员工角色集。
15. **风险**：V2.1 会改动已上线的 V41 账号统一口径；迁移脚本、登录/多单位选择、会话、菜单、管理端组织树、小程序客户工作台、文件/PDF 要同步回归，不能只改后端矩阵。P3/P4 必须同批或开关成对切换；旧 `/unit/**` 保留兼容窗口，避免旧版小程序客户在 P4 当天失去签字/下载能力；登录响应变更需最低版本/强制更新或按 `clientVersion` 兼容旧 token。
