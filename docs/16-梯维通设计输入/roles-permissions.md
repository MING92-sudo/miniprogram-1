# 梯维通 · 角色与权限矩阵 V1.3

> 适用范围：微信小程序（一个登录入口）+ 后台管理端（规格见 `admin-spec.md`，可运行原型见 `admin/`；平台管理员的项目 / 合同台账走后台管理端，不做小程序页面）。  
> 核心原则：**账号不选角色、后台定角色；前端只隐藏、后端必校验；权限 = 功能 + 数据范围 + 字段可见性。**

---

## 0. 一页纸结论

- 共 **9 个角色**：安装部 3 个、维保部 3 个、使用单位 2 个、平台 1 个；一人可多角色，**登录页不选角色**。
- 安装移交职责分离：**项目负责人发起 → 资料员上传 → 安装主管审核 → 维保主管接收 → 维保员验收 → 双方主管签字**。
- 资料员**不能**发起/提交移交单；维保人员**不能**接收/指派；使用单位管理员默认不能代签，**兼任签字人角色后可签署**，签名独立留痕。
- **维保部经理为正式角色**，数据范围为**全部维保项目**，负责合同、跨项目调度、绩效与归档后修订审批。
- **维保记录必须双人签字**：主检人 + 配合人，两名不同的维保人员；双签完成后才能发起使用单位签字。
- 使用单位组织为**单级**，不做“集团—项目”两级。
- 合同金额默认对维保主管脱敏，仅维保经理 / 使用单位 / 平台可见。
- 权限 = 功能权限 + 数据范围 + 字段脱敏；使用单位仅见本单位，维保人员仅见本班组/本人，安装部仅见本项目。
- 跨项目支援使用**限时授权**，不长期扩大数据范围。
- 已归档签名不可修改；修订需“维保经理 + 平台”双人确认并生成新版本。
- 前端按后台返回的 `menus / tabs / actions` 渲染，**后端每个接口都校验**；前端隐藏不等于权限。
- §4 的 **71 个权限码已逐码闭合归属**：28 个由小程序路由直接承载，其余 43 个按「Web 管理端承接 / 小程序页内动作 / 系统自动执行 / 本期明确不做」四类处置，见 §12。
- 按钮不可用分**两档门控**（§8.4）：永久权限拒绝用原生 `disabled`，临时前置条件未满足用 `aria-disabled` + 保持可聚焦 + JS 拦截。**两档并存是设计，不是实现不一致。**

## 1. 角色定义

| 代码 | 角色 | 归属 | 账号开通方 | 典型人员 | 默认数据范围 |
|---|---|---|---|---|---|
| `INST_CLERK` | 安装部资料员 | 安装部 | 安装部主管 | 资料员、文控 | 被指派的安装项目 |
| `INST_PM` | 安装部项目负责人 | 安装部 | 安装部主管 | 项目经理、现场负责人 | 本人负责的安装项目 |
| `INST_MGR` | 安装部主管 | 安装部 | 平台管理员 | 安装部经理、技术负责人 | 本安装部及下级 |
| `MAINT_TECH` | 维保人员 | 维保部 | 维保主管 | 维保工、急修工、主检/配合人 | 本班组 + 本人派工/所辖电梯 |
| `MAINT_SUP` | 维保主管 / 调度 | 维保部 | 维保经理 / 平台 | 维保站长、调度 | 本维保项目部 |
| `MAINT_MGR` | 维保部经理 | 维保部 | 平台管理员 | 维保部负责人、区域经理 | 全部维保项目 |
| `CLIENT_ADMIN` | 使用单位管理员 | 使用单位 | 平台管理员 / 维保主管 | 物业经理、设备主管 | 本单位全部电梯 |
| `CLIENT_SIGNER` | 使用单位签字人 | 使用单位 | 使用单位管理员 / 平台 | 值班经理、物业负责人 | 本单位 + 被指派待签单据；可由管理员兼任 |
| `PLATFORM_ADMIN` | 平台管理员 | 平台 | 平台 | 运维、实施 | 全量（运维用途，不参与业务签字） |

说明：

- **一人可多角色**，例如维保主管同时是维保人员、安装部主管同时是项目负责人。
- **使用单位签字人必须由使用单位书面授权**；管理员可兼任，但需在开通 / 授权时由平台或维保主管同时授予 `CLIENT_SIGNER`，不建议自行加签。
- `PLATFORM_ADMIN` 可排查数据，但**不能代替业务方签字**；敏感操作需二次确认并写审计日志。
- **维保部经理为正式角色**：合同续签、跨项目调度、归档后修订必须由其审批；平台不可代签。
- **使用单位管理员可兼任签字人**：需同时授予 `CLIENT_SIGNER`，签字时按签字人角色留痕；管理员身份本身不产生签字权。
- 使用单位组织保持**单级**：一个使用单位一个组织，不设区域管理员层级。

## 2. 账号与登录规则

1. **一个手机号 = 一个账号**，绑定微信 `openid`；同一账号可拥有多个角色。
2. 登录页**不提供角色选择**。登录成功后后台返回 `roles + permissions + dataScope`，前端据此渲染工作台。
3. 首次使用：由管理员生成**邀请码 / 组织二维码**，员工扫码加入对应单位，管理员审批后激活。
4. 多角色用户：默认进入优先级最高的工作台（维保 > 安装 > 使用单位），可在「我的 → 切换工作台」切换；**登录页不出现切换**。
5. 账号状态：`待激活 → 正常 → 停用 / 离职`。停用后立即吊销 token，未完成工单转交主管。
6. 使用单位签字提醒走**微信订阅消息**，不依赖短信；小程序内保留待办入口。
7. 使用单位管理员可同时拥有 `CLIENT_SIGNER`：待办合并展示；签字时按签字人角色校验，审计记录同时保留两个角色。

### 6.4 使用单位签字链路

1. 维保人员提交记录单 → 主管复核（可配置）。
2. 系统生成**一次性签署任务**，微信订阅消息通知使用单位签字人。
3. 签字人打开记录单，核对项目、异常整改、现场照片。
4. 勾选确认 → 手写签名 → 服务端写入时间戳、GPS、设备指纹。
5. 生成 PDF + 文件哈希，双方签署完成后自动归档并通知维保人员/主管。
6. 拒绝签署必须填写原因，记录单退回维保人员处理，重新走签字链路。

## 7. 多角色、调岗与离职

| 场景 | 规则 |
|---|---|
| 一人多角色 | 权限取并集；数据范围逐条判断；登录后进入默认工作台，可在「我的」切换 |
| 临时支援 | 由主管发起**限时授权**（起止时间 + 范围 + 权限点），到期自动回收，全程审计 |
| 调岗 | 停用旧角色、授予新角色；未完成工单转交；历史签名与记录保留 |
| 离职 | 账号停用、token 立即失效、待办转交；保留审计与电子签名证据 |
| 代签 | **禁止无授权代签**。签字必须由 `CLIENT_SIGNER` 完成；管理员可兼任该角色，但签名按签字人身份留痕；未兼任时不能代签 |
| 管理员兼任签字人 | 同一账号拥有 `CLIENT_ADMIN` + `CLIENT_SIGNER`；待办合并，签字独立留痕；不得转授签字权 |
| 双人维保签字 | 每条维保记录必须由主检 + 配合人两名**不同账号**的维保人员签字；同一账号不能兼任两个角色；双签后才能送使用单位 |
| 外包维保 | 仅授予 `MAINT_TECH` 且限定项目 / 电梯；禁止导出与跨项目查看 |

> 限时授权的字段与校验以 `admin-spec.md:171`（字段）与 `admin-spec.md:173`（校验：有效期 1–30 天、`end > start`、权限点至少 1 项）为准；本文件不重复定义数值区间。

## 8. 技术落地建议

### 8.1 数据模型

| 表 | 用途 |
|---|---|
| `sys_user` | 账号、手机号、openid、状态、所属组织 |
| `sys_org` | 公司 / 安装部 / 维保部 / 使用单位（树形） |
| `sys_role` / `sys_permission` | 角色与权限点 |
| `sys_user_role` | 用户-角色（支持多角色） |
| `sys_role_permission` | 角色-权限点 |
| `sys_role_scope` | 角色-数据范围（org / project / team / self） |
| `biz_project` / `biz_elevator` | 项目与电梯台账 |
| `biz_handover` / `biz_handover_doc` | 移交单与资料 |
| `biz_record` | 记录主表：主检人、配合人、双签时间、PDF 与哈希 |
| `biz_record_item` | 点检项、实测值、照片、异常说明 |
| `biz_order` / `biz_order_log` | 急修 / 报修工单与流转日志 |
| `biz_signature` | 签名图、PDF、哈希、时间戳、GPS |
| `sys_audit_log` | 登录、授权、签字、退回、导出、作废 |

`sys_audit_log` 的字段与采集口径见 §13.4。

### 8.2 权限校验

- 权限码规范：`<domain>:<action>`，例如 `handover:create`、`record:sign_request`、`order:dispatch`。
- JWT 建议携带：`sub`、`orgId`、`roles`、`perms`、`scopeVersion`；角色变更后版本号递增，旧 token 失效。
- **每个 API 服务端校验**：权限点 + 数据范围 + 单据状态，三者同时满足；前端隐藏不作为安全边界。
- 数据范围统一由 `scope` 解析器生成查询条件，禁止各接口手写 `if role === ...`。
- 登录返回 `menus / tabs / homeCards / actions`，前端只负责渲染；避免角色判断散落在页面里。
- 导出类接口单独鉴权并重新脱敏；审计日志不可删除。

### 8.3 微信侧

- `wx.login` → `openid`；手机号通过 `getPhoneNumber` 获取（需企业主体与相应权限），验证码登录兜底。
- 角色只从服务端读取，**绝不接受客户端传入角色**。
- 使用单位签字提醒使用订阅消息；一次性签署任务带随机 token，防转发、防重放。
- 签名页展示记录单版本号与哈希前 8 位，签署前可核对。

### 8.4 不可用控件的两档门控

「按钮不可用」有两种不同语义，实现方式不同。**两档并存是设计决定，不应被当作实现不一致**（§10 决策 17）。

| 档位 | 语义 | 实现 | 是否可聚焦 | 原型对应 |
|---|---|---|---|---|
| **永久权限拒绝** | 当前角色**没有**该权限码，且不随页内状态改变 | 原生 `disabled` + `title` 说明缺失的权限码 + 可见理由文案 | **否**（无权限的操作不应进入 Tab 顺序，符合预期） | 屏 03「新增外接项目」缺 `project:edit`；屏 08「导出台账」缺 `elevator:export` |
| **临时前置条件未满足** | 角色**有**权限码，但单据状态或页内前置条件未满足 | `aria-disabled="true"` + **保持可聚焦** + JS 在捕获阶段拦截 click 与 Enter / Space + 可见理由文案 | **是**（必须可聚焦，否则用户取不到禁用理由） | 屏 11「确认签署」由同意勾选框门控 |

约定：

1. 第二档必须保持可聚焦：原生 `disabled` 元素不派发事件，屏幕阅读器用户 Tab 不到按钮、也听不到禁用原因。
2. 第二档的 JS 拦截发生在**捕获阶段**（同时拦 click 与 Enter / Space），因此后端校验仍是唯一安全边界。
3. 无 JS 环境（原型脚本被禁用）下，第二档由两条 CSS `:has()` 规则兜底（遮罩 + 提示文案），原型已实现。
4. 第一档不得滥用：只有"权限永久缺失且无需解释交互路径"时才用原生 `disabled`；有权限但状态未满足的一律走第二档。
5. 判定依据分别是**权限码**（第一档）与**状态 / 前置条件**（第二档），不得混用同一档表达另一种语义。
6. **实测锚点**（V1.3 取证，说明两档在原型里是真实存在的两种实现而不是文档设想）：第一档共 3 处原生 `disabled`，分别是 `index.html:1472`（屏 03「新增外接项目」缺 `project:edit`）、`index.html:2062`（屏 08「导出台账」缺 `elevator:export`）、`index.html:2713`（屏 16 对照面板的「禁用态示例」，其 `title` 本身就要求写出「缺哪个权限码 / 由哪个角色开通」）。第二档的运行时实例是屏 11「确认签署」：`aria-disabled` 由脚本按同意勾选框状态加卸（`index.html:2819-2839`），`click` 与 `keydown` 两个监听都以捕获阶段注册，勾选后自动移除；无 JS 时由两条 `:has()` 规则承担视觉禁用与理由文案（`index.html:587-589`）。
7. 一处需要明说的边界（避免被当成不一致）：屏 03 的「续签提醒」与「处理」是 `.link` 形态（`index.html:1439` / `index.html:1468`），语义上属于**永久权限拒绝**（缺 `contract:edit`），但实现用了第二档的 `aria-disabled`。原因不是错误，而是第 1 条判据优先：链接形态紧贴说明卡，必须让键盘与读屏能取到「续签归后台管理端办理」这句理由。因此两档的**选择判据是可聚焦性需求，不是权限码与状态的词性**；表格里的「永久 / 临时」是最常见组合，遇到 `.link` 这类需要解释的入口时按第 1 条走第二档。后台管理端侧对应处置见 `admin-spec.md:190` 与本文 §12 `contract:edit` 行。

## 9. 验收用例

| # | 场景 | 预期 |
|---|---|---|
| 1 | 资料员尝试发起移交单 | 无入口；直接调用 API 返回 403 |
| 2 | 项目负责人提交审核，资料缺 1 类 | 被拦截；提示缺件；可走容缺审批 |

| 5 | 使用单位签字人访问其他单位记录单 ID | 返回 404/403；不泄露数据是否存在 |
| 6 | 使用单位管理员未兼任签字人时尝试代签 | 被拒绝；需授予 `CLIENT_SIGNER` |
| 7 | 维保人员查看非本人电梯档案 | 不在数据范围；列表不出现，直接访问被拒绝 |
| 8 | 安装部用户查看维保合同金额 | 金额脱敏或不可见 |
| 9 | 已归档记录单尝试修改 | 驳回；需维保经理 + 平台发起修订，生成新版本 |

## 11. 实现默认值

## 13. 小程序侧补充规格（P2-10）

通用规格已由 `admin-spec.md` 维护，本章**只写小程序侧差异 + 交叉引用**，不重复定义、不新增数值。

### 13.1 四态

通用规格见 `admin-spec.md` §7（`admin-spec.md:341`，四态表 `admin-spec.md:345-348`）。小程序侧差异：

| 态 | 小程序实现 | 与后台侧的差异 | 原型对照 |
|---|---|---|---|
| 无权限 | 路由 `/pages/403/index`，关键参数**只有 `from?`**（`routes-and-menus.md:127`） | 后台 403 页会列出**所需权限码 + 允许角色**（`admin-spec.md:348`）；小程序 403 **不回显目标单据 id**，以维持 §9 用例 5 的「不泄露数据是否存在」 | 屏 12 |
| 空态 | **双分支**：① 无数据（引导创建 / 引导接单）② 筛选无结果（引导清空筛选） | 后台侧仅定义了筛选无结果分支（`admin-spec.md:345`） | 屏 13 |
| 加载态 | 骨架屏（非转圈占位） | 后台骨架时长 220ms 与「分页/排序本地瞬时不显示」（`admin-spec.md:346`）为 Web 口径，小程序不套用该毫秒数 | 屏 14 |
| 失败态 | 接口失败卡 + 「重试」 | 后台用「模拟异常」开关触发（`admin-spec.md:347`）；小程序由真实请求失败驱动 | 屏 15 |

范式屏 12–16 **不新增业务路由**，只是上述规格的可视化对照，对应关系见 `routes-and-menus.md` §10。

### 13.2 字段校验

通用规格见 `admin-spec.md` §5（`admin-spec.md:306`），表单校验口径在 `admin-spec.md:315`（失焦 + 提交双校验、错误文案在字段下方、必填星号）。小程序侧差异：

1. 校验时机同为**失焦 + 提交**，但事件源是小程序组件的 `blur` 与表单 submit；错误文案渲染在字段下方，必填项在标签上有必填标记。
2. 规则**按行引用、不重复定义**：
   - 手机号 `^1[3-9]\d{9}$` → `admin-spec.md:264`
   - 故障描述 ≥5 字、录音编号 `^REC-\d{4,6}$` → `admin-spec.md:264`
   - 邀请码有效期 1–30 天 → `admin-spec.md:173`；默认 7 天 → §4.6（`invite:manage` 行）
   - 限时授权 `end > start` 且权限点 ≥1 → `admin-spec.md:173`（依据 §7 限时授权）
   - 容缺受理理由必填 → §4.1（`handover:submit` 行）+ 屏 02 / 屏 09 呈现
3. 签字前置校验：勾选确认未完成时，「确认签署」走 §8.4 **第二档**（`aria-disabled` + 可聚焦 + 捕获阶段拦截），不得改用原生 `disabled`。
4. 数值型默认值（SLA 分钟、token 有效期等）源文档未给出的，一律按 §13.5 写「由平台配置下发」。

### 13.3 列表排序 / 筛选 / 分页

通用规格见 `admin-spec.md:314`（列排序三态、关键字搜索、多筛选器、分页 8/16/32、行多选批量、空态、加载骨架）。小程序侧差异：

1. 分页形态为**下拉刷新 + 触底加载更多**，不用页码器；后台的「默认 8 条/页」是 Web 口径，不适用于小程序。
2. 筛选用 chips 多选，语义等价于后台的多筛选器；chips 清空即空态第二分支（§13.1）。
3. 列表不做批量操作条（无多选全选），需要批量的场景留在后台管理端（`admin-spec.md:314`）。
4. 承载列表的 `.phone` 容器必须完整可滚动、不裁切内容。**当前原型有 6 个屏内元素存在 14–46px 裁切**，属实现缺陷；因本批 index.html 逐字节冻结未修，登记在 §14 R1。
