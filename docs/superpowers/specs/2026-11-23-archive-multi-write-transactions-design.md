# 档案管理多写事务边界设计

## 目的

修复 Task 5 台账 deferred 的档案管理多写事务缺口，确保一次业务操作中的数据库写入同成同败，失败不留半成品。

## 范围

- `createEmployee`：员工主记录与主角色行原子写入。
- `updateEmployee`：员工主记录、显式清 NULL、主角色行变更原子写入；班组审计继续 best-effort。
- `deleteUseUnit`：清维保记录客户引用、删客户账号、删使用单位原子完成。
- `batchGeo`：保留单条业务错误进入 `failed[]` 的部分成功契约；未捕获数据库/系统异常回滚本批此前写入。
- `deleteElevator` 当前只有单次删除，不做多写改造；校验—删除竞态不在本任务内。

## 非范围与约束

- 不改变公开方法签名、接口路径、响应结构、权限和业务校验。
- 不做全项目事务重构，不引入自动重试、外部平台调用或 Flyway 迁移。
- 未经用户明确要求不提交 Git。

## 方案

采用现有 Spring `@Transactional` 公共 Service 入口与事务代理测试，不重构写入流程。另用以环境变量启用的隔离 MySQL 测试执行 Flyway 迁移并通过 mapper 代理注入后续写失败，直接断言实际行状态。

未采用全项目扫描，因为会扩大既有任务边界；未采用 `batchGeo` 每项独立事务，因为会改变数据库异常时整批失败的原子性目标。

## 验收

- 各链路第二写/后续写失败经过真实事务代理触发 rollback，成功路径 commit。
- 隔离 MySQL 中员工、角色、单位、客户账号、记录引用与坐标在失败后保持原状。
- `batchGeo` 合法项与业务非法项混合时仍返回并保存部分成功；审计失败不阻断员工更新。
- `mvn -f backend/pom.xml test` 全量通过；真实 MySQL 不可用时必须明确报告未执行，不得声称完成该项验收。
