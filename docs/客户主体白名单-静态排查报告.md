# 客户主体白名单 — 全量静态排查报告

> 执行时间：2026-11-20 08:30—09:30（GMT+8）
> 起因：小程序实测发现 BUG-1（`/me/menus` 对客户返回 401 → 前端清登录态 → 客户登录后被踢回登录页）、BUG-2（`ElevatorController.unitAnchor` 用旧 `sys_user_role` 口径，客户全线失效）。两者同属一类问题：**客户令牌被白名单放行，但端点内部只认员工主体**。本报告把这一类问题一次性扫清，不再逐个撞。

## 一、方法

排查基准是鉴权拦截器里的白名单函数 `AuthInterceptor.clientAllowed(uri, method)`——它决定**客户令牌能到达哪些端点**。白名单分四类：

| 类别 | 规则 |
|---|---|
| 前缀全放 | `/client/**`、`/unit/**` |
| 精确端点 | `/me/menus`、`/auth/me`、`/auth/change-password`、`/auth/bind-wechat`、`/auth/client/me`、`/auth/client/change-password`、`/auth/logout`、`/health` |
| 仅 GET | `/files/*`、`/elevators`、`/elevators/by-code`、`/elevators/{id}/profile` |

工具：`scripts/e2e/scan-customer-principal.js`（可复跑，退出码非 0 表示有高风险项）。

判定逻辑：

1. 解析全部 `@RestController`（**含 `auth/` 包，不只是 `controller/` 包**——首版只扫 `controller/`，把 `AuthController` 整体漏掉，导致「白名单里的 `/auth/*` 全是死规则」这种假结论）；
2. 组装每个端点的完整路径，筛出白名单可达的；
3. 扫描 handler 方法体：**员工专属信号**（`currentUser(` / `empId(` / `employeeMapper` / `SysUserRole` / `userRoleMapper`）与**客户分支信号**（`CUSTOMER` / `ATTR_UNIT_ID` / `ATTR_PRINCIPAL_TYPE` / `clientAccount` / `isClient` / `isCustomerRequest` / `portalRoles`）；
4. 只有员工信号、没有客户信号 → 高风险。

## 三、修复的 3 个缺陷

三个端点都在白名单内，都能被客户令牌调用，但内部第一句就是 `currentUser(request)`——它只查 `employee` 表。客户令牌的 subject 是 `client_account.id`，查不到 → 抛 401 → 前端 `request.js` 把 401 当作登录失效，清 token 并跳登录页。

| # | 端点 | 修复前 | 修复后 | 用户可感知影响 |
|---|---|---|---|---|
| 1 | `POST /auth/change-password` | **401** | 走 `ClientAccountService.changePassword`，改 `client_account.password_hash` | 客户在个人中心改密 → 被踢回登录页，且密码根本没改 |
| 2 | `POST /auth/bind-wechat` | **401** | 走 `ClientAccountService.bindWechat`，写 `client_account.openid` | 客户绑定微信 → 被踢回登录页，微信未绑定 |
| 3 | `POST /unit/account/password` | **401** | 按主体分流：客户改 `client_account`，旧门户令牌仍改 `use_unit` | 客户改密失败并被踢（`use_unit.password_hash` 在 V41 迁移后已清空，旧口径必然 401） |

修复方式统一为「按主体分流」，并把判定抽成一处：`AuthInterceptor.isCustomerRequest(request)`，与既有 `/auth/me` 的写法合并，避免以后又在别处手写内联判断。

### 3.1 实测证据（客户 `13800000003`）

== 用新口令重新登录 ==

### 3.2 一个静态扫描器抓不到的同类问题

第 3 个缺陷的表选错（`use_unit` vs `client_account`）发生在 **service 层**：`UnitAccountController` 方法体里只出现了 `ATTR_UNIT_ID`，方法体级扫描判定为「安全」。是人工沿调用链追到 `UnitAccountService.changePassword` 才发现它查的是 `use_unit` 表。

**边界说明**：本扫描器保证「controller 方法体层」不遗漏，service 层仍需人工追。已逐一复核的白名单 service 调用如下，均按 `useUnitId` 收敛：

| 端点组 | Service | 收敛依据 |
|---|---|---|
| `/unit/elevators`、`/unit/records/*`、`/unit/faults` | `UnitPortalService`、`UnitRecordService` | 入参 `resolveUnit()`，客户取 `client_account.use_unit_id` |
| `/unit/records/{id}/confirm` | `UnitRecordService.confirmAs` | 同上 + `signerOf()` 从 `client_account` 取真实签字人 |
| `GET /elevators*` | `ElevatorService.listViewForUnit/profileForUnit` | 独立客户方法，入参 `unitAnchor()` |
| `/unit/accounts` | `UnitAccountService.createAccount` | `PROVISION_ROLES` 校验，客户角色直接 403 |

## 五、白名单清理

### 5.1 删除 2 条死规则

| 规则 | 问题 |
|---|---|
| `/auth/client/switch-unit` | 无对应端点（真实能力叫 `select-unit`，且由 `sel=1` 短时令牌分支单独处理） |
| `/auth/client/bind-wechat` | 无对应端点（客户绑微信走 `/auth/bind-wechat` 或 `/auth/client/*` 均无此路径） |

死规则的危害不是「多放行一个不存在的路径」，而是**让人误判客户能力边界**：读白名单会以为客户能切换单位、能自助绑微信，实际 404。

### 5.2 收窄 1 处前缀

`GET /elevators/**` → 精确到 `GET /elevators`、`/elevators/by-code`、`/elevators/{id}/profile`（正则）。

原因：`GET /elevators/{id}/archive` 是**移交档案**端点，权限码 `handover:view`，客户角色不在授权表（`PermissionMatrix` 只授予 IM/MS/MM/PA/SA 与 IC/IP/IW/MT）。原来靠权限矩阵 403 兜住，数据没泄露，但客户不该「够得着」一个与自身无关的内部档案端点。收窄后返回更明确的 `403 客户账号仅可访问客户门户接口`。

### 5.3 保留 `/client/**`（未删）

该前缀下**当前无任何端点**，访问会 404。首版排查时按 fail-closed 原则删掉了它，但既有单测 `ClientTokenInterceptorTest.validClientTokenPassesOnClientPath` 以 `/client/records/pending` 作为「合法客户路径」基准——说明这是**既定设计预留**（P3 客户端点族），不是笔误。已恢复，并在注释里标注：

> 现状该前缀下尚无端点；保留是设计预留，但它属「前缀全放」，将来新增 `/client/*` 会自动对客户开放——若要长期不用建议整体删除。

**建议**（未执行，需产品确认）：`/unit/**` 与 `/client/**` 两套客户前缀并存，本身就是口径分裂的温床。若 `/client/**` 半年内不再使用，应删除并统一到 `/unit/**`。

### 5.4 删除第二个菜单入口 `GET /auth/menus`（2026-11-20 已执行）

排查中发现一个**白名单之外、但同属「双入口」性质**的问题：`GET /auth/menus` 对客户返回 `403`（不在客户白名单），而它和小程序的 `GET /me/menus` 在语义上都是「按角色下发菜单」。403 不清登录态，前端也只调 `/me/menus`，所以不构成运行故障；但它让「客户能拿到什么菜单」这件事有两个答案，读代码/读白名单的人容易误判。

处理：**整条删除**，而不是继续留着 403。

| 项 | 处理 |
|---|---|
| `AuthController.menus()` | 删除 |
| `MenuService`（含 `MenuServiceTest` 5 例） | 删除 |
| `AuthController` 构造器第 4 个形参 `menuService` | 删除（7 处单测构造同步） |
| `admin/src/api/auth.js` | 注释改为「后端 /auth/menus 已删除」，无 `getMenus` 封装可删 |
| E2E `cases.auth.js` | 原「GET /auth/menus（管理员）→ ok」改为「旧端点已删除 → 404」，**重加即红** |

**为什么能删**：该端点自 2026-11-16 起已注废弃（M5 起管理端菜单走 `admin/src/ui/menu-config.js` + permission-v2 本地投影），admin 前端无任何调用者；小程序只用 `/me/menus`。删除后菜单下发**只有一个入口**，且该入口本身已按主体分流（员工内部菜单 / 客户工作台菜单）。

**契约变化**：`GET /auth/menus` → `404 code=404「接口不存在」`（由 `GlobalExceptionHandler.handleNotFound` 统一封装，不再是 403 或空菜单）。同步记录见 `docs/04-接口文档.md` V2.69、`docs/14` §7.3。

### 5.5 连带删除 `POST /auth/bind-employee`、`POST /auth/bind-use-unit`（同日执行，V2.70）

同一类「第二个入口」在**令牌**上也有一个：这两个端点是登录后的「自铸角色令牌」通道——`bind-use-unit` 直接签发 `UNIT_ADMIN` 员工令牌，而 `bind-employee` 按 body 指定角色。越权防护本身有效（角色只取库内真实值，非本人角色一律 403），但它们是客户主体二分之后最容易口径回流的地方：一旦有人接个页面上去，客户账号就可能重新拿到员工角色令牌。

处理：连同私有 `roleLogin()`、`services/auth.js` 的 `bindEmployee/bindUseUnit`、mock 两条路由一并删除；E2E 由「WORKER 越权 403」改为 **404 锁死**。

> 判断口径：**保留 403 只能证明「现在拦得住」，删除 404 才能证明「以后没人能绕」**。同类清理优先选后者——尤其是能力本身已经不再需要的时候。

### 7.1 连带修的一处前端体验

`pages/profile/password.js` 原来无论员工还是客户，改密成功都提示「修改成功，请牢记新密码」然后 `nav.back()`。但客户改密会由 `ClientAccountService` 清会话（安全设计：口令变更即令牌作废），员工改密不动会话。修复前客户根本改不了密（401），所以这个差异一直没暴露；修复后客户第一次能真正改密，返回上一页就会因 401 被静默踢回登录页。

现按 `isCustomerPrincipal()` 分流：客户提示「修改成功，请用新密码重新登录」并 `reLaunch` 登录页；员工保持原行为。
